## Context

2026-09-08 的实际桌面端检查显示：订单页同屏展示空订单列表、完整建单表单和未选择订单的详情占位；履约页只展示订单选择器；工资、财务、客户和商品也普遍同时展示列表和创建表单。系统的领域规则已在 V2 中稳定，本次不应重新设计业务规则，而应让界面遵循负责人的实际工作顺序。

## Goals / Non-Goals

**Goals:**

- 区分浏览列表、创建对象、处理详情和维护资料四类任务。
- 订单新建和商品新建提供足够完整的编辑空间；客户、收支登记可按需展开。
- 履约首页先回答“现在有哪些待做事项”，再让负责人进入具体订单。
- 在空数据时明确告诉用户先建立哪些基础资料，并提供可达入口。
- 侧栏语言和分组面向工作室负责人，而不是暴露 V2、数据隔离或迁移概念。

**Non-Goals:**

- 不新增账户、权限、云同步、原料库存或自动决策规则。
- 不把订单创建强制拆成不可回退的多步向导。
- 不调整生产、质检、工资、财务、售后的事实口径。
- 不引入路由库；现有单页桌面壳以内的受控工作状态足以表达页面切换。

## Decisions

### 订单使用明确工作状态，而不是同屏三栏

`OrdersPage` 维护 `list`、`create`、`detail` 三个状态。列表状态只承载查询、选择和新建入口；创建状态提供完整多商品表单；详情状态承载金额调整、资金、分批发货和售后。创建成功直接进入新订单详情，避免再让用户回到列表寻找刚创建的数据。

不采用抽屉：订单表单和详情后续都会继续增长，抽屉宽度会限制多商品编辑与长备注阅读。不采用强制向导：定制订单需要随时修改客户、商品数量、单价和确认金额。

### 履约首页先展示跨订单队列

`useFulfillment` 在已有订单摘要基础上读取订单及其订单商品履约余额，导出由订单、客户、商品和阶段余额组成的队列项。履约页聚合显示制作、捏毛装袋、待打包、待发货数量，并列出尚有未完成数量的订单商品；点击某项进入原有单订单履约处理区。

现阶段使用现有 IPC 聚合读取，避免为纯 UI 首屏重构引入新的数据库表或接口。订单量显著增长后可再把该聚合下沉到专用查询接口。

### 基础资料和操作表单按需展开

客户和商品页面初始只展示列表和“新建”入口；客户创建以轻量编辑区按需展开，商品创建/编辑使用完整工作区。工资页以“工资结算”和“人员与时薪”切换，结算新建按需进入编辑状态。财务页保留经营概览和流水，收支登记按需展开，待报销独立保留为持续待办。

### 导航按工作性质分组

侧栏保持现有八个入口，但添加业务运营、资金与分析、基础资料分组。客户和商品暂不隐藏，避免首次建档路径变深；设置只承载财务类目和垫付人等规则资料。

## Risks / Trade-offs

- [履约客户端聚合会增加首屏读取] → 仅读取订单及其商品履约余额；数据量增加时演进为后端汇总接口。
- [同页受控状态没有 URL] → 桌面本地应用没有分享/刷新 URL 的需求，能以最低复杂度保留当前应用壳。
- [页面切换会打断未提交草稿] → 创建/编辑页面仅在显式“返回/取消”时离开；提交失败时草稿保持不变。
- [一次重构多个模块风险较高] → 将测试与验证按阶段写入单一提案，每完成一阶段做定向测试和界面检查。

## Migration Plan

1. 先为目标操作流添加会失败的页面契约测试。
2. 实施应用壳、订单和履约首页的 P0 操作流，并验证。
3. 实施客户、商品、工资和财务的按需表单与导航分组，并验证。
4. 完整运行测试、类型检查、Lint、构建，在运行中的桌面端检查空数据和有订单状态；不改动本地业务数据。
5. 如需回滚，只回滚本提案涉及的渲染层和履约 composable；底层事实数据无需迁移。
