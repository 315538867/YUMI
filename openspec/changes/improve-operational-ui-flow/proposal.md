## Why

当前桌面端把列表、创建表单和对象详情长期并列在同一页面。对订单这类多商品、分批发货、售后和资金调整并存的业务，这会同时呈现三种互相冲突的工作任务；空数据时还会让用户看到无法完成的订单表单。履约页面又要求先选订单，无法作为负责人每天查看待办的入口。

## What Changes

- 将订单调整为“订单列表 → 新建订单 → 订单详情”三个明确工作状态；创建订单使用完整页面，不强制多步向导。
- 将履约首页改为全局待处理队列，订单选择仅作为筛选/进入详情的方式。
- 将客户、商品、兼职人员、工资结算、日常收支等页面从长期并列的“列表 + 表单”改为按操作展开的工作区。
- 将侧栏按业务运营、资金分析和基础资料分组，并移除面向使用者的 V2、迁移和内部状态文案。
- 保留全部既有 V2 本地接口、数据口径和业务规则；本次只调整前端操作流与履约读取聚合。

## Capabilities

### New Capabilities

- `operational-ui-flow`: 为负责人提供按“查找、创建、处理后续动作、维护基础资料”分层的桌面端业务操作流。

### Modified Capabilities

- `multi-process-fulfillment`: 履约入口增加跨订单的待处理队列，不再要求先选择订单。

## Impact

- 主要修改 `src/renderer/pages/`、`src/renderer/composables/use-fulfillment.ts`、`src/renderer/pages/app.tsx`、`src/renderer/styles/app.css` 与页面契约测试。
- 不修改 SQLite schema、订单/资金/工资/售后领域规则，不破坏已有 V2 IPC。
- 分阶段在同一个提案内实施与验证，避免创建多份相互依赖的 UI 提案。
