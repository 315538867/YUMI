## Context

参见 `proposal.md`。当前 `App` 使用 `inspectingOrderId`、局部人员详情状态和局部排班详情状态分别驱动三个 `Dialog.Root`。订单详情的数据契约与仓储查询已包含 `OrderDetail.notes`，但渲染层未使用该字段。详情中的编辑、状态更新和完成登记依赖局部状态与既有 IPC，不需要数据迁移。

## Goals / Non-Goals

**Goals:**

- 用单一页面级详情目标管理订单、人员和排班详情的打开、返回与跨详情跳转。
- 复用现有详情内容、读取和保存逻辑，仅替换承载详情的模态容器。
- 为订单备注提供保留换行的条件式展示。
- 保持短时输入或确认操作仍使用既有弹窗。

**Non-Goals:**

- 不引入 URL 路由、浏览器历史、深链接或新的 IPC 接口。
- 不调整订单、人员、排班的领域规则、数据表或数据迁移。
- 不将新建与编辑表单整体改造为独立页面。

## Decisions

### 1. 在 `App` 提升统一详情目标状态

使用带 `kind` 和 `id` 的详情目标替代订单和排班的顶层检查器状态，并将人员详情的打开回调提升至 `App`。打开详情时同步切换对应导航视图；关闭详情时仅清空详情目标，因而返回该目标所属列表。

备选方案是在三个工作区内继续维护各自的详情状态。该方案无法让订单、人员与排班详情稳定地跨区跳转，也会保留多个并存的弹窗状态，因此不采用。

### 2. 将三个检查器改为页面级详情组件

保留现有读取、刷新、保存、错误处理和嵌套短流程窗口；将 `Dialog.Root`、`Dialog.Content`、关闭按钮替换为正常文档流的详情工作区容器和返回按钮。组件接收 `onBack`，而不是 `onOpenChange`。

备选方案是在详情弹窗中增加更大尺寸或全屏模式。该方案仍保留模态焦点与层叠窗口问题，不能满足页面工作区目标，因此不采用。

### 3. 跨详情跳转替换当前详情目标

人员详情的“查看订单/班次”和订单详情的“查看班次”通过 App 级回调替换当前详情目标。切换后只渲染一个页面级详情组件；返回操作回到目标所属列表，不维护额外的详情栈。

备选方案是维护历史栈以支持逐级返回。当前需求只要求返回相应列表，历史栈会提高状态复杂度，暂不引入。

### 4. 订单备注条件展示并保留换行

订单详情仅在 `order.notes` 为非空时渲染“订单备注”区块，并通过 CSS 的 `white-space: pre-wrap` 保留管理员录入的分行。数据读取继续使用既有 `OrderDetail.notes`。

## Risks / Trade-offs

- [详情状态提升后遗漏某个旧回调] → 使用界面源代码契约测试覆盖页面详情、备注和已移除的详情标题弹窗，并以 TypeScript 检查所有属性传递。
- [长详情内容在窄窗口下可读性下降] → 使用现有工作区内容区域的滚动能力，限制详情内容最大宽度并复用响应式网格规则。
- [跨详情跳转后用户期望回到上一详情] → 当前返回明确回到目标所属列表；不维护未被需求要求的历史栈，后续可独立扩展。

## Migration Plan

1. 增加失败的界面契约测试，确认当前代码仍以详情弹窗承载且未渲染订单备注。
2. 提升详情状态并替换三个详情容器，保留短流程对话框。
3. 添加样式与备注渲染，运行完整质量检查。
4. 本变更仅影响客户端渲染，发布后刷新应用即可生效；如需回滚，可回退本次提交，不涉及数据回滚。
