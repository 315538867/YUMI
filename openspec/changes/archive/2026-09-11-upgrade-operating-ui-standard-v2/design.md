## Context

本变更落实 `docs/solutions/2026-09-10-yumi-operating-ui-design-standard-v2-solution.md` 与 `docs/solutions/2026-09-10-order-information-architecture-and-workflow-solution.md` 已确认的规范。当前 renderer 已有 `YumiPageHeader`、`YumiBusinessList`、`YumiButton` 和 `yumi-page-tabs`，但 `yumi-page-tabs` 同时用于设置页的两级标签，订单详情则把动作放在概览底部。订单页已有列表/创建/详情状态、订单级导出和按 `shipmentId` 导出清单的桥接；资金已有记录和冲正服务。发货批次尚无作废状态和对应逆向数量处理。

当前仍有 `yumi-core-capability-recovery` 处于最后人工验证阶段。本变更必须复用其已完成的订单金额、资金、导出和履约数据契约，不重复实现其领域规则；涉及相同文件时，实施应先确认该变更没有未合入的冲突修改。

## Goals / Non-Goals

**Goals:**

- 以共享组件和样式表达动作层级、主标签、次级分段控件和只读优先规则。
- 让订单模块成为完整样板：列表入口、只读详情、紧凑概览、发货批次、资金流水和可追溯的批次作废；再将相同页面模式扩展到全部现有业务页面。
- 统一用户可见的“排班”和“发货”语义，不破坏既有 fulfillment 内部数据契约。
- 对发货作废提供从 SQLite 到 renderer 的完整链路，并确保数量汇总、待发校验和导出只使用有效批次。

**Non-Goals:**

- 不复制参考稿的具体颜色值；YUMI 的颜色必须通过独立定制的语义 token 统一管理。
- 不重写订单金额、订单变更、资金冲正、工作簿字段或履约事件的既有领域规则。
- 不把排班页面改造成订单发货页面，也不修改内部 fulfillment 路由、IPC 名称或历史审计事件名称。
- 不进行高风险的大爆炸重写；全局页面迁移按列表、详情/记录、工作台/排班和基础资料四类分阶段推进，但不得将订单样板视为本变更的最终边界。

## Decisions

### 1. 通过共享表现组件分离主标签与次级分段控件

新增或扩展共享 UI 导出，提供语义化的主标签与次级分段控件；它们接收当前值、项目和切换回调，采用可访问的导航/按钮语义。`yumi-page-tabs` 不再承担两种层级的视觉职责：主标签使用文字加底部指示，次级控件使用浅底容器和紧凑选中块。

选择此方案是为了让订单详情和设置页复用同一规则，而不是在各页手写按钮 variant。替代方案是在 CSS 中根据父页面选择器覆盖现有按钮；该方案会继续让标签语义由页面偶然结构决定，难以在后续页面稳定复用。

### 2. 订单状态机保持现有三态，收紧入口与编辑边界

继续使用 `OrdersPage` 的 `list | create | detail` 工作区状态和 `overview | fulfillment | funds | after_sales` 内部视图状态，只将用户可见 `fulfillment` 标签映射为“发货”。订单页初始化保持 `list`；行打开进入 `detail + overview`；编辑订单内容改为详情页头部明确触发的抽屉/互斥编辑态。创建保存、内容变更保存、发货/资金写入后均刷新当前实体并回到对应只读列表/详情。

选择保留内部状态名可减少路由和工作台深链风险。替代方案是重命名全部内部 fulfillment 类型和目标字段；这会扩大到后端和既有工作台逻辑，不能为用户可见命名收益提供足够回报。

### 3. 概览以四项横向指标、商品表和两组档案替代大面积卡片

订单详情头部放订单编号、客户、日期、状态和页面动作；概览只保留订单金额、累计收款、待收、发货进度四项紧凑指标。订单商品使用 `YumiDataTable` 或语义等价的密集表格承载并显示商品合计，客户与订单、交付与生产使用可扫描的说明列表；最近发货只展示最近批次的只读摘要，并提供进入完整发货记录的局部入口。页面头部保留订单表导出、更多操作和编辑，发货清单出口只存在于具体批次。

这样信息密度与动作归属同时提升。替代方案是保留四个大卡片并调整列数；它无法解决卡片尺寸与订单内容稀疏、底部动作漂移的问题。

### 4. 发货视图以批次列表为默认，批次操作绑定具体记录

订单“发货”视图默认展示按时间倒序的 `YumiBusinessList`（或表格）批次记录，显示批次编号、发货日期、承运商/单号、商品数量、状态和登记信息。详情页头部为“新建发货”和“导出发货汇总”；新建表单使用现有 `YumiSheet`。每个批次详情/行承载“查看详情”“导出本批清单”和“作废本批”。

选择记录绑定的出口，使 `exportShippingList(orderId, shipmentId)` 始终有明确 `shipmentId`。替代方案是保留概览的全局清单导出并弹出批次选择；虽然技术可行，但会继续模糊清单与批次的归属。

### 5. 发货作废使用显式生命周期与逆向履约事件

扩展 `V2Shipment` 为可区分有效与已作废的记录，并新增作废输入（原因、作废时间由服务端时钟生成）和 `voidShipment` API。SQLite 迁移在 `shipments` 增加作废状态、原因和时间字段；仓储读取完整历史，服务端只允许对有效批次作废。作废事务必须：标记批次为已作废、保留批次/商品快照、为每个 `shipment_item` 写入数量为原数量负值的逆向 fulfillment 事件或等价的可审计事件，并记录审计日志。所有可发数量、累计已发/待发、订单摘要和导出汇总只计算有效净发货结果；按批导出清单仍允许读取其历史快照，并明确标识该批次已作废。

选择逆向事件而不是删除原事件，原因是既有履约状态由事件叠加计算，逆向事件可在不改写历史的前提下恢复待发数量。替代方案是删除原 shipment 与事件，或只在 renderer 忽略作废批次；前者破坏审计，后者会让履约状态和可发数量继续错误。

### 6. 资金默认列表，冲正由原流水发起

资金子视图上方只显示紧凑汇总和头部登记动作；流水行展示类型、实际日期、金额、支付方式、凭证和链路状态。登记表单进入抽屉；冲正并更正操作从原流水行/详情预置原记录，继续调用既有 `correctFund`，不复制该领域逻辑。

选择复用现有资金服务可避免形成第二套更正规则。替代方案是只隐藏表单而保留全局“原资金流水”选择器；该方案不能满足从事实上下文发起更正的可追溯交互。

## Risks / Trade-offs

- [发货作废与既有已发数量算法不一致] → 在领域服务、仓储、工作簿和 renderer 共用“有效批次/净事件”计算，并以首次发货、多次发货、作废和再次发货的测试矩阵验证。
- [活跃的核心恢复变更与订单页同时修改] → 实施前检查 git 状态和 active change 状态，优先基于已完成契约做小范围渲染层改动；若存在未合入冲突，先协调变更顺序而非覆盖文件。
- [名称替换误伤内部技术标识] → 仅替换用户可见文案，保留 `fulfillment` 类型、API 与数据字段，使用源码测试区分文案与内部识别符。
- [新增共享标签组件影响窄屏] → 在组件 CSS 中定义 720px 以下的横向滚动/换行规则，并为键盘焦点、`aria-current` 或 `aria-pressed` 添加测试。

## Migration Plan

1. 新增共享标签和页面动作样式，先将设置页切换到主/次标签组件，验证层级不再同形。
2. 调整应用导航和排班页所有用户可见“履约”文案；保持现有导航 id 与 target 结构。
3. 调整订单页的列表入口、详情头部、概览商品表、发货/资金默认列表和抽屉入口；保留当前订单、资金与导出服务调用。
4. 增加发货作废契约、数据库迁移、仓储/服务/IPC/preload/composable，实现逆向事件、有效批次汇总与导出标识。
5. 补齐领域、IPC、renderer、可访问性和样式回归测试，执行 typecheck、lint、test、build、`git diff --check` 与严格 OpenSpec 验证。

如果需要回滚，可先回退 renderer 组件/样式和导航文案；数据库迁移保留新作废字段且旧代码可忽略其 nullable 字段。已经作废的批次不得通过回滚被物理删除，恢复发布时仍需保留历史和逆向事件。

### 8. 视觉基线以参考稿的结构为准，颜色使用 YUMI 独立语义色板

桌面人工验收发现，仅迁移交互组件不足以达到目标。订单列表、概览、发货批次和资金流水必须以确认参考稿的容器层级、栅格、表头、记录密度、辅助信息和动作归属作为视觉结构基线；颜色不从参考稿复制。

颜色由 `tokens.css` 中独立定义的画布、中性色、品牌、状态与焦点 token 承担。任何按钮、标签、表格选中态和空状态均消费语义 token；不得在业务页面用硬编码颜色模拟参考稿，也不得继续保留跨页面不一致的旧色彩。

选择此方案可以同时满足“视觉细节对齐”和“品牌颜色独立定制”。替代方案是直接复制参考稿颜色，或只在现有页面上做局部 CSS 微调；前者不满足品牌定制，后者会继续保留当前容器、密度和表格层级偏差。

### 9. 视觉规范作为全局经营界面契约，而非订单局部样式

订单参考稿确认的是全站可复用的经营界面语言，不是订单模块的专属皮肤。`tokens.css`、共享 UI 组件和页面模式必须共同构成唯一来源：所有业务页面使用同一套页面头部、动作分级、主/次标签、容器、表格、指标摘要、表单和反馈状态规则。

全局落地按页面类型而非按颜色替换推进：

1. **列表型页面**采用“页头 + 工具条 + 单一业务容器 + 固定列数据表”，行内只放对象相关动作；
2. **详情/记录型页面**采用“页头动作 + 连续摘要 + 一级标签 + 内容分组或记录表”，默认查看，编辑为显式低频状态；
3. **工作台/排班型页面**采用“主视图标签 + 任务/记录主体”，筛选归入工具条，禁止再堆叠同形 Tab；
4. **基础资料型页面**采用“页头 + 次级范围切换 + 可维护记录主体”，停用、删除等危险动作保留在对象上下文；
5. **视觉验收**同时检查桌面和窄屏下的容器、栅格、行高、信息主次、状态和动作归属，不以功能可用替代视觉完成。

颜色继续只由 YUMI 独立语义 token 决定；参考稿只提供信息结构、内容密度与交互层级，不提供配色来源。

### 11. 全局交付以页面清单和同一验收口径管理，不以订单样板收口

当前 renderer 的业务页清单为订单、客户、商品、排班、工作安排、财务、工资结算、报表、设置与工作台。每个页面都必须在对应类型的迁移任务中完成共同验收：页面级动作归属页头右侧；列表/记录主体优先使用工具条、单一容器和具名数据表；详情默认只读并以连续摘要、信息分组或记录表组织；一级与二级切换只使用各自语义控件；编辑、作废、冲正、批量处理等低频或危险动作只能在明确对象上下文与确认流程中发生。

实施顺序按风险控制分为：先完成订单样板与共享组件，再迁移高频列表和记录主体，然后覆盖工作台、排班、基础资料和其余报表，最后以 1440px 与窄屏截图对全部页面逐项复验。阶段完成只能更新该阶段状态；只有页面清单全部通过自动化与人工视觉核对，才可把全局设计系统标记为完成。

### 10. 列表工具条和记录表采用共享骨架，页面动作与记录动作分层

列表型经营页面使用 `YumiPageHeader + YumiListToolbar + YumiListSurface + YumiDataTable` 的组合。页头只放新建、导出等影响整个页面的动作；工具条只放关键词、状态/日期范围等影响当前记录集的控件及结果统计；表格行只放查看详情或对应对象的受控动作。

`YumiDataTable` 必须接收业务可访问名称，使辅助技术可以区分“客户列表”“商品列表”“兼职人员列表”等记录主体。工具条与容器的响应式规则由共享 CSS 负责，避免每个页面以独立卡片、绝对定位或无名称表格重建一套布局。

已接入该组合的高频列表包括订单、客户、商品、兼职人员、工资结算，以及财务现金流水、待报销、订单售后、订单级资金流水与发货批次，以验证检索、状态筛选、结果计数、只读详情入口和窄屏换行；经营报表的交期风险记录也已采用工具条和具名表格。其余报告记录区仍按同一规则迁移，且所有页面仍需完成桌面与窄屏人工视觉验收后才能标记完成。
