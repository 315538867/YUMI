## Context

参见 proposal.md。当前履约页面已获取订单与履约进度，但没有工作安排与人员字典的聚合层；工作安排页面已提供创建、报数和质检入口。共享契约中的任务带有 `orderItemId`、`processType`、`plannedQuantity`、`assignedOn` 和状态，足以建立日期级双视角，无需增加 IPC 或数据库字段。

## Goals / Non-Goals

**Goals:**

- 在渲染层构建可测试的订单商品 × 工序 × 任务聚合模型。
- 让订单视角、人员周历与派工抽屉使用同一套工作安排事实和刷新流程。
- 保留订单产品操作台与既有任务报数、质检业务逻辑，仅增加精确任务的导航编排。

**Non-Goals:**

- 不创建新的主进程接口、数据库迁移或服务端排班上限校验。
- 不恢复 V1 月度风险图、小时格、开始/结束时间或日内冲突判断。
- 不重写既有工作安排页的报数和质检表单。

## Decisions

### 1. 以任务而非工作安排为聚合原子

一个工作安排可以包含多个订单商品任务；履约行、周历卡片和待派计算均以单个任务作为原子，通过 `orderItemId + processType` 归并。

选择原因：避免同一安排中的其他订单商品错误出现在当前行，且能为任务卡提供精确处理导航。替代方案是按工作安排聚合后再展示任务列表，但会让数量计算和跨订单显示更容易出错。

### 2. 有效已派状态固定为 pending 与 pending_inspection

仅两种仍需要后续处理的任务预占当前工序在制数量；confirmed 和 cancelled 不预占。派工视图将同时计算 `unassigned = max(wip - reserved, 0)` 与 `overassigned = max(reserved - wip, 0)`。

选择原因：与现有提交完成—质检确认的履约事实边界一致，且让待质检任务在确认前继续可见。替代方案是完成申报后立即释放数量，但会允许同一在制数量被重复派工。

### 3. 行内抽屉复用既有创建工作安排契约

派工抽屉只负责收集预填上下文和表单输入，仍调用既有创建接口。订单行入口预填订单商品和工序；人员周历入口预填人员和日期，要求用户再选订单商品和工序。

选择原因：不引入第二套派工数据模型，两个视角保存后只需调用同一个 reload。替代方案是把周历的 `+` 仅导航到旧页面，但会破坏“看到即派”的操作闭环。

### 4. 履约页顶层维护视角和导航协调，纯计算下沉到 composable

`useFulfillment` 负责并行加载订单、履约进度、工作安排和人员，并导出纯派生函数/视图模型；页面维护视角切换、周起始日、抽屉状态及导航。订单视角、周历和抽屉拆为子组件。

选择原因：让数量计算可以单测，避免履约入口继续膨胀成不可测试的大组件。替代方案是全部内联在页面中，但会使刷新、筛选和点击冒泡难以验证。

### 5. 前端阻止常规超派并显式暴露已有超派

抽屉以当前待派数量为上限；刷新后若读到超派，不修改历史任务而以异常状态展示。由于本轮不改后端，并发窗口仍通过刷新和异常暴露处理。

选择原因：满足当前“零后端改动”的边界，保持可追溯任务事实。替代方案是增加后端原子校验；它能更强地阻止并发超派，但超出本轮已确认范围。

## Risks / Trade-offs

- [并发创建可能产生超派] → 保存成功后统一 reload，并把超派显示为可处理异常；后续如出现多人并行使用需求，再单独扩展服务端原子校验。
- [订单量大时工作安排全量读取增加渲染压力] → 本轮先在本地桌面应用按需做内存聚合，并将聚合函数保持纯净；性能数据出现后再增加范围查询。
- [行点击与内部动作冲突] → 所有派工与任务卡处理器显式阻止事件冒泡，并加交互测试。
- [人员已删除] → 使用稳定 workerId 聚合，名称不存在时显示“已删除人员”，不丢失任务。

## Migration Plan

1. 先加入聚合函数及失败测试，固定状态、数量和多任务安排的语义。
2. 接入订单视角和精确任务导航，再接入共用派工抽屉与周历。
3. 执行类型检查、单元/组件测试和 Electron 手工验收。
4. 回滚时仅撤回渲染层新增视图与组件；已有工作安排和履约事件数据不需要迁移或回滚。
