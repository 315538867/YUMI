设计的关键约束是：业务规则不能分散在页面组件中；排班同时受人员时间、订单交期和商品模具批次日产能约束；财务历史必须避免被商品默认参数变更影响；本地数据必须可备份和恢复。

## Goals / Non-Goals

**Goals:**

- 在 Electron 内实现清晰的本地后端、领域服务和 SQLite 数据边界。
- 使 UI 可预览成本和排班风险，但由主进程执行权威计算和持久化。
- 为订单、收付款、排班、实际完成和审计建立可事务化的写入流程。
- 让未来迁移到远程 API 或多端同步时可以复用领域规则。

**Non-Goals:**

- 不在第一期运行独立 HTTP 后端或开放本机端口。
- 不实现复杂库存、采购、客户营销、会计或自动批次推算。
- 不通过“强制阻止”拦截超工时、超模具产能或超交期排班；这些是可审计的风险确认。

## Decisions

### 决策：以 Electron Main 作为本地后端

Renderer 只负责页面、表格、日历和即时预览；Preload 暴露按业务命名的受限 API；Main 进程负责 IPC 入参校验、领域服务、SQLite、附件、备份和审计。

选择原因：单机离线应用不需要额外服务端口，且将系统和数据写入能力留在 Main 进程能防止 UI 直接绕过规则。

备选方案：本机 Fastify/Nest HTTP 服务会增加端口、生命周期和部署复杂度；云端 API 留到需要多端协作时再引入。

### 决策：模块化领域服务与仓储分层

Main 层按 `catalog`、`orders`、`payments`、`scheduling`、`production`、`analytics`、`backup`、`audit` 拆分。每个模块包含输入验证、应用服务、领域计算和仓储访问；Repository 只处理数据库读写。

写入调用链固定为：`Renderer → preload API → IPC handler → application service → domain service → repository → SQLite transaction`。

### 决策：订单商品保存财务与制作快照，物理模具产能读取当前配置

订单商品创建时复制商品名称、价格、缝边单价、材料重量、损耗率、包装成本、标准制作时长、提成和固定成本时薪。这样商品默认参数调整不会污染历史订单。

模具数量、单模具产出和每日最大批次数代表当前物理资源，对未完成订单的排产按商品当前配置计算。每次产能配置变更记录审计日志。

### 决策：Shift 和 ShiftTask 分离

`Shift` 表达兼职人员在某日的开始和结束时间；`ShiftTask` 表达该时段内一个订单商品的计划数量和实际完成。一个 Shift 可以包含多个 ShiftTask，便于同一人员在同一时段制作多种商品。

预计任务分钟数为 `计划数量 × 商品标准制作时长`；Shift 总预计分钟数与时段分钟数比较，生成超时或未满时长风险。

### 决策：模具产能按商品和日汇总

同一商品、同一天的所有计划数量共同占用产能：

```text
日最大产能 = 模具数量 × 单模具每批产出 × 每日最大批次数
```

保存或预览 ShiftTask 时，服务汇总该商品同日的其他有效计划任务。缺勤、取消和未完成任务进入待补排时必须释放原计划数量占用。

### 决策：风险采用“预览 → 确认 → 审计保存”

排班保存分两步：首次 `schedule.previewShift` 返回标准化风险代码；用户确认后传回 `confirmedWarningCodes` 调用 `schedule.saveShift`。没有确认的风险不保存；已确认风险可保存，并记录风险、时间和关联业务对象。

人员时间重叠、工时超出或未满、模具超载和交期不足均采用该流程。数据损坏、非法金额、缺少订单商品或不存在的人员仍属于硬错误，必须拒绝保存。

### 决策：成本区分预计与实际

订单创建时提供预计胶水、包装、工时、提成和固定成本。实际完成后，实际任务工时和合格完成数量更新实际人工成本与提成；第一期材料成本默认使用订单快照的预计材料成本，预留后续材料调整能力。

月固定成本通过“月度固定成本 ÷ 当月目标生产工时”得到工作室固定成本时薪，订单创建时保存当前费率快照。

### 决策：SQLite 迁移、附件和备份包

SQLite 表结构通过可重复执行的迁移管理。付款凭证和商品图片存入应用数据目录的受控附件路径，数据库存储元数据和相对路径。备份包包含数据库和附件清单；恢复前创建当前备份。

### 决策：渲染端按功能划分，复用桌面设计系统

Renderer 使用 `pages` 管理工作区，使用 `features` 封装订单、排班、商品和人员的状态与交互，使用 `design-system` 统一 Radix Themes 的颜色、密度、表格、命令栏、检查器和风险提示。排班采用按人员分组、按日期和时间展示的资源日历；月视图仅显示产能和风险聚合。

## Risks / Trade-offs

- [单机数据丢失或电脑故障] → 启动/退出自动备份、手动备份、恢复前备份和可导出业务数据。
- [商品参数修改导致历史计算混乱] → 财务与制作参数写入订单商品快照；物理产能变更单独审计。
- [排班超限确认被滥用] → 风险确认保留审计记录，并在订单、日历和报表中持续展示。
- [同一 Shift 中多个任务难以分配实际工时] → 每个 ShiftTask 独立记录实际工时；Main 端校验任务实际工时汇总并提示超过 Shift 实际时长的异常。
- [本地附件被用户手动删除] → 应用在读取附件失败时显示缺失状态，不删除业务流水；备份校验附件清单。
- [未来多端同步时冲突] → 领域服务与仓储接口不依赖 IPC，未来替换为远程 API 和中心数据库时保留核心规则。

## Migration Plan

1. 初始化 Electron、React、TypeScript、Radix Themes、SQLite 和测试基础设施。
2. 创建数据库迁移、应用数据目录和备份目录；首次启动创建空数据库。
3. 按商品、订单收付款、排班生产、报表的顺序交付模块。
4. 每一阶段升级数据库前自动创建结构迁移前备份；迁移失败时回滚事务并保留原数据库。
5. 若应用升级引入不兼容数据迁移，应用必须阻止继续写入、提示恢复最近备份或执行专用迁移。
