# YUMI V2 核心业务重构技术设计

- 关联提案：`rebuild-yumi-v2-core-business`
- 关联方案：`docs/solutions/2026-09-07-yumi-v2-core-business-reconstruction-solution.md`（v2.1）
- 设计日期：2026-09-07
- 状态：已规划，待实施授权
- 实施方式：一个 OpenSpec 提案，按阶段 A 至 E 顺序实施；每个阶段完成后在同一 `tasks.md` 更新证据

## Context

详见 `proposal.md`。当前 V1 的 Electron 组合根打开 `yumi-studio.sqlite`，通过单体 `StudioRepository`、`StudioService`、`src/shared/contracts.ts` 和 `src/renderer/pages/app.tsx` 支撑订单、排班、生产和报告。该形态无法表达以下已确认规则：四道工序的分离流转；任务完成与次日质检分离；制作/捏毛不合格的不同扣款；排班与考勤两种工资参考；负责人最终实发；现金流水与订单核算成本的分离；私人垫付整笔报销；以及大订单的分批发货和弹性售后。

V1 数据均为测试数据，不迁移。V2 需要从空库开始，在一个连续提案中先建立事实模型，再按业务依赖逐步开放履约、结算、财务和报告。阶段拆分仅用于实施、验收和风险控制，不代表多个提案或多个独立业务模型。

## Goals / Non-Goals

**Goals:**

- 用独立 V2 数据库、附件和备份空间承载所有正式业务事实，不改写 V1 数据。
- 将订单金额、订单内容、订单资金、履约数量、工资结算、实际现金流水和订单核算成本明确分离。
- 固定制作、捏毛装袋、打包、发货四道工序，支持期初在制品、返工、补发和分批发货。
- 对不可自动判断的售后责任、收费、后续任务、工资最终实发保留负责人决策及备注。
- 使 renderer、preload、IPC、service、repository 和 domain 使用分领域契约，避免单体页面/服务继续膨胀。
- 在同一提案内按可验证阶段推进，每个阶段都有独立验证点和不跨越的业务边界。

**Non-Goals:**

- 不实现原料库存、原料采购分摊、银行/支付/打卡自动同步、收入账户管理、会计凭证、预计收款提醒、物流轨迹或可配置流程引擎。
- 不将房租、水电、物业、公共材料或日常采购自动关联到订单或分摊为订单成本。
- 不自动决定售后责任、对客户收费、创建补发任务或退款。
- 不迁移、导出为 V2、自动删除或在 V2 页面显示 V1 测试业务数据。

## Decisions

### 1. V2 使用独立存储空间与独立迁移序列

组合根以集中 `V2StorageConfig` 派生 `yumi-studio-v2.sqlite`、`attachments-v2` 和 V2 备份目录。V2 连接使用 `v2_schema_migrations`，开启外键、WAL 和 busy timeout；恢复仅接受带 V2 元数据的备份，并先创建当前 V2 安全备份。选择独立文件而非清空 V1 表，可以在不做迁移的前提下保留 V1 回退参考，并杜绝旧查询误读新事实。

### 2. 事实表优先，摘要只读派生

V2 的核心事实表包括：客户、商品、订单、订单商品快照、金额调整、订单变更、统一财务流水、发货批次、工作安排、工序任务、完成申报、质检、履约事件、工资结算、扣款、售后、类目、垫付人、报销、附件与审计。订单总额、净收、待收、阶段数量、两种工资参考、待抵扣余额、月度经营结果和订单直接利润均由事实计算或以只读摘要缓存，不允许负责人直接覆盖。

金额统一使用整数分；数量使用非负整数；日期使用 `YYYY-MM-DD`；时间戳使用 ISO 8601。每个跨表确认操作使用一个 SQLite 事务，失败时不留下部分事实或孤立审计记录。

### 3. 订单金额、内容、资金和核算成本分开建模

`orders.initial_confirmed_amount_cents` 仅记录初始确认金额；`order_amount_adjustments` 保存之后的正负调整；`order_change_records` 保存商品、数量、包装、配饰等变更的前后快照；`financial_entries` 保存实际收款、退款、售后收费、工资和日常资金事实。计算规则：

```text
当前订单金额 = 初始确认金额 + 金额调整合计
实际净收款 = 实际收入合计 - 实际退款合计
当前待收 = 当前订单金额 - 实际净收款
订单直接利润参考 = 订单净收款 - 订单核算成本
月度经营结果 = 月度实际收入 - 月度实际经营支出
```

订单内容变更不自动改金额；订单减额不自动退款；已发生资金纠错通过冲正和新记录，而非覆盖原记录。订单核算成本由商品快照、已确认工序结果和售后核算成本组成；日常现金支出不关联订单。

### 4. 四工序数量流转以履约事件为唯一来源

四道工序固定为：制作、捏毛装袋、打包、发货。工作安排按日期、兼职人员和工序建立，可含多个同工序任务。制作计划分钟默认使用“商品标准制作分钟 × 计划数量 + 负责人额外预留”；其余工序计划分钟由负责人输入。完成申报和次日质检分离；只有质检合格数量才产生下一阶段可用量。期初在制品仅能进入待捏毛装袋、待打包或待发货，绝不反推历史工资/成本。

`fulfillment_events` 是阶段数量的唯一来源，禁止直接更新订单商品的“完成数”。阶段 A 先以订单确认数量限制发货，阶段 B 引入履约事件后把上限收紧为待发货可用量。

### 5. 工资结算保留两种参考，最终工资由负责人确认

每次结算选择兼职人员和任意日期范围。排班口径按已确认任务的计划分钟，考勤口径按负责人填写的考勤总分钟；两种口径共享提成、扣款和任务来源，只变更时薪分钟。制作/捏毛装袋合格计提成，打包/发货仅计时薪；制作不合格扣制作提成、标准分钟时薪和胶水，捏毛不合格扣捏毛提成及“计划分钟 ÷ 计划数量 × 不合格数量”时薪。扣款不可使本期参考或最终实发为负，余额顺延。

负责人填写最终实发金额、付款日期和备注；确认时锁定任务/扣款分配，并在同一事务创建唯一工资支出。返工或补发合格任务作为新任务正常计薪，保留原不合格扣款事实。

### 6. 统一现金流水支持日常财务与整笔报销

`financial_entries` 从一开始就是现金事实的唯一表，通过来源和业务类型区分订单资金、工资、手工收入、手工支出和报销付款。财务统计严格按实际收付款日期；收入不区分公账/私人账户。支出可为公账支出或私人垫付；私人垫付只能选择已建垫付人，原支出日计入经营支出，后续只能一次性整笔报销。报销付款是现金事实，但不二次计入经营支出。

动态类目与垫付人支持新建、重命名、停用；已引用记录不删除。日常支出不得关联订单；售后核算成本记录在售后单并进入订单核算成本，不自动新增经营支出。

### 7. 分层、契约与页面拆分

目标目录边界：

```text
src/main/
├── database/v2-storage.ts, v2-connection.ts, v2-migrations.ts
├── domain/order-amounts.ts, order-funds.ts, fulfillment.ts, settlement.ts, finance.ts
├── repositories/order-repository.ts, fulfillment-repository.ts, settlement-repository.ts, finance-repository.ts
├── services/order-service.ts, fulfillment-service.ts, settlement-service.ts, finance-service.ts
└── ipc/order-ipc.ts, fulfillment-ipc.ts, settlement-ipc.ts, finance-ipc.ts, register-v2-ipc.ts

src/shared/contracts/
├── common.ts, customers.ts, products.ts, orders.ts, fulfillment.ts, settlements.ts, finance.ts, reports.ts, index.ts

src/renderer/
├── pages/app.tsx
├── pages/orders/, fulfillment/, work-assignments/, settlements/, finance/, customers/, products/, reports/, settings/
├── composables/use-orders.ts, use-fulfillment.ts, use-work-assignments.ts, use-settlements.ts, use-finance.ts
└── components/order-detail/, fulfillment/, settlement/, finance/
```

页面仅处理布局和 UI 事件；composable 处理加载、草稿、提交、派生展示和错误；组件只接收 view model 与回调，不能直接调用 IPC。domain 不访问 SQLite，repository 不含 React/IPC，service 处理输入校验和跨领域编排，IPC 只映射稳定通道，preload 只暴露共享契约。

### 8. 单提案内的阶段门槛

阶段 A 完成前不得创建生产、工资或日常财务事实；阶段 B 完成前不得创建工资结算；阶段 C 完成前不暴露工资自动记账；阶段 D 完成前不以手工财务页面替代订单资金；阶段 E 完成前不删除 V1 实现或测试。每阶段通过其定向测试及任务记录后才继续，整体完成后执行全量测试、构建与严格 OpenSpec 校验。

## Risks / Trade-offs

- [重构范围大、旧新逻辑混用] → V2 使用独立数据空间、独立 API 组合根和领域目录；V1 删除只在阶段 E 处理。
- [阶段 A 尚无履约数量而先有分批发货] → 阶段 A 只按订单确认数量设上限，阶段 B 上线时立即增加待发货可用量上限。
- [负责人灵活决定导致数据不可分析] → 对售后、最终工资、负责人调整等例外强制要求来源、日期、金额/数量和备注，保留审计。
- [实际现金与订单成本重复统计] → 统一现金流水仅统计实际收付款；日常支出不关联订单；售后核算成本不自动产生现金支出。
- [扣款/返工重复计薪或重复记账] → 扣款分配、结算确认、工资流水、冲正关系均加唯一约束并以事务提交。
- [私人垫付报销重复计入经营支出] → 原垫付为经营支出，报销付款仅记录现金归还，不计入经营结果。
- [用户误以为 V1 数据丢失] → V2 启动和备份页面明确标识 V2 数据空间，V1 文件不删除且不自动迁移。

## Migration Plan

1. 阶段 A 创建 V2 数据空间和订单基础事实，应用组合根切换到 V2 API；V1 数据保留但 V2 不展示。
2. 阶段 B 在同一 V2 数据库追加履约表、工序页面和发货可用量强约束；不改变阶段 A 已保存订单资金事实。
3. 阶段 C 追加结算、扣款和工资流水关联，复用阶段 B 质检结果和阶段 A 统一资金表。
4. 阶段 D 扩展统一资金表来源、类目、垫付和报销，提供月度财务与售后页面；不复制订单收退款。
5. 阶段 E 将所有报表/导出切换至 V2 事实，确认全量回归后删除或隔离 V1 页面、IPC、类型和测试。
6. 任一阶段需要回滚时，保留 V2 数据文件和备份，回退到前一应用构建；不得通过删除 V2 表或覆盖 V1 文件回滚。
