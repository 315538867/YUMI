## Context

当前数据模型已经有 `customers` 表、订单 `customer_id` 外键列和 `customer_snapshot_json` 快照列，但订单创建与更新接受带可选 `id` 的通用客户输入：缺少 `id` 时，仓储层会直接插入客户主档。客户查询目前只服务于订单下拉和客户订单历史，桌面端没有独立客户管理页面。

本变更跨越共享 contract、SQLite 仓储、服务校验、IPC/preload 与 React 页面。数据库中已有历史订单，且 `orders.customer_id` 的既有结构允许空值；不能通过破坏性表重建影响本地现有数据。业务需求以 `proposal.md` 和本变更 specs 为准。

## Goals / Non-Goals

**Goals:**

- 将客户主档、订单客户快照和客户聚合视图分成职责明确的模型与读写路径。
- 从服务边界起强制所有新建或编辑订单关联已存在客户，并在界面提供同样的前置提示。
- 让客户汇总从关联订单及其当前资金状态实时推导，避免冗余余额数据失效。
- 保持旧订单数据和快照可读取，无需为本次功能迁移或重写历史记录。

**Non-Goals:**

- 不将 `orders.customer_id` 改为数据库级 `NOT NULL`，也不为此重建 SQLite 表。
- 不提供订单页手填临时客户、订单页快捷新建客户、客户合并、标签或 CRM 跟进功能。
- 不在客户主档编辑时回填任何历史订单快照。
- 不为此变更改变付款、退款、发货或订单状态本身的业务规则。

## Decisions

### 1. 将客户主档输入与订单客户快照输入拆分

共享 contract 保留客户主档的 `CustomerProfile` / `CustomerInput` 语义，并新增面向订单的客户关联与快照输入模型：客户标识为必填，名称、联系方式和收货地址表示本次订单快照，备注只属于客户主档。订单详情继续暴露已保存快照，避免订单页面根据当前客户主档重新渲染历史信息。

**理由：** 通用且 `id` 可选的客户输入是自动建档的根源。显式拆分使编译期与服务层校验都能表达“订单必须关联已有客户、订单字段只改快照”。

**备选方案：** 继续复用可选 `id` 的 `CustomerInput`，只在运行时约定不得为空。该方案容易再次被仓储调用绕过，且无法表达备注不是订单数据，故不采用。

### 2. 在服务边界强制现有客户关联，仓储只读取目标客户并写订单快照

订单创建和更新的输入校验必须拒绝缺失客户标识或不存在的客户。仓储在写入订单前读取该标识对应的客户；它不得再执行“无标识则插入客户”的分支。选择客户后，订单快照以提交的订单级名称、联系方式和地址为准；未被订单覆盖的显示值在界面加载客户资料时预填。客户主档仅通过客户管理的新增、更新接口写入。

**理由：** 服务层提供可测试的统一业务边界，仓储移除隐式写入后可防止其它调用路径意外自动建档。订单快照独立持久化能保证客户主档变更不改写历史。

**备选方案：** 只在前端禁用空选项。IPC 或未来调用方仍可提交空客户，无法满足订单保存约束，故不采用。

### 3. 新增独立客户管理读写接口，保留既有订单选择列表接口兼容性

新增客户管理所需的列表、详情、创建、更新和删除接口及对应 preload 方法；现有轻量 `customers.list()` 仍可作为订单客户下拉的数据源，避免把汇总字段、查询条件和详情责任混入既有调用。管理列表支持按名称、联系方式、默认收货地址筛选，并返回展示所需的汇总字段；详情返回客户主档、汇总和关联订单历史。

**理由：** 客户管理与订单编辑的数据量、展示字段和交互不同。分离读模型可以使订单选择保持轻量，并让管理页有稳定的详情聚合契约。

**备选方案：** 扩展 `customers.list()` 以同时承载管理页、下拉与详情。这样会让每个订单编辑器加载不需要的聚合数据，且难以区分检索和详情语义，故不采用。

### 4. 客户汇总从订单关联与当前资金状态实时计算

客户详情和管理列表的订单数量、待发货数量、当前未结清金额均基于 `orders.customer_id` 关联订单计算；未结清金额复用订单当前收款与退款结果，不能保存在客户记录中。待发货的判断使用现有订单发货/流程状态定义，并在实现前复用系统现有状态常量或查询语义。

**理由：** 付款或退款发生后，持久化在客户表内的总额会产生同步风险。按关联订单计算可自然反映当前值，且严格限定只统计当前客户关联订单。

**备选方案：** 在客户表保存并在订单、付款、退款每次变化时递增维护。写路径较多且容易遗漏退款、订单改绑客户等场景，故不采用。

### 5. 不改表结构，以业务校验覆盖新增与编辑订单；删除使用关联检查加事务保护

本次不迁移 `orders.customer_id` 的可空列。历史记录维持原样；新订单和后续订单编辑通过服务输入校验保证必须有关联客户。删除客户时先检查订单关联，再在同一事务内执行删除并将外键/并发失败统一映射为明确的“存在关联订单，不能删除”领域错误。

**理由：** 将可空列改为非空需要 SQLite 表重建及历史数据处置，风险超过当前需求。应用层约束能在不迁移的情况下满足新增业务行为；事务检查确保删除结果不会因检查与删除之间的状态变化而误导用户。

**备选方案：** 立即迁移为 `NOT NULL`。虽然约束更强，但需要为历史空关联订单确定归属或补造客户，改变历史数据，不采用。

### 6. 客户管理页面独立为页面组件，订单编辑器只保留选择与快照编辑

桌面端导航新增客户管理入口。客户管理的列表、表单与详情放入独立页面组件，并通过顶层应用完成导航切换；订单编辑器删除“新建客户/临时客户”路径，保留已有客户选择、资料预填和订单快照输入。保存前后均显示清晰的客户关联错误，保存成功后刷新相关页面数据。

**理由：** 顶层应用页面已包含多个业务模块，客户管理的列表与详情状态不应继续堆积在订单编辑器中。将订单编辑器收敛为关联客户和维护本单快照，更符合职责边界。

**备选方案：** 在订单弹窗内增加客户管理子界面。该方式会保留“订单是客户主档入口”的心智模型，并使独立维护和详情汇总难以发现，故不采用。

## Risks / Trade-offs

- [历史数据可能存在空 `customer_id`] → 客户详情查询以明确关联为准；订单读取继续兼容既有快照。新建和编辑订单从服务层拒绝空关联，不批量改写历史记录。
- [待发货状态的既有枚举或计算分散] → 实现前从现有订单列表/详情的状态逻辑提取同一判定，并用状态覆盖测试锁定口径。
- [客户删除与订单写入并发] → 在仓储事务中执行关联检查和删除，并把数据库外键失败转换成稳定的业务错误。
- [客户端页面与现有大型应用文件存在耦合] → 客户管理实现为独立组件，顶层仅连接导航和刷新回调；改动前先处理与并行中的 `app.tsx` 修改的合并边界。
- [实时聚合增加查询成本] → 本地桌面应用的数据规模可接受；先使用按客户关联的聚合查询，只有测得性能问题时再优化索引或读取策略。

## Migration Plan

1. 先发布共享 contract、服务校验和仓储行为，使新建及编辑订单均要求存在客户，且不再自动插入客户主档。
2. 同一版本发布 IPC/preload、客户管理页面和订单编辑器，避免桌面端出现无法维护客户却已强制选择客户的中间状态。
3. 不执行数据迁移：已有客户、订单 `customer_id` 与 `customer_snapshot_json` 原样保留；历史订单仍按已保存快照展示。
4. 升级后以自动化测试和手工回归验证客户 CRUD、删除保护、订单保存校验、快照隔离及付款/退款后的聚合刷新。
5. 如需回滚，回滚应用代码即可；本变更不新增或重建数据库表。新增的客户主档与既有表结构兼容，回滚版本仍可读取它们。
