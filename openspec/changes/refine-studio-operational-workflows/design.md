- 提案名称：工作室运营流程优化
- Change ID：`refine-studio-operational-workflows`
- 方案版本：v1.3
- 状态：提案设计
- 创建人：Codex
- 创建时间：2026-09-05
- 最后修改时间：2026-09-05

## Context

见 [proposal.md](proposal.md) 和各能力 delta spec。当前应用已使用 SQLite、共享 TypeScript 契约、Electron IPC 和 React 单页界面；已有 `xlsx` 依赖及报表导出流程。商品和订单商品具备成本快照，排班任务保存预计分钟数及部分实际字段，但排班仍以起止时段为中心，且没有包含不合格产出的完整实际完成质量数据。订单已有客户地址快照但界面仍使用“常用地址”表述，订单与发货表也依赖手工整理，且缺少按次发货记录及已发/待发汇总。

## Goals / Non-Goals

**Goals:**

- 使商品、订单、报表和排班的新增字段在数据库、快照、IPC、服务和界面之间一致流转。
- 通过现有 XLSX 基础设施按订单生成稳定、可打印的订单表和发货清单模板。
- 将本月重量建立在实际完成数量和订单商品重量快照的历史事实上。
- 用排班级预留时长表达弹性，并以原子完成提交保存合格、不合格和实际完成总数；实际完成总数由合格数量与不合格数量自动汇总。

**Non-Goals:**

- 不实现库存扣减、物流跟踪或复杂的订单发货状态流转；本期只记录每次发货数量，并由系统计算订单维度的已发数量和待发数量。
- 不实现工资、提成、不合格扣费、扣费标准或结算周期；二期另起提案。
- 不把额外预留时长按任务分摊或将其视为实际工时。
- 不改写既有历史排班的产出、成本、审计日志，或将未登记实际完成数量的历史记录伪造为 0。

## Decisions

### 1. 商品费用采用单件成本字段并随订单快照固化

在商品表增加 `accessory_cost_cents` 和 `replacement_bag_cost_cents` 两个非负整数字段，在订单商品表增加同名快照字段。成本预览与创建订单使用每件费用乘以订单数量计入预计直接成本；旧商品和旧订单的新增字段以 0 初始化。

- 选择原因：用户明确要求在录入商品页维护费用，按单件成本与既有包装成本、提成模型一致，订单快照可防止历史金额随商品编辑漂移。
- 未选择“仅写在订单备注中”：不能纳入成本预览、导出和订单历史。
- 未选择“做成独立可配置配件明细”：会引入配件库存、数量和价格规则，超出本期范围。

### 2. 商品新建采用单页表单，保留同一校验入口

`ProductDialog` 组织为连续分区表单，包含基础资料、制作参数和全部费用；保存仍使用同一份商品创建输入和服务校验，不增加草稿或多步状态机。

- 选择原因：满足“一步完成”，同时避免多套字段校验和中间状态。
- 未选择“分步向导”：与反馈相反，且对当前字段量不必要。

### 3. 收货地址仍是订单快照，一键复制只影响当前草稿

客户资料中的持久化地址继续作为客户默认收货地址来源。订单表单统一显示“收货地址”；在已选客户且地址非空时提供“复制客户收货地址”按钮，写入当前订单草稿的地址快照。保存订单时按既有快照规则持久化，后续修改草稿或订单不反写客户资料。

- 选择原因：可快捷复用地址，又不会意外污染客户档案或历史订单。
- 未选择“订单地址始终跟随客户”：会破坏收货地址的订单时点语义。

### 4. 每笔订单导出一个含两张工作表的 XLSX 工作簿

复用既有 `xlsx` 依赖与文件保存桥接，新增按订单 ID 的文档生成服务和 IPC，并以订单发货记录表与发货明细表保存每次发货。工作簿包含“订单表”和“发货清单表”：两者均使用订单和订单商品快照；图片存在时嵌入或以受控缩略图呈现；订单表汇总数量和金额；发货清单列出订购数量、本次发货数量、累计已发数量和待发数量。每次发货先由用户在系统中录入并保存本次发货数量，导出时通过 `shipmentId` 带出对应发货数据；未指定 `shipmentId` 时，本次发货列为空，累计已发和待发仍按历史记录计算。导出本身不新增发货记录或修改订单状态。

发货数据采用 `shipments`（订单级发货批次）和 `shipment_items`（批次内订单商品数量）两张表：每个批次关联一个订单，每个订单商品在同一批次最多一条明细。保存批次时在事务内校验数量非负且不超过保存前待发数量；已发数量按明细求和，待发数量按订购数量减累计已发数量计算。已保存批次允许修改，修改时先排除原批次数量再校验新数量；发货记录不提供硬删除，以保留审计依据。订单商品数量不得被修改为低于累计已发数量，也不得删除已有发货明细的订单商品。

- 选择原因：同时满足两种参考表格，保持单个可打印文件的交付方式，并避免未经确认的发货业务模型。
- 未选择“只在导出的 Excel 中手工维护发货数量”：无法累计多次发货，也无法可靠计算订单的已发和待发数量。
- 未选择“PDF 作为唯一格式”：当前已有 XLSX 依赖，表格可继续编辑、打印和补填，且无需新增渲染依赖。

### 5. 月度总重量按实际完成数量与订单商品重量快照汇总

报告服务按自然月筛选已完成排班任务，使用 `completed_quantity × order_item.weight_grams` 聚合克数，再换算为千克。质量不影响制作总重量：合格和不合格品均为实际产出，且 `completed_quantity` 必须等于合格数量与不合格数量之和；没有完整实际完成质量数据的历史任务不计入，避免虚构重量。

- 选择原因：实际完成数量比计划数量更能反映已产出，订单商品快照保证商品重量变更不会改写历史月报。
- 未选择“按合格数量统计”：会低估实际制作和材料消耗，且可在二期另加合格产出重量指标。

### 6. 排班时长采用任务基础合计加排班级预留，并移除固定时段

`shifts` 保存 `extra_minutes`，任务 `estimated_minutes` 继续表达基础任务时长；每项基础任务时长按 `计划制作数量 × 标准制作时长` 计算，并向上取整到分钟，排班基础总时长为各任务基础时长之和，最终总时长为基础总时长加全局额外预留时长。新建和编辑界面不再展示或要求 `start_time`、`end_time`，但数据库迁移保留这两个历史字段并改为可空，仅用于兼容旧数据，不参与新流程计算。固定时段风险删除，模具日产能和交期风险保留。

- 选择原因：不使用无意义的时间占位值，时长模型与用户的弹性排班方式一致。
- 未选择“隐藏时间控件但保留时间校验”：仍会产生错误的重叠和时段容量风险。

### 7. 完成状态与质量数量原子保存，并与工资计算解耦

在 `shift_tasks` 新增可空 `completed_quantity` 和 `unqualified_quantity`。目标状态为 `completed` 时，状态更新请求必须为每个任务提供合格数量和不合格数量；服务验证字段完整、均为非负整数，并将实际完成数量自动汇总为 `qualified_quantity + unqualified_quantity`。仓储在同一事务写入实际完成、合格、不合格三项数量和排班状态，详情不再通过减法推导不合格数量，而是读取已保存的不合格数量。现有 `rework_quantity`、`scrap_quantity`、实际分钟、人工成本和提成字段保留用于历史数据兼容；新完成登记以独立的 `unqualified_quantity` 作为不合格总数，不再要求用户拆分返工/报废，也不把旧字段与新字段重复相加。本期不由新增质量数据触发工资、提成或扣费金额运算。

- 选择原因：杜绝“已完成但缺质量数据”的部分状态，并为二期工资结算保存独立、可审计的原始数量。
- 未选择“只保存实际完成和合格数量再推导不合格数”：不合格数量是后续质量追溯和二期工资结算的明确业务数据，必须显式录入并持久化，不能只依赖派生结果。

## Risks / Trade-offs

- [新增商品费用遗漏订单快照或成本公式] → 以端到端创建订单测试覆盖默认值、编辑商品后的历史订单不变和成本预览汇总。
- [XLSX 中图片不可用或版式不一致] → 图片缺失时保留文本商品信息并使用固定表头与列宽；导出测试校验工作表名、字段和汇总值。
- [月度重量误计历史任务] → 仅统计有完整实际完成质量数据的已完成任务，并明确将历史未登记记录排除。
- [SQLite 表重建遗漏列/索引] → 显式复制保留列，恢复索引，并在数据库迁移测试中覆盖既有版本升级。
- [完成状态与任务数量写入不同步] → 使用单事务更新并测试任一输入无效时不写入任何记录。
- [订单编辑后待发数量出现负数] → 修改或删除订单商品前校验累计已发数量，禁止将订购数量降到已发数量以下。
- [重复提交同一发货批次] → 发货批次和明细使用明确 ID、唯一约束及事务提交，界面保存成功后刷新累计汇总。
- [旧生产记录接口与新质量字段重复计算] → 将完成登记统一到一个服务入口，旧返工/报废字段仅兼容读取或显式映射，不重复计入实际完成数量。
- [旧工资报表仍引用既有成本字段] → 不改写其历史规则；回归测试确保本期未添加任何不合格扣费公式。

## Migration Plan

1. 新增数据库迁移：为商品、订单商品快照、排班和排班任务添加新字段；新增订单发货记录及发货明细表；重建 `shifts` 表以保留但允许为空的历史时间字段，并增加 `extra_minutes`；旧费用填 0、旧完成数量和不合格数量保持 `NULL`。
2. 先更新共享契约、领域/服务/仓储和 IPC，再更新界面、导出和报表，避免新 UI 调用旧接口形状。
3. 迁移在 SQLite 事务中执行；失败时回滚。已完成迁移后的回退使用应用既有备份/恢复能力；不删除旧排班时间数据，避免历史记录丢失。
4. 通过新库初始化、旧库升级、商品-订单快照、发货批次累计、订单数量约束、导出工作簿、月度重量和排班完成状态的集成测试后发布。

## Open Questions

无。本期每次发货由用户录入本次发货数量并形成发货记录；系统按订单商品汇总累计已发数量，使用“订购数量 - 已发数量”计算待发数量。发货清单导出展示当前发货记录和累计结果，但导出操作本身不新增发货记录、不修改订单状态。二期工资扣费口径也不影响本期质量数据的保存方式。
