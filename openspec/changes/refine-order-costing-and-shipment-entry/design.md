## Context

见 `proposal.md`。现有订单成本快照和 `orders.actual_cost_cents` 仅保存总额；商品成本模型没有捏毛装袋和缝边成本。现有排班允许多个任务，额外预留时间无法唯一归属；发货表单常驻订单详情。

## Goals / Non-Goals

**Goals:**

- 以订单创建时的成本快照稳定计算完整预计/实际成本。
- 将单任务排班的基础时长与额外预留时长完整归属为实际人工。
- 通过成本详情与新增发货弹窗收敛订单详情的操作密度。

**Non-Goals:**

- 不增加真实采购、领料、运费或手动费用台账。
- 不重新计算既有订单的历史成本快照；缺失新增成本字段按 0 兼容。
- 不修改已有历史发货记录或提供删除能力。

## Decisions

1. **售价和成本分离。** 保持现有订单缝边单价作为客户增值服务售价；新增商品缝边成本作为内部成本。订单启用缝边时数量从商品数量派生，创建/更新都由服务端强制归一，避免前端绕过。
2. **预计与实际只在人工来源不同。** 预计人工按订单数量、快照标准分钟和创建订单时默认时薪；实际人工按已完成排班的 `estimated_minutes + extra_minutes` 和该人员当日工资历史。材料、包装、配件、替换袋、捏毛装袋、缝边成本和提成均按订单快照与订单数量计算。
3. **实际成本按订单详情动态汇总并同步总额。** 抽取统一的订单成本明细计算器：订单详情/成本弹窗用其提供可解释的按商品明细；排班完成、订单创建和更新后将汇总写回 `orders.actual_cost_cents`。这样报表复用持久化总额，详情不会与报表口径分叉。
4. **排班任务改为单一。** 前端移除多任务操作；服务层在预览、保存和编辑入口校验任务数为 1。既有多任务排班允许查看，已不能按新的编辑请求保存。
5. **发货仅新增。** 历史记录只读，发货输入草稿仅在新增发货弹窗生命周期内存在；保留已有创建接口与导出接口，移除 UI 编辑入口但不删除底层更新接口以兼容现有本地数据和调用面。
6. **新建兼职人员默认工资。** 读取默认成本设置后预填新建人员时薪；保存后仍创建独立工资历史，系统默认值后续不反写既有人员。

## Risks / Trade-offs

- [旧订单缺少新成本字段] → 数据迁移增加默认 0；历史订单快照缺少字段时读取归零。
- [实际成本在排班未完成前不完整] → 成本详情明确展示“实际人工仅计入已完成排班”；其他成本基于订单数量稳定展示。
- [取消多任务排班影响工作流] → 后端给出明确校验信息，前端仅保留一个商品选择；保留历史多任务记录只读。
- [成本动态明细和报表总额不一致] → 所有写入点复用同一汇总函数，并以服务测试覆盖。

## Migration Plan

1. 迁移商品表新增两项非空成本列，默认 0；已有订单商品快照保持原 JSON，读取时兼容缺失字段。
2. 发布后，新建/更新商品、订单、排班和发货遵循新规则；旧订单可打开成本弹窗，新增成本项目显示为 0。
3. 如需回滚，仅可保留新增列和快照字段而恢复旧界面；SQLite 默认列对旧程序兼容。
