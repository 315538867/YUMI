## Context

关联方案：`docs/solutions/2026-09-14-product-process-payroll-and-formula-center-solution.md`（v1.1）。提案名称为“YUMI 商品、工序、工资与公式中心重构”，Change ID 为 `redesign-product-process-payroll-and-costing`，创建人 Codex，创建日期 2026-09-14，当前处于计划阶段且未授权实施。

当前 Electron 离线桌面应用已经具有商品、订单商品快照、排班、工序任务、履约事件、工资结算和整数金额工具，但业务计算分散在 main 领域函数与 renderer 页面中。现有模型把计划分钟、单任务实际分钟、制作时薪、非制作质量和订单期初在制品耦合在一起；新需求则要求排班与最终工时分离、制作纯计件、计时工序按次日确认时长结算，并允许一段同工序时间处理多个商品。

已归档的 `2026-09-14-yumi-core-capability-recovery` 改动过商品成本、订单快照和订单级缝边收费等同一批落点。本提案实施前必须以当前工作区代码和归档后主规格为基线复核，不回退已经生效的订单级缝边收费、订单金额和查看优先交互。

## Goals / Non-Goals

**Goals:**

- 用单一结构化公式事实统一主进程计算、renderer 预览、公式目录和公式展示。
- 建立商品预计盈利、商品阶段存量、条件缝边、负责人次日工时核算和新工资口径的完整事实链。
- 保持订单级客户缝边价格与商品级缝边预计成本边界清晰。
- 在同一个 OpenSpec 提案内按 A、B、C、D 四阶段实施，每阶段具有独立验证检查点。
- 直接建立目标数据库模型，不增加旧业务数据转换和兼容分支。

**Non-Goals:**

- 不接入 SD 卡或当前非联网打卡机，不实现设备协议。
- 不做仓库、库位、采购、批次、盘点和原材料库存管理。
- 不按商品或订单分摊一段多商品计时工资，不生成商品历史实际利润。
- 不自动认定员工恶意延长时间，不因效率提示自动扣薪。
- 不改变订单收退款、物流单号、分批发货和最终财务支出的既有事实职责。

## Decisions

### 1. 同一个提案内按四阶段交付

`tasks.md` 使用四个一级阶段：A 公式中心、B 商品与预计盈利、C 商品阶段存量与履约、D 工时核算与工资。阶段 B 依赖 A；阶段 C 依赖 B 的字段和快照；阶段 D 依赖 A 的工资公式与 C 的工序结果。

选择单提案是因为字段、履约、工资和公式属于同一业务口径，拆成多个 change 会产生重复临时兼容层。替代方案是四个独立提案，但会使中间状态长期存在“新商品字段配旧工资”或“新工序配旧结算”的不一致，因此不采用。

### 2. 共享公式使用结构化表达式而不是可执行字符串

新增 `src/shared/calculations/`，至少包含公式结果类型、表达式构造与渲染、材料成本、商品预计盈利、工资、订单金额和公式目录。表达式节点只允许受控的常量、变量、加减乘除、求和和比例节点；计算结果包含标识、名称、单位、最终值、公式文本、代入文本及组成明细。

`src/shared/money/index.ts` 继续负责整数分、毫克、微元/克和分钟时薪等精度运算；公式中心负责组合业务规则，不复制金额解析和舍入基础能力。禁止 `eval`、函数构造器或脚本解释字符串。

替代方案是只集中后端函数、前端继续手写公式说明，但仍会发生说明漂移；另一替代方案是数据库保存公式字符串，会引入执行安全和版本控制问题，均不采用。

### 3. renderer 预览与 main 权威计算使用同一纯函数

商品和订单编辑草稿可直接调用 shared 纯函数实时预览。保存请求只提交售价、重量、成本、提成、预计时长等原始字段；main service 使用相同计算器重新校验。派生成本、利润和工资即使由 renderer 附带也不作为可信输入。

这既满足桌面应用即时反馈，也保持 IPC 边界的可信性。无需通过额外 IPC 为每次键盘输入请求主进程计算。

### 4. 金额公式组件直接展示结果和公式

新增 `YumiCalculatedAmount`。组件接收结构化 `CalculationResult`，默认直接显示业务名称、金额、公式主干和代入结果，并可展开组成明细。预计利润率使用同一结果基类的比例展示；售价为零时以不可计算状态展示。

组件不接收页面拼接的公式字符串。金额使用等宽数字与统一人民币格式，正负结果除了颜色外必须有文字或符号语义，公式不得只存在于 hover 内容。

### 5. 商品目标字段直接替换旧成本字段

新商品模型保留基础资料、默认售价、单件材料重量、包装/配饰/替换袋/缝边耗材/固定成本、制作/捏毛装袋/缝边提成、四道工序预计单件分钟及产能参数。单件材料重量同时表示使用量和成品材料重量。

单件制作胶水用量、材料损耗率、人工材料成本和人工胶水成本不进入新契约、新表单或新公式。设置增加捏毛装袋、缝边、打包发货三道工序预计基准时薪；实际工资继续读取员工个人时薪。

数据库金额保存整数分，重量保存毫克，分钟保存非负整数，克单价继续使用现有高精度整数单位。

### 6. 商品预计盈利只计算当前预计值

基础商品预计单件成本为：

```text
全局材料克单价 × 单件材料重量
+ 包装成本 + 配饰成本 + 替换袋成本 + 单件固定成本
+ 制作提成 + 捏毛装袋提成
+ 预计捏毛装袋计时工资 + 预计打包发货计时工资
```

预计计时工资使用“预计单件分钟 ÷ 60 × 对应预计基准时薪”。制作预计分钟只服务排产与产能参考，不进入制作工资或预计计时人工。

预计单件利润为默认售价减基础预计成本；预计利润率为预计利润除默认售价。缝边预计增加成本单独计算“缝边耗材 + 缝边提成 + 预计缝边计时工资”。客户缝边收入属于订单商品事实，只有订单已有缝边单价和数量时才计算订单缝边预计增量利润。

### 7. 商品使用全页工作区

商品列表继续作为入口，创建、查看和编辑通过主内容区路由状态承载，不再使用 `YumiSheet` 保存完整表单。详情提供商品概览、成本与预计盈利、制作产能、商品存量四个标签；右侧或稳定区域保留实时预计盈利预览。

短确认动作（停用、单次存量调整）仍可使用对话框。布局复用现有 `YumiPageHeader`、`YumiMetricStrip`、`YumiPrimaryTabs`、`YumiSection` 和表格组件，避免新建卡片墙视觉体系。

### 8. 商品阶段存量采用事件流水

新增 `product_stage_inventory_events`，字段至少包含商品、阶段、数量增减、来源类型、可选订单商品关联、发生日期、备注和创建时间。阶段按物理加工状态定义为：已制作待捏毛装袋、已捏毛装袋未缝边、已缝边待打包发货、已打包待发货。尚未绑定订单的已捏毛装袋商品不提前假设是否需要缝边。

期初重录、负责人调整和投入订单全部写流水，不允许无流水覆盖余额。投入订单由领域服务在单一 SQLite 事务中写商品负向事件和订单履约正向事件，并校验商品一致、阶段余额、订单剩余需求和缝边需求。已捏毛装袋未缝边存量按目标订单是否仍需缝边分别进入待缝边或待打包发货；已缝边存量只可满足仍有缝边需求的订单并直接进入待打包发货。

不扩展为完整库存系统，因为当前只需要工序阶段数量和投入订单事实。

### 9. 履约固定为条件缝边的四道岗位工序

目标工序类型为：

```text
making
fluffing_bagging
edge_sewing
packing
```

renderer 将 `packing` 统一显示为“打包发货”。订单发货批次仍负责物流与已发货事实，不再把 `shipping` 作为兼职岗位任务。

捏毛装袋完成时按订单 `edgeQuantity` 剩余需求分流：需要缝边的部分进入待缝边，其余进入待打包发货；缝边完成进入待打包发货；打包发货完成进入已打包待发货；发货批次再进入已发货。

只有制作具有合格与不合格质量结果。其他三道工序只登记完成数量。

### 10. 排班与实际结果、工时分离

工作安排保存员工、日期、单一工序、任务列表、可选参考计划数量和备注。预计分钟可以由商品预计时长计算并用于风险提示，但不保存为实际工资来源，也不要求开始/结束时间。

制作由独立结果确认录入完成、合格、不合格。计时工序由 `work_time_reviews` 在次日核算，记录员工、日期、单一工序、核算分钟、个人时薪快照、来源、状态和备注，关联一个或多个员工、日期和工序一致的工作安排，并关联这些工作安排中的多个商品完成明细。同一工作安排最多只能进入一条未作废核算记录。

`process_results.actual_minutes` 不作为新模型权威工时；一段核算分钟不会拆分或重复写入各商品结果。

### 11. 工时核算保留风险证据和设备接入口

核算页面按完成明细计算：

```text
预计总分钟 = Σ(商品完成数量 × 商品该工序预计单件分钟)
时间差 = 核算分钟 − 预计总分钟
预计效率 = 预计总分钟 ÷ 核算分钟
```

效率只作为负责人复核信息。来源字段支持 `manual_review` 和未来 `attendance_device`，并预留外部记录标识、原始开始和结束时间；当前 UI 固定创建 `manual_review`。无论来源如何，只有负责人确认后的 `approved_minutes` 才能进入工资。

### 12. 工资只聚合可追溯的新事实

制作工资：

```text
Σ(合格数量 × 冻结制作提成)
- Σ(不合格数量 × 冻结单件材料重量 × 冻结材料克单价)
```

捏毛装袋和缝边工资为已确认核算分钟对应的个人时薪，加关联商品完成数量对应的冻结提成；打包发货只有已确认核算分钟对应的个人时薪。

工时确认时在同一事务中冻结工作日期生效的员工时薪并提交完成结果，重复确认必须幂等。已确认工时不得直接修改；只有在完成结果未被下游消耗且工时未进入已确认结算时，才可原子作废工资来源与完成结果后重录。一条工时最多进入一个有效结算；已进入确认结算后的工资差异通过后续结算中关联原工时与原结算的正负调整处理，不得静默作废来源。现有扣款抵扣、顺延、最终实发人工确认和财务流水事务继续保留，但来源聚合不再使用周期级 `attendanceMinutes` 或排班参考分钟。

### 13. 不分摊多商品计时工资为历史实际成本

同一工序时段可处理多个商品，而工资无需拆分到商品。订单成本详情只显示订单商品快照可计算的预计成本和明确可归属金额，不按数量、预计分钟或任意比例把实际计时工资伪装成订单/商品历史实际成本。

如果未来需要实际利润，必须另行确定工时分摊规则并建立新提案；本提案不预留隐藏分摊算法。

### 14. 数据库直接重建目标结构

本提案不做历史业务数据迁移。实施时修改最新初始化结构或增加破坏性重建步骤，使目标数据库只包含新字段、工序和关系；不复制旧商品、订单快照、排班、履约、期初在制品、工资或结算数据，不保留旧公式、旧 `shipping` 或旧实际分钟兼容分支。

业务发生后的新订单商品快照和工时/工资快照仍必须保留，这是新模型内部的费率冻结，不属于历史迁移。

## Risks / Trade-offs

- [与已归档提案修改同一商品文件] → apply 前重新读取当前主规格和代码，以 `2026-09-14-yumi-core-capability-recovery` 的已生效结果为基线，不回退订单级缝边价格与订单金额行为。
- [单提案改动范围较大] → 严格按 A、B、C、D 阶段推进；前一阶段测试、类型检查和 OpenSpec 状态未通过时不进入后一阶段。
- [共享公式重构影响多个页面] → 先用特征测试锁定现有仍需保留的订单金额与金额精度，再逐个替换调用方，禁止 renderer 保留并行公式。
- [SQLite 重建会清空旧业务数据] → 部署前明确备份和重置步骤；备份仅用于保留原始文件，不执行导入新库。
- [预计时长与实际工作差异较大] → 始终标记“预计”，只做人工核对，不自动扣薪或阻止确认。
- [商品阶段存量与订单履约双边不一致] → 只允许通过单一领域服务事务投入订单，不暴露分别修改两边余额的接口。
- [已确认工时被重复结算] → 结算来源建立唯一引用约束或等价的事务校验，作废和更正保留审计事实。
- [已确认工时更正破坏下游数量或工资] → 仅允许在完成结果未被下游消耗且未进入确认结算时原子作废；其他情况必须先处理下游履约或结算调整。

## Migration Plan

这里的“迁移”仅指部署到新目标模型，不包含旧业务数据转换：

1. 在实施开始前备份当前本地数据库文件，并确认备份可读取。
2. 完成阶段 A 至 D 的代码和测试后，停止使用旧业务库。
3. 删除或重建目标业务数据库，按最新 schema 创建空库和必要默认设置。
4. 负责人在新商品全页工作区重新建立商品资料，并在商品存量标签录入现场实际阶段数量。
5. 新订单、排班、履约、工时和工资从新模型开始记录，不导入旧记录。
6. 若发布验证失败，回滚应用版本并恢复原数据库文件；不得让新旧模型共用同一业务库。
