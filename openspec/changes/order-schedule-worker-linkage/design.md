- 状态：拟实施
- 创建人：Codex

## Context

现有 SQLite 模型已经通过 `order_items.id -> shift_tasks.order_item_id` 和 `workers.id -> shifts.worker_id` 建立了生产关联。`src/main/services/studio-service.ts` 负责写入校验和业务编排，`src/main/repositories/studio-repository.ts` 负责订单、班次和人员读取；`src/shared/contracts.ts` 定义 IPC 共享返回值；`src/renderer/pages/app.tsx` 集中承载订单、排班和人员界面。

现有排班保存已经使用 `ShiftPreviewResult.risks` 和 `confirmedWarningCodes` 实现风险确认；现有完成登记已保存合格/不合格数量。实现应复用这些入口，避免新增第二套写入协议。详见提案和变更规格中的用户可观察行为。

## Goals / Non-Goals

**Goals:**

- 抽取唯一的订单商品生产进度聚合规则，供订单列表、订单详情、排班预览和人员详情复用。
- 通过服务端聚合返回最新进度，避免在渲染层分别计算造成口径分叉。
- 兼容既有 `productionStatus`、收款、发货和人员结算逻辑。
- 让超排风险进入现有风险确认链路，并为所有新进度行为建立测试证据。

**Non-Goals:**

- 不新增数据库表、缓存进度字段或后台同步任务。
- 不重构现有单文件页面为全新页面架构。
- 不改变订单金额、发货数量、提成和工资计算。
- 不做自动排班、批量分配或库存扣减。

## Decisions

### 决策 1：实时聚合而不是持久化进度字段

新增服务层纯聚合逻辑，读取 `orders/order_items/shifts/shift_tasks/workers` 的现有事实数据，按订单商品计算进度，再组装订单级和人员级读模型。

- **理由**：当前是单机 SQLite，排班和完成写入入口数量有限；实时聚合避免遗漏同步入口和历史数据回填。
- **备选方案：在 `order_items` 保存已排/已完成字段。** 不采用，因为每个班次状态、完成登记和排班编辑都必须同步更新，容易产生事实数据与汇总字段不一致。
- **备选方案：新建独立排产表。** 不采用，因为当前需求是补齐可见性和防错，不需要引入另一套排产事实。

### 决策 2：以班次状态区分有效计划与实际结果

有效已排只统计 `scheduled` 班次的计划量；`completed` 班次只用合格完成量抵扣订单需求；`leave`、`absent`、`cancelled` 不占有效已排。对于完成后合格量不足、质量不合格或历史安排释放造成的缺口，聚合结果标记为待补排。

- **理由**：订单交付目标是合格品，计划量不能替代实际合格结果。
- **边界**：超排确认后允许保存，因此已排量可能超过需求；展示层将未排/待补排下限设为 0，同时保留超排风险信息。

### 决策 3：增加排产状态而不是立即重定义既有制作状态

共享契约增加排产进度读模型和排产状态字段；既有 `productionStatus` 继续服务原有筛选、报表和流程。订单页面同时展示两类信息，但把新的排产状态作为联动进度主信息。

- **理由**：降低对现有报表和存量数据的兼容风险，先用只读状态验证业务口径。
- **备选方案：直接替换 `productionStatus`。** 不采用，因为会把本次联动需求扩大为状态机迁移。

### 决策 4：复用风险确认机制

在仓储预览中增加订单超排风险，由服务层统一检查确认码；创建和编辑排班都必须经过同一检查。编辑时排除当前班次，再将本次草稿计划加入计算。

- **理由**：当前模具产能和交期风险已经走同一机制，复用可以保持交互和审计一致。

### 决策 5：服务端返回关联读模型，渲染层只负责绑定

扩展 `OrderSummary`、`OrderItemDetail`、`OrderDetail`、`WorkerDetail` 和 `ShiftPreviewResult` 的返回契约。订单列表使用轻量汇总，订单详情使用商品进度和相关班次，人员详情使用订单任务汇总；跳转只传实体 ID。

- **理由**：避免 `app.tsx` 直接拼接跨实体数据，也避免三个页面各自实现规则。

## Risks / Trade-offs

- [聚合查询增加列表读取成本] → 先使用按订单商品和班次任务的索引与单次聚合查询；在当前单机规模下不引入缓存，若后续有性能证据再优化。
- [历史班次状态或质量字段不完整] → 对空值按 0 处理，保留既有历史记录；只有实际存在的合格数量抵扣需求，测试覆盖迁移前的历史完成记录。
- [超排确认后未排数量显示为 0 可能掩盖超排] → 单独返回并展示超排量/风险徽标，不把超排静默吞掉。
- [订单级多商品状态互相冲突] → 先计算商品级状态，再按“制作完成、待补排、已排满、部分已排、待排产”的优先级汇总，详情始终保留商品级明细。
- [现有 `productionStatus` 与新排产状态含义相近] → 在契约和界面使用明确字段名与中文标签，文档注明两者暂时并存，不在本变更中改变旧状态流转。

## Migration Plan

1. 先新增聚合函数和服务测试，再扩展共享契约，确保旧返回调用方仍可编译。
2. 接入订单列表/详情和人员详情；完成只读展示后再接入排班预览的超排风险。
3. 通过现有演示数据和端到端测试验证请假、缺勤、取消、不合格、超排和多商品订单。
4. 本变更无需 SQLite 迁移；回滚时删除新增读模型、风险码和渲染绑定即可，既有订单、排班、质量记录不需要回滚。
5. 完成后运行 `npm run typecheck`、`npm run lint`、`npm test`、`npm run build` 和 `openspec validate order-schedule-worker-linkage --strict`。
