# Proposal: 重构负责人任务式经营工作流

## Why

当前 V2 页面已经具备订单、履约、工资、财务、客户、商品及售后等业务能力，但页面沿用“标题 + 分区 + 列表 + 空状态”的信息陈列方式。负责人进入页面后需要先理解系统如何分区，再自行判断现在应做什么；同一页面堆叠多个标题、多个空列表和重复操作入口，首用、日常处理、跨订单履约以及结算复核的路径都不连续。

捏捏工作室的实际工作不是按模块浏览资料，而是持续处理待决定事项：安排生产、登记工序结果、检查不合格、组织分批发货、处理售后、确认工资和报销。订单还存在多商品、多数量、分批生产与分批发货并行的情形，不能用一个“推进下一步”覆盖全部状态。系统需要以负责人决策和任务流为中心，同时保留负责人对售后责任、收费、排班和实发工资的最终裁量。

## What Changes

- 新增默认入口“工作台”，把需要负责人决定和可以直接推进的跨模块事项汇集为一个可进入实际处理区的任务列表；工作台不成为手工待办或 KPI 仪表盘。
- 将订单从单线流程页改为商业记录工作区，并将订单履约拆为可跨订单查看的工序/履约队列；订单详情通过概览、履约、资金、售后四个互斥视图处理同一订单。
- 明确生产批次/工序任务与发货批次的对象边界：生产任务按商品数量流转，发货记录按实际寄出的组合保存；订单层不得用单一“下一步”替代并行批次的真实状态。
- 将工资结算改为负责人选择周期、比较排班与考勤两套参考工资、最终人工确认实发的闭环；确认即视为实际发放并写入工资支出。
- 将财务改为“月度经营结果 / 现金流水 / 待报销”互斥工作视图；支持同次批量报销多笔私人垫付，且原垫付经营支出与报销现金流不得重复计入经营支出。
- 将客户、商品和设置统一为资料库型交互；支持在新建订单上下文中快捷新建客户/商品并回填，避免丢失草稿和跳页。
- 建立全局交互约束：一个页面仅有一个主标题、一层主要视图切换、一个实体级主操作和一个主要记录列表；按首用、前置资料缺失、筛选无结果分别展示不同空状态。

## Capabilities

### New Capabilities

- `responsible-workbench`: 负责人默认工作台、决策队列、可推进队列与跨模块深链。
- `payroll-confirmation-workflow`: 周期工资参考、负责人确认实发、质量扣款顺延或待退款及工资支出联动。
- `cashflow-reimbursement-workflow`: 月度经营/现金流/待报销工作视图、按付款日统计与私人垫付批量报销。

### Modified Capabilities

- `operational-ui-flow`: 用任务式页面模型、导航、唯一主操作和分型空状态取代当前分区堆叠式运营页面。
- `detail-workspaces`: 订单等对象详情支持互斥业务子视图、工作台深链定位及返回上下文保留。
- `order-and-payment-management`: 订单作为商业记录，订单履约、资金和售后分区处理；订单完成状态基于全部商品/批次履约与发货事实，不提供误导性的统一下一步。
- `production-scheduling`: 排班、工序结果、质检、不合格扣款和返工继续以任务/批次为单位流转；已接入的在制品可从当前阶段建档，不回填历史工资。
- `shipment-entry-dialog`: 新增发货从实际可发数量构建发货批次，允许同一订单多个商品与多批次持续分批发货，并保持历史发货只读。

## Impact

- **Renderer**：新增工作台页面与任务卡片读模型；调整 `src/renderer/pages/app.tsx` 导航与页面间上下文；重构订单、履约、工资、财务、客户、商品和设置的页面结构与状态恢复策略。
- **Shared contracts / preload / IPC**：新增工作台待处理事项查询契约；新增私人垫付批量报销输入与结果；补充对象工作区深链所需的查询/定位参数。
- **Main process**：增加工作台聚合读模型服务；将多个私人垫付的报销创建封装为单一原子事务；必要时补充订单、履约、售后和结算的轻量查询投影。
- **Database**：优先从既有 V2 订单、履约、质检、售后、结算、财务事实派生工作台，不新增手工待办表。若批量报销仅复用现有 `advance_reimbursements` 关联表，则无需为该能力新增业务表；需要的约束通过事务、唯一关联和查询校验保障。
- **Tests**：补充领域服务、IPC、页面流程和跨模块深链测试；保留负责人裁量，不引入自动判断责任、收费、排班或实发工资的逻辑。
