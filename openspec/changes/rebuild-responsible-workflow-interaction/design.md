## Context

当前桌面端通过 `src/renderer/pages/app.tsx` 的本地 `View` 状态在订单、履约、工资、财务、报表、客户、商品和设置之间切换，默认入口是订单。各页面已经由 V2 领域服务提供订单、工序任务、质检、售后、工资结算和财务事实，但页面之间没有统一的跳转上下文；财务报销契约目前仅支持单笔 `advanceFinancialEntryId`。

现有领域模型已包含 `V2ProcessTask`、工序结果、质检、在制品接入、工资结算、财务流水和售后记录。因此本次以既有业务事实派生任务与视图，而不是引入第二套流程状态或手工待办。方案动机及用户可见行为以 `proposal.md` 和本变更的能力规格为准。

## Goals / Non-Goals

**Goals:**

- 建立任务式默认入口，并以稳定的跨页面导航上下文把负责人带到真实处理位置。
- 把订单、履约、工资、财务、资料库改为一屏一个主要工作目标的交互模型，同时复用已落地的 V2 领域事实与负责人裁量。
- 为批量报销补齐原子领域命令、IPC 和界面能力，保证经营结果和现金流水的统计边界不变。
- 为在制品接入、质量扣款、返工、分批发货与售后建立可测试的端到端路径。

**Non-Goals:**

- 不创建独立的人工待办、自动催办、自动责任判定、自动收费或自动排班系统。
- 不接入打卡机、不把考勤记录变成排班或实发工资的唯一依据。
- 不实现原材料库存管理、采购成本拆分或订单级日常支出归集。
- 不改变既有测试数据的保留策略；本变更不要求为测试数据提供生产迁移兼容层。

## Decisions

### 1. 用应用级导航上下文替代页面间临时跳转

在 `src/renderer/pages/app.tsx` 将当前单一 `View` 状态扩展为应用级工作区状态：`view`、来源、对象标识和可选定位目标。导航上下文至少支持订单 ID 与订单子视图、工序任务 ID、售后记录 ID、结算 ID、财务视图与待报销条目 ID。页面接收明确的 `navigationTarget` 与 `onNavigate` 回调，并在完成处理或返回时恢复来源上下文。

选择该方式是因为现有 Electron 应用没有浏览器路由，且当前需求是同一主工作区内的上下文切换；保留本地状态可以避免引入 URL、历史栈和深链接持久化的额外复杂度。备选方案是增加 React Router；本次不采用，因为它不能单独解决来源恢复和组件草稿保留，且会扩大桌面应用路由改造范围。

### 2. 工作台采用只读聚合投影，不新增待办表

新增共享工作台契约和 main-process 聚合服务。服务从订单、履约、质检、售后、结算和财务未报销记录读取事实，归一化为带 `kind`、`bucket`、`priority`、`subject`、`quantityOrAmount`、`dueHint` 与 `navigationTarget` 的工作台事项。`bucket` 固定为 `decision` 或 `advance`，由明确规则映射：例如待质检、待确认结算、待处理售后进入 `decision`；待排工序、待发货、待报销进入相应可推进/处理入口。工作台只显示和跳转，不写入领域状态。

选择投影避免待办与领域事实双写、关闭待办后事实仍未解决等一致性问题。备选方案是持久化手工任务；不采用，因为用户明确不需要新的手工待办体系。

### 3. 订单按对象工作区处理，履约按跨订单队列处理

订单页维持“列表 / 创建 / 详情”互斥模式，订单详情新增 `overview | fulfillment | funds | afterSales` 子视图。订单页负责商业记录和单订单上下文；履约页只维护一个跨订单工序队列及一个阶段筛选，工序任务和现有在制品接入记录是该队列的事实来源。订单详情或工作台进入的特定工序任务会传递定位标识；履约页滚动/聚焦到目标任务并打开相应结果、质检或发货操作。

选择分离的原因是订单可并行包含多个商品、生产批次和发货批次，订单不具备唯一“下一步”；履约队列才是处理工序的最佳扫描位置。备选方案是为订单定义整体状态机和单一推进按钮；不采用，因为它会掩盖分批并行事实并误导负责人。

### 4. 创建资料采用调用方拥有草稿的回填协议

订单创建页保存订单草稿在自身状态中。客户/商品快捷新建以抽屉或对话框在原页面上下文中打开，提交后返回新建实体并自动写回相应草稿字段；若快捷创建取消或失败，原订单草稿保持不变。资料页的正常新建/编辑仍由其自身工作区管理，不能借由跳页重置订单草稿。

选择回填协议优于跳转到客户/商品页，是为了实现前置资料缺失时的连续操作。备选方案是跳转到资料页后由负责人手动返回并重新选择；不采用，因为会丢失输入上下文并增加首用阻力。

### 5. 工资确认使用“两个参考计算 + 一个负责人实发”模型

结算服务和视图以同一工资期间生成两个互不相加的参考口径：排班时长参考工资、考勤时长参考工资。任务快照决定制作/捏毛装袋的件数提成和各任务计价；打包、发货只参与时薪。确认命令只接受负责人提交的实发金额、付款日期和备注，且在同一事务内确认结算并创建 `worker_settlement` 来源的财务支出。

不合格制作任务产生提成、标准工时和胶水扣款。尚未确认的结算按现有扣款可用期间进入后续结算；已确认结算不得回写，需保存待退款处理记录。返工通过新的正常工序任务重新排班和结算，原任务不撤销扣款。

选择该模型是因为排班衡量产能、考勤记录实际到场，二者均可供负责人参考但不能替代最终裁量。备选方案是只选择其中一个时长口径自动支付；不采用，因为不满足已确认的业务规则。

### 6. 批量报销是原子命令，按选中垫付逐笔生成流水

将单笔 `V2ReimbursementInput` 扩展为批量输入 `V2ReimbursementBatchInput`，包含非空且去重的 `advanceFinancialEntryIds`、统一的 `reimbursedOn`、`paymentMethod` 和 `note`。财务服务在单一数据库事务内逐笔加载并校验选中条目：必须为私人垫付日常支出、未存在报销关联且仍可报销；全部通过后，为每笔原垫付创建一笔 `reimbursement` 来源财务流水并写入现有 `advance_reimbursements` 关联。批次响应返回所有新流水与关联的原垫付标识。

选择“一笔垫付对应一笔报销流水”而非合并为一个总额流水，是为了保留现有一对一关联表、逐笔审计及待报销状态判断，且无需新增报销批次表。备选方案是 UI 逐笔调用现有单笔命令；不采用，因为中途失败会产生部分成功。备选方案是新建一笔汇总报销流水；不采用，因为现有关联表模型是一对一且会降低追溯性。

### 7. 财务页面采用互斥模式，统计复用付款日与来源规则

财务页本地管理 `monthlyResult | cashflow | reimbursements` 三种模式，并只渲染当前模式的主内容。月度经营结果继续调用按 `occurredOn`（业务实际付款日期）计算的汇总；现金流水展示包括报销在内的财务记录；待报销视图只展示可报销私人垫付并启动批量确认。原私人垫付作为原日常支出计入经营支出，报销流水只进入现金流水，汇总函数继续排除其对经营支出的重复影响。

选择同一页面互斥模式而非拆分多个导航页，保持“财务”是同一业务对象、同时避免截图中三块纵向区域竞争注意力。备选方案是保留同页分段；不采用，因为用户明确反馈多标题、多列表干扰处理路径。

### 8. 售后保持自由处理记录，确认动作才派生后续事实

售后记录继续关联订单和原发货批次，并保存负责人输入的责任判断、客户收费、工作室成本和备注。界面将其作为订单“售后”子视图和工作台待决定事项展示。只有负责人明确选择重新包装、补发、返工或其他后续动作时，服务才创建对应工序任务、发货需求或财务关联；不从原因文本自动推导动作。

选择显式确认是为保持负责人裁量与真实定制场景的灵活性。备选方案是按责任类型自动生成固定流程；不采用，因为无法覆盖客户协商收费、少量免收费和组合处理。

## Risks / Trade-offs

- [工作台聚合查询跨多个服务，事项重复或排序不稳定] → 为每类事项定义唯一业务锚点和去重键，并在服务单元测试中覆盖同一工序、售后或结算只生成一条同类事项。
- [应用级导航上下文增加页面耦合] → 共享契约仅传递对象标识和声明式目标，页面不得传递组件实例或临时表单状态；来源恢复集中在 `App` 管理。
- [批量报销事务或校验不完整导致部分报销] → 使用仓储事务，先全量校验、后写入；为重复 ID、已报销、混入非私人垫付和写入异常加入回滚测试。
- [工资质量扣款影响历史结算的账务追溯] → 已确认结算不可更新；待退款使用独立处理状态和审计记录，避免回写历史金额。
- [现有页面重构范围较大，容易把视觉调整混入行为改造] → 每个页面先完成导航、主要列表和视图互斥，再接入已有设计系统组件；按任务清单逐项保留业务行为回归测试。
- [本地原生依赖可能阻塞全量测试] → 将领域/IPC/Renderer 测试分层执行并记录已执行命令；如 `better-sqlite3` 本机构建失败，明确报告环境阻塞，不将其视为业务用例失败。

## Migration Plan

1. 在现有 `codex/v2` 工作区完成共享契约、领域服务和 IPC 的向后兼容扩展；现有单笔报销入口在迁移期调用批量命令的单元素路径或保持适配层。
2. 增加工作台和应用级导航上下文，先接入现有页面而不删除既有业务服务；为订单、履约、工资、财务页面加入目标定位和来源返回。
3. 重构各页面为目标工作区，并在每一页完成后运行对应 Renderer 测试和核心领域/IPC 测试。
4. 批量报销只复用现有财务流水与 `advance_reimbursements` 表，数据库无需历史数据回填；测试数据可按既有 V2 重建策略清理。
5. 如部署后出现页面导航或聚合事项错误，回退 Renderer 对工作台和新导航上下文的使用，同时保留新增只读查询与批量报销服务；如批量命令故障，停止入口暴露并继续使用兼容的单笔适配入口。
