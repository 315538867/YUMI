## Context

本变更横跨排班、四工序履约、工时核算、工资结算、SQLite 数据迁移和多个界面入口，动机与业务边界见 `proposal.md` 和八份规格增量。

当前实现以 `work_assignments + process_tasks` 统一表达四道工序：计时核算明细通过 `process_task_id` 找到订单商品，制作完成与质检分别写入 `process_results` 和 `quality_inspections`，计时核算存在 `draft → confirmed → voided` 状态及再次确认动作。该结构使计时排班必须先绑定订单商品，也使制作和计时都暴露了不必要的二次操作。

实现必须满足以下约束：

- 继续兼容既有制作任务、历史计时任务、履约事件、核算和结算记录的读取。
- SQLite 迁移只能新增版本，不能重写已经执行的历史 migration。
- 所有影响履约数量和工资来源的确认、更正、作废必须在主进程事务内完成。
- 渲染进程校验只用于即时反馈，主进程必须独立重复所有业务校验。
- 本期不接入考勤设备，不改变物流发货批次和财务结算的既有职责边界。

## Goals / Non-Goals

**Goals:**

- 在数据模型和 API 上明确区分“制作数量排班”与“计时公共班次”。
- 为制作提供一次提交的结果与质量原子核算，为计时工序提供一次提交的时间与多商品原子核算。
- 让核算明细直接落到 `order_item_id` 并冻结后续工资、预计效率所需快照。
- 以“有效核算记录是否存在”投影待核算/已核算，审计状态不额外制造负责人待办状态。
- 收口新增排班入口，同时保留历史数据、作废链、更正链和结算锁定保护。
- 让负责人工作台直接识别制作待核算任务与无任务计时班次，并统一导航到待核算工作区。

**Non-Goals:**

- 不删除历史 `process_tasks`、`process_results`、`quality_inspections` 或旧计时核算关联。
- 不把一项计时班次拆成多段考勤，也不实现休息时段自动扣除。
- 不允许无排班直接登记核算。
- 不根据预计效率自动扣薪、拒绝确认或调整履约数量。
- 不在本次变更中重做工资结算、履约调整或发货模块。

## Decisions

### 1. 工作安排使用显式排班模式，计时班次不创建任务

在 `work_assignments` 增加排班模式字段，例如：

- `making_task`：新制作排班，必须包含制作 `process_tasks`。
- `timed_shift`：新计时排班，不包含 `process_tasks`。
- `legacy_task`：迁移前创建的历史安排，保持原任务关系和只读兼容。

新建输入改为可判别联合类型：制作输入包含 `tasks`，计时输入只包含 `workerId`、`assignedOn`、`processType` 和 `note`。主进程按排班模式校验字段组合，禁止计时输入夹带任务、数量、预计分钟或返工来源。

对 `timed_shift` 增加部分唯一索引，约束同一 `worker_id + assigned_on + process_type` 最多一条未取消记录。历史 `legacy_task` 不纳入索引，避免旧库中合法的多任务班次导致升级失败。

**选择理由：** 继续复用 `work_assignments` 可保留周历、人员、日期和状态查询；增加显式模式比通过“任务数组是否为空”推断更稳定，也能安全隔离历史数据。

**未采用方案：** 新建独立 `timed_shifts` 表。它会使周历、状态更新、人员反查和导航形成两套仓储及查询，收益不足以抵消复杂度。

### 2. 业务只展示两种核算状态，审计记录保留内部状态

负责人看到的状态由安排投影：

- 存在有效安排且没有当前有效核算：待核算。
- 存在当前有效核算：已核算。

`voided` 继续作为历史记录的审计状态，但不作为第三类负责人待办；作废后安排重新投影为待核算。新流程不再创建 `draft`。迁移时现有草稿标记为作废历史并释放其关联安排，现有已确认和已作废记录保持不变。

**选择理由：** 删除审计状态会破坏追溯；把审计状态与用户待办状态分离，可以同时满足“两状态流程”和历史可查。

**未采用方案：** 继续保留草稿并隐藏按钮。隐藏并不能消除主进程中的半完成业务事实和二次确认分支。

### 3. 新计时核算一项安排对应一条有效记录

在 `work_time_reviews` 增加可空的 `work_assignment_id`：新记录必须填写，历史聚合记录允许为空并继续通过 `work_time_review_assignments` 读取。新写入仍可同步维护关联表用于兼容查询，但服务层只接受单个 `workAssignmentId`。

数据库对新记录建立“每项安排最多一条 `confirmed` 当前记录”的唯一约束；更正事务先将旧记录转为 `voided`，再写入新的 `confirmed` 版本。增加 `supersedes_review_id`、`void_reason`、`voided_at` 等审计字段，以表达更正和作废链。

**选择理由：** 用户核对的是一项班次的实际时间和产出，一对一关系可以消除当前跨多安排聚合造成的状态歧义。保留旧关联表可避免强行拆分历史记录。

### 4. 时间范围是唯一工时输入，分钟由主进程确定

新计时核算输入包含 `startedAt` 和 `endedAt`，不接受 `approvedMinutes`。时间选择精度为分钟；主进程要求秒和毫秒为零，校验：

1. 开始时间的本地业务日期等于安排 `assignedOn`。
2. 结束时间严格晚于开始时间。
3. 当前主进程时间大于或等于结束时间。
4. 差值为正整数分钟。

计算结果继续存入 `approved_minutes`，原始时间写入现有 `raw_started_at/raw_ended_at`，`worked_on` 取开始日期。跨日不拆单。

**选择理由：** 复用现有分钟和原始时间列可以降低迁移成本；由主进程计算避免前端换算、时区或篡改造成不一致。

**未采用方案：** 同时允许手工分钟覆盖。双来源会产生“时间范围与分钟不一致”且无法确定工资依据。

### 5. 计时商品候选直接从履约可处理量生成

`WorkTimeReviewService` 增加候选查询，输入为计时安排标识和可选搜索词；服务验证安排人员、日期、工序及状态后，从订单商品履约汇总计算当前工序可处理量：

- 捏毛装袋：已合格制作进入的可用量。
- 缝边：待缝边量与订单缝边剩余需求两者的较小值。
- 打包发货：当前待打包量。

候选返回 `orderItemId`、客户、订单号、商品快照、交期、订单时间、可处理数量、单件预计分钟和适用提成。排序固定为逾期优先、交期升序、订单时间升序，稳定键使用订单和商品标识。前端勾选后把数量初始化为可处理量，但允许负责人调小。

提交时主进程在同一写事务内重新计算所有候选可处理量并逐项校验，不能信任页面加载时的数值。相同订单商品在一次核算中只能出现一次，数量必须为正整数。

**选择理由：** 排班不再持有订单上下文，核算时必须直接查询真实履约池；事务内复算可以处理多个窗口并发核算同一商品的情况。

### 6. 计时核算明细以订单商品为主关联并冻结快照

迁移重建 `work_time_review_items`，使 `order_item_id` 成为新记录必填主关联，并新增：

- `piece_rate_cents_snapshot`
- `expected_unit_minutes_snapshot`
- 可选 `process_task_id`，仅保留历史兼容
- 唯一约束 `review_id + order_item_id`

历史明细从关联 `process_tasks` 回填 `order_item_id`、提成和可取得的预计分钟；无法可靠补齐的历史预计分钟允许为空，界面明确显示历史指标不可计算。新记录必须具有完整快照，打包发货提成固定冻结为 0。

每个新明细直接生成以 `work_time_review_item` 为来源的履约事件，不再先创建 `process_result`。履约事件日期取核算归属日期。确认、履约事件和核算明细必须在同一 SQLite 事务提交。

**选择理由：** `order_item_id` 是履约流转的真实归属，快照是未来商品参数变化后仍可复算工资和效率的必要条件。

**未采用方案：** 核算时临时创建隐藏 `process_tasks`。这会把已经解耦的计划关系重新伪造出来，并继续污染已派/超派口径。

### 7. 制作核算通过一个原子服务命令完成

共享契约新增制作核算输入：`processTaskId`、`completedQuantity`、`qualifiedQuantity`、核算日期及备注。主进程校验：

- 任务必须是制作且尚未核算。
- `0 <= qualifiedQuantity <= completedQuantity <= plannedQuantity`。
- `unqualifiedQuantity = completedQuantity - qualifiedQuantity`。
- `unfinishedQuantity = plannedQuantity - completedQuantity`，仅用于展示和释放排产缺口。

本方案明确以本次制作排班计划作为实际产出上限，避免一项任务超额消耗其他有效制作排班已占用的订单需求；现场实际超过计划时，负责人先调整尚未核算的制作计划或新增制作安排，再按调整后的计划核算。

允许 `completedQuantity = 0`，用于负责人确认当班没有产出的真实结果并关闭待核算事项。v16 migration 重建或兼容调整 `process_results.completed_quantity` 约束为非负整数；零产出仍创建结果和 `0/0` 质量事实以保留审计，但不得生成履约事件、计件工资或材料扣款。

服务在一个数据库事务中创建 `process_result` 和 `quality_inspection`，生成适用的合格履约事件、制作计件工资依据与材料扣款，并把任务直接转为 `confirmed`。新界面和 IPC 不再暴露“先完成、后质检”的操作链；旧方法只保留历史兼容或内部测试所需，不作为新 UI 入口。

**选择理由：** 继续保存结果与质量两类事实可兼容结算及审计，但负责人只需一次操作，且不会留下待质检中间态；允许零产出可以如实关闭班次而不伪造数量。

### 8. 制作和计时更正、作废均采用版本替换

制作与计时更正输入都与各自新建核算相同并额外要求原因。服务先检查两类锁：

- 履约锁：旧完成量是否已被下一工序、发货或其他不可逆事实消耗。
- 结算锁：该核算是否已进入已确认工资结算。

计时以 `work_time_reviews` 作为版本根；制作以 `process_results` 作为版本根，为其增加 `status`、`supersedes_result_id`、`void_reason`、`voided_at` 等审计字段，并对每项制作任务建立最多一条当前有效结果的部分唯一约束。制作版本同时关联其 `quality_inspections`、履约事件、工资来源和材料扣款来源。

未锁定时，在一个事务中删除或冲销旧版本生成的履约事件、取消未确认工资来源、将旧版本标记为 `voided`、写入原因和替代关系，再创建新的 `confirmed` 版本。作废只执行前半段并使对应安排重新投影为待核算。负责人执行“更正”时不需要先手动作废再重新登记。

如果旧核算已被加入工资结算草稿，服务 SHALL 同步取消旧草稿来源并重新计算该草稿的计时工资、制作计件、材料扣款和总金额；只有进入已确认结算才形成结算锁。已被履约或确认结算锁定时拒绝直接操作，履约差异使用现有履约调整，工资差异使用后续结算调整。

**选择理由：** 两类核算采用一致的版本替换规则，既满足界面上的统一“更正/作废”，也避免草稿结算残留旧金额或已结算历史被静默改写。

### 9. 结算读取核算明细快照，不再依赖计时任务

结算候选中的计时工资继续从 `work_time_reviews.approved_minutes` 和时薪快照计算，计件提成改为汇总 `work_time_review_items.completed_quantity × piece_rate_cents_snapshot`。相应调整 `worker_settlement_timed_items`：新增 `work_time_review_item_id`，允许历史 `process_task_id` 为空或保留，并以核算明细快照复制结算行。

已确认历史结算保持原值；新查询同时兼容旧任务型明细和新订单商品型明细。核算更正或作废时，处于草稿结算中的旧来源必须取消并触发草稿金额重算；已确认来源只允许通过后续结算调整。任何迁移都不得重新生成已存在的结算来源。

**选择理由：** 新计时排班没有任务，结算必须消费核算时冻结的事实，而不是查询当前商品配置或伪造任务。

### 10. 渲染层收口为人员周历和单次核算工作台

排班页默认并只保留人员周历；删除订单视角页签和行内派工，保留当前周历布局、周切换、稳定人员颜色及日期格“+ 派工”。派工抽屉根据工序类型切换表单：制作沿用订单商品任务编辑，计时只显示人员、日期、工序和备注。

待核算面板按安排类型渲染：

- 制作：实际产出、合格数量，实时展示系统计算的不合格与未完成；允许实际产出为零，但不得超过本次计划。
- 计时：一个开始/结束时间范围、候选商品选择器、逐项完成数量和只读效率指标。

计时安排的可进入规则只按本地业务日期判断：`assignedOn <= 今天` 时可打开核算，`assignedOn > 今天` 时只打开安排详情。系统不在打开表单前声称班次已经结束；确认提交时再校验开始日期等于排班日期、结束时间晚于开始时间且不晚于当前时间。

确认后直接刷新为已核算。已核算详情对制作和计时都提供查看、更正、作废，不再出现草稿、保存并确认、确认工时或待质检按钮。

负责人工作台不再只遍历 `assignment.tasks`。它直接从制作待核算任务和 `timed_shift` 生成“待核算”事项，并深链到排班菜单的统一待核算视图；制作一次核算后不再生成新的待质检事项，历史待质检记录仍按旧数据只读兼容。

`工作安排记录` 页面移除“新建工作安排”和实际数据录入，仅保留筛选、列表、详情、状态及核算记录查看。订单和人员详情只读展示或导航到排班/核算菜单，不自动打开创建表单。

**选择理由：** 单一创建入口可避免不同页面维护不同规则；核算集中后，工作安排详情不再承担业务提交职责。

### 11. 契约、IPC 与幂等边界同步调整

共享契约按制作/计时拆分工作安排输入，新增制作一次核算、计时候选、计时确认、更正和作废输入输出。`v2-runtime`、IPC handler、preload API 和渲染 composable 使用同一命名与类型。

计时确认命令以 `workAssignmentId` 作为业务幂等边界，制作确认以 `processTaskId` 作为业务幂等边界：已有当前有效核算时返回明确冲突；更正必须携带旧版本 ID 并验证它仍是当前版本。

履约事件增加可空的 `source_event_key`。所有新核算事件都使用确定性的事件级键，并建立部分唯一索引 `(source_record_type, source_record_id, source_event_key)`；捏毛装袋分流时分别使用不同键，例如 `to_edge_sewing` 与 `to_packing`。历史事件允许该键为空。事务与事件级唯一索引共同保证命令重试不重复写入，同时允许一个核算明细合法生成多条履约事件。

**选择理由：** Electron 渲染进程不是可信边界，必须通过共享契约和主进程服务统一校验；明确当前版本可防止两个窗口覆盖彼此。

## Risks / Trade-offs

- **[历史计时安排可能一条核算关联多个安排]** → 保留 `legacy_task` 和旧关联表只读兼容；新流程只对 `timed_shift` 强制一对一，不强拆历史记录。
- **[重建核算明细和结算明细表可能破坏外键]** → 在 v16 migration 中使用临时表复制、行数/关联校验、事务提交，并增加目标结构守卫与迁移测试。
- **[两个窗口同时核算同一订单商品可能超量]** → 主进程在写事务内重新汇总可处理数量，逐项校验后再生成事件；页面校验不作为最终依据。
- **[跨日和系统时区造成归属偏差]** → 时间选择和业务日期均使用本地时区，要求分钟精度，`worked_on` 固定取开始时间本地日期并覆盖跨午夜测试。
- **[更正时旧产出已被下游部分消耗]** → 不做自动净额猜测；检测到任一下游消耗即阻止直接回退并引导使用显式履约调整。
- **[核算已进入工资草稿后更正导致金额陈旧]** → 在同一事务中取消旧草稿来源并重算草稿；已确认结算继续形成硬锁。
- **[捏毛装袋一个明细需要生成多条分流事件]** → 使用事件级 `source_event_key`，不得只对来源记录 ID 建唯一约束。
- **[移除订单视角后制作待派可见性下降]** → 订单详情继续展示制作排产缺口和履约阶段数量，只移除直接创建入口及不成立的计时已派口径。
- **[工作安排记录已有未提交的并行界面改动]** → 实施时按文件逐项合并并保留现有工作树修改，禁止整文件覆盖；测试先锁定“移除新建入口、详情只读”的行为。
- **[旧客户端与新数据库混用]** → 升级前备份，数据库版本升级后不支持旧客户端继续写入；启动时用目标结构守卫拒绝不兼容模型。

## Migration Plan

1. 在变更实施前备份 SQLite 业务库，并记录 v15 数据库中工作安排、任务、核算、核算明细、履约事件和结算来源数量。
2. 新增 v16 migration：
