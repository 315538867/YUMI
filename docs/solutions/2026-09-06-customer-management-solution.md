## 1. 范围

本方案为 YUMI 捏捏工作室桌面应用新增独立“客户管理”模块，并调整订单客户选择规则。

纳入范围：

1. 客户主档的独立列表、新增、编辑、详情和受限删除。
2. 客户详情的已关联订单、待发货、收付款/退款影响后的当前欠款汇总。
3. 订单创建和编辑时必须选择已建档客户。
4. 订单中允许修改本次客户资料，但只更新订单客户快照，绝不回写客户主档。
5. 保留既有客户与订单关联，不迁移、不删除历史数据。

不纳入范围：

1. 订单页手动填写临时客户或从订单页新增客户。
2. 客户合并、客户标签、等级、营销、跟进记录或外部联系人同步。
3. 改写既有订单、发货单、导出单据中的客户快照。

## 2. 当前行为

1. 数据库已有 `customers` 主表和 `orders.customer_id` 外键字段，订单同时保存 `customer_snapshot_json`。
2. 当前订单创建/编辑在未传入客户 ID 时会自动插入客户主档；订单表单也将“已有客户”之外的路径标记为“新建客户”。
3. 预加载层仅暴露客户列表与客户订单历史接口，渲染层没有独立“客户管理”导航和页面。
4. 客户历史当前只返回订单列表，未提供客户详情、汇总、新增、编辑和删除能力。
5. 数据库中的历史客户及订单均已保留客户关联；这些客户应继续显示并可维护。

## 3. 已确认的业务规则

1. 客户档案仅能在“客户管理”中新增和编辑。
2. 创建或编辑订单时必须选择一个已建档客户；未选择客户不得保存，并提示先到客户管理建档。
3. 订单选择客户后带出姓名、联系方式和默认收货地址；用户仍可在订单中针对本次业务修改这些字段。
4. 订单中对客户资料的修改只写入订单客户快照，不修改客户主档；客户主档后续编辑也不改写历史订单、发货单和导出单据。
5. 所有新订单都必须具备明确的 `customer_id`，不再存在手填临时客户或无客户关联的新增订单。
6. 历史客户记录全部保留并直接展示在客户管理中，无需数据迁移。
7. 客户详情只汇总其 `customer_id` 已关联的订单；当前欠款随订单收款与退款实时重算。
8. 有已关联订单的客户禁止删除；没有关联订单的客户允许删除。

## 4. 页面与交互设计

### 4.1 导航与客户列表

在桌面应用侧边栏新增“客户管理”入口，位置与订单、商品、制作/发货等经营模块保持一致。

列表提供：

- 名称、联系方式和地址关键字搜索；
- 新增客户按钮；
- 客户名称、联系方式、默认地址；
- 最近订单日期；
- 累计订单数；
- 待发货订单数；
- 当前欠款；
- 查看详情和删除入口。

删除入口只对零关联订单客户可用。若客户已有订单，界面不执行删除，并明确提示“该客户已有订单记录，不能删除”。

### 4.2 新增与编辑客户

新增、编辑表单仅维护客户主档字段：

- 客户名称（必填）；
- 联系方式；
- 默认收货地址；
- 备注。

保存成功后刷新客户列表。该操作不会批量回填或改写任何历史订单的客户资料。

### 4.3 客户详情

客户详情页或详情抽屉由三部分组成：

1. 客户资料区：展示主档资料和编辑入口。
2. 汇总区：累计订单数、待发货订单数、当前欠款、最近订单日期。
3. 关联订单区：按现有订单摘要口径展示订单号、交期、生产状态、应收、已收净额、未收金额和资金状态；点击后沿用现有订单详情/编辑入口。

当前欠款定义为该客户全部关联订单 `outstandingCents` 的合计；订单收款、退款或订单金额变动保存后，重新进入或刷新客户详情即可取得最新汇总。

### 4.4 订单表单

订单表单将现有“已有客户”选择器改为必填“客户”选择器：

1. 默认不选中客户。
2. 未选择客户时禁止提交，并显示明确校验提示。
3. 选择客户后从主档带出名称、联系方式与默认地址。
4. 名称、联系方式与地址字段继续允许编辑，但用于保存订单客户快照，不修改主档。
5. 移除“新建客户”文案、订单页自动建档逻辑，以及没有客户 ID 的保存分支。

## 5. 技术设计与边界

### 5.1 领域模型与持久化

- 保持 `customers` 表及客户主档字段不变；历史数据无需迁移。
- 保持 `orders.customer_id` 和 `customer_snapshot_json` 的双轨结构。数据库字段暂不强制改为 `NOT NULL`，以避免无必要的 SQLite 表重建；服务层对所有新建、编辑订单强制校验客户 ID，确保业务层不再产生空关联订单。
- 将订单使用的客户输入从通用 `CustomerInput` 中分离为专用订单客户输入：客户 ID 必填，姓名、联系方式和地址作为本次订单快照字段。客户备注仅属于主档，不作为订单表单字段。
- 订单创建和编辑均先校验所选客户存在，再写入 `customer_id` 和订单快照；绝不创建或更新客户主档。
- 主档删除前查询关联订单数。数量大于零时返回领域校验错误；数量为零时删除客户。

### 5.2 服务、IPC 与契约

保留现有 `customers.list()` 供订单客户选择器加载基础资料，避免破坏既有调用方。新增独立管理能力：

- 客户管理列表：返回客户主档及列表汇总数据。
- 客户详情：返回客户主档、汇总数据与关联订单摘要。
- 新增客户、编辑客户、删除客户。

新增契约类型应区分以下职责：

- `CustomerProfile`：纯客户主档；
- `CustomerOverview`：列表所需的主档加统计；
- `CustomerDetail`：主档、汇总及关联订单摘要；
- `OrderCustomerSnapshot` / 订单客户输入：订单的本次姓名、联系方式和地址快照数据，与客户主档更新请求分离。

主进程服务负责输入校验和删除约束；仓储层负责客户聚合查询、详情查询和受限删除；IPC 与预加载层仅暴露经过类型约束的操作；渲染层不直接拼装 SQL 或推断财务金额。

### 5.3 渲染层组织

为避免继续膨胀现有应用根组件，客户管理使用独立页面组件承载列表、详情和编辑弹窗/抽屉；应用根组件只负责导航、页面切换和数据刷新边界。订单编辑弹窗仅负责客户选择、快照回填与提交校验。

## 6. 验收标准

1. 侧边栏存在“客户管理”入口，能浏览历史已有客户与后续手动新增客户。
2. 可按名称、联系方式或地址搜索客户；列表正确显示最近订单、累计订单、待发货订单和当前欠款。
3. 可新增、编辑无订单客户；编辑客户主档后，历史订单、发货信息和已导出的业务单据不被改写。
4. 客户详情只展示已关联订单，并正确汇总订单数、待发货数和当前欠款；收款、退款后刷新可见最新金额。
5. 有关联订单的客户删除失败且提示原因；无关联订单客户可删除。
6. 新建和编辑订单必须选择已建档客户；没有客户选择时不能保存。
7. 订单选择客户后自动带出主档资料；订单内修改姓名、联系方式、地址后，只影响本订单快照，不回写主档。
8. 新建和编辑订单均不会再自动创建客户；所有新订单均保存有效客户关联。
9. 新增服务、仓储和渲染测试覆盖客户 CRUD、删除限制、客户汇总、订单必选客户、快照不回写主档等关键场景；类型检查、Lint、全量测试、生产构建及 OpenSpec 严格校验通过。

## 7. 风险与明确取舍

1. 历史数据库架构允许 `orders.customer_id` 为空，但本次不做高风险表重建；以服务层校验保障今后新增和编辑订单的业务不变量。
2. 客户主档和订单快照的重复是有意设计，用于保留真实的历史下单资料；不能通过主档编辑“修正”旧订单上的客户信息。
3. 当前欠款按已关联订单的未收金额相加，不代表客户信用额度、对账单或跨订单收款核销能力；这些能力超出本期范围。
4. 不支持从订单页快捷新增客户，以确保客户档案始终由客户管理显式维护。
