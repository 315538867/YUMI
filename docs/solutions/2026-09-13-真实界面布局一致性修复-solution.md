# YUMI 真实界面布局一致性修复方案

- **方案版本**：v1.1
- **设计日期**：2026-09-12
- **最后更新**：2026-09-13
- **方案状态**：实施中
- **关联既有方案**：
  - `docs/solutions/2026-09-10-yumi-operating-ui-design-standard-v2-solution.md`
  - `docs/solutions/2026-09-08-yumi-design-system-ui.md`
- **关联 OpenSpec**：`yumi-ui-layout-consistency-remediation`（实施中；2026-09-13 新建）
- **适用范围**：经营工作台真实运行页面的布局、层级、共享组件、详情展现方式和运行时暴露链路

> 本方案是在真实 Electron 页面核对后形成的“视觉与页面结构纠偏”方案；此前未完成提案已于 2026-09-13 归档，本方案使用新的 OpenSpec 单独追踪。它不重新发明业务，不改变已经确定的订单、商品、排班、发货、资金、盈利、工资、报表和设置业务口径；它只解决真实界面与设计图偏差、共享组件不一致、页面层级不稳定和运行时接口缺失问题。

## 1. 背景与问题定义

当前设计稿已经形成了较完整的业务页面集合，但真实运行界面与设计稿仍有明显差异。主要问题不是单个页面的颜色或字号，而是页面骨架没有成为可执行的全局规范：

1. 页面级 Tab 被放在内容中间，导致用户不能快速判断当前页面边界；
2. 页面、区块、控件之间的留白没有统一尺度，同类页面出现过大的空白或控件贴合；
3. 设置、商品、客户、工资、排班、订单详情等页面的页头、操作区、表格工具栏和卡片样式不一致；
4. 详情内容使用抽屉时存在错位风险，长内容、表格和多 Tab 详情无法稳定承载；
5. 表格搜索区在窄宽度下被 flex 压缩，筛选按钮和统计文本出现变形；
6. 同一页面不同 Tab 的动作有时在主标题右侧，有时在副标题右侧，用户无法形成稳定预期；
7. 返回按钮混入业务动作组，甚至出现在按钮组中间，破坏导航层级；
8. 订单详情需要按真实功能固定为“概览、排班、发货、资金、盈利、售后”六个页面级 Tab，概览只保留摘要和概览，不把排班、发货详情重复塞回概览；
9. 发货记录与发货清单需要保持记录级关系，发货清单必须保存创建时快照，不能被后续商品或订单修改追溯性地改变；
10. 真实运行中发现 `window.yumiV2.reports.getOrderBusinessDetail is not a function`，说明渲染层声明、preload 暴露、IPC 注册和主进程服务之间存在运行实例不一致，不能只通过 UI 绕过。

## 2. 目标

### 2.1 目标

- 建立所有经营页面共用的“页头 → 页面级 Tab → 当前内容”骨架；
- 用统一的 spacing、宽度、按钮、表格工具栏、卡片和反馈 token，消除页面私有拼法；
- 明确页面级 Tab、区块级切换、记录级操作和实体级操作的边界；
- 统一页头动作位置、返回行为、详情打开方式和抽屉/Dialog/独立页面的使用边界；
- 让订单详情可以稳定承载六个页面级 Tab，并保持概览高密度、职责单一；
- 修复 `getOrderBusinessDetail` 的真实运行链路，并增加防回归验证；
- 先修共享基础能力，再按页面迁移，避免逐页出现新的视觉分叉；
- 在真实 Electron 页面中完成 1440px、窄屏和多 Tab 手工验收。

### 2.2 非目标

- 不改变订单、商品、排班、发货、资金、盈利、售后、工资和报表的业务规则；
- 不修改“制作、捏毛装袋、打包”等真实生产阶段的定义；
- 不改变发货双方承担方、运费字段、优惠金额、提成和人工成本的计算口径；
- 不新增权限、审批、库存、会计分录或自动化决策；
- 不在本次变更内重写所有后端领域模型；
- 不以设计稿静态占位内容替代真实数据和真实操作；
- 不为了追求像素相似而引入固定最小高度，避免产生大面积空白。

  - 文件：`src/renderer/components/ui/sheet/yumi-sheet.tsx`、`src/renderer/components/ui/dialog/yumi-dialog.tsx`
- 页面与组件样式
  - 文件：`src/renderer/styles/pages.css`、`src/renderer/styles/components.css`

### 3.2 已确认的业务页面

迁移时以真实页面为准，至少覆盖：

- 工作台/总览；
- 商品列表与商品详情；
- 客户列表与客户详情；
- 订单列表与订单详情；
- 排班订单视角与人员周历视角；
- 发货记录与发货清单；
- 月度经营、工资结算、人员与时薪；
- 设置中的工作室参数、计算公式、财务资料、数据保护；
- 补录期初在制品等专用工作区。

### 3.3 运行时错误链路

静态源码中已经存在以下声明与实现：

```text
renderer: src/renderer/composables/use-orders.ts
  -> window.yumiV2.reports.getOrderBusinessDetail(orderId)

preload: src/preload/index.ts
  -> ipcRenderer.invoke('v2:reports:orders:business:detail', orderId)

main IPC: src/main/ipc/report-ipc.ts
  -> service.getOrderBusinessDetail(orderId)

service: src/main/services/report-service.ts
  -> repository.listOrderBusinessSources()
```

但真实 Electron 运行实例仍提示：

```text
window.yumiV2.reports.getOrderBusinessDetail is not a function
```

实施时必须验证运行中的 preload bundle 是否为当前源码构建结果，并检查：

1. `window.yumiV2.reports` 是否存在；
2. `getOrderBusinessDetail` 是否为函数；
3. renderer 调用是否能够到达 IPC handler；
4. IPC handler 是否调用 service；
5. 无数据、未知订单和 service 异常是否有稳定反馈；
6. 重新加载页面后不会因为旧 preload 缓存继续报错。

## 4. 统一页面骨架

所有页面默认采用以下顺序，除非是明确的全屏工作区：

```text
应用导航
└─ 页面容器
   ├─ 页面标题区
   │  ├─ 信息型页面标题
   │  ├─ 上下文/状态说明（按需要显示，不强制写成一句话）
   │  └─ 页面级动作组（右侧）
   ├─ 页面级 Tab（有页面级分区时才出现）
   ├─ 当前 Tab 内容
   │  ├─ 区块标题/说明/区块级动作
   │  ├─ 指标或摘要
   │  ├─ 工具栏
   │  └─ 表格、列表、表单或工作区
   └─ 页面级反馈/状态
```

### 4.1 页面标题必须承载有效信息

页面标题不是装饰性大字，也不要求固定为“一句话”。标题应优先承担识别当前对象、当前范围和当前状态的任务；副标题只补充标题无法承载的上下文，信息没有增量时可以省略。

标题采用以下信息优先级：

1. **对象**：当前正在查看或处理什么，例如“订单详情”“商品”“工资”；
2. **对象识别信息**：客户、订单号、商品名、月份或人员，例如“罗小雨｜订单详情”“2026 年 9 月工资”；
3. **当前范围/状态**：必要时补充“待发货”“本周”“只读”等上下文；
4. **动作**：不要把“编辑”“新建”写进标题，动作应放在右侧按钮组。

推荐示例：

| 页面 | 不推荐 | 推荐标题 | 可选说明 |
| --- | --- | --- | --- |
| 订单详情 | `订单详情` | `罗小雨｜订单详情` | `待发货 · 预计 2026-09-26 发货` |
| 商品列表 | `商品管理` | `商品` | `商品参数下单时冻结；这里只记录实际胶水用量。` |
| 工资 | `工资` | `2026 年 9 月工资` | `确认实际工资并处理待退款。` |
| 排班 | `排班页面` | `排班` | `按订单查看待派与已派，或按人员查看本周任务。` |
| 设置 | `设置` | `工作室参数` | `维护全工作室统一使用的参数。` |

规则：

- 标题至少要让用户知道“我在哪里、正在看什么”；
- 说明必须提供范围、状态、影响或下一步中的至少一种信息；
- 说明没有信息增量时直接省略，不用无意义的宣传句或重复标题；
- 标题过长时优先保留对象和关键识别信息，次要信息放到摘要或说明；
- 页面级动作仍固定在标题行右侧，不因标题信息变多而移到说明行。

### 4.2 页面级 Tab

- 只承载整个页面主内容的切换，例如订单详情的“概览 / 排班 / 发货 / 资金 / 盈利 / 售后”；
- 固定在页面标题和说明下方，位于内容开始之前；
- 不放在两个内容卡片之间；
- 同一页面的所有页面级 Tab 使用同一个组件、同一个位置、同一个选中态；
- Tab 切换不改变页面标题、页头动作和返回位置；
- URL/hash 或页面状态应能表达当前 Tab，刷新后保持上下文；
- 页面级 Tab 数量较多时允许横向滚动，但不改成“更多”菜单隐藏核心业务 Tab。

### 4.3 区块级切换

- 只用于单个区块内部的不同视角，例如排班页的“订单视角 / 人员周历”；
- 必须放在所属区块的标题和说明附近，不能冒充页面级导航；
- 区块级切换使用 `YumiSegmentedTabs` 或同等明确的区块组件；
- 区块级切换只影响该区块，不应导致整页标题、页头动作或其他区块位置变化。

### 4.4 页面模式

| 页面模式 | 适用页面 | 固定结构 | 主要动作归属 |
| --- | --- | --- | --- |
| 列表页 | 商品、客户、订单、工资、人员 | 页头 + 可选页面 Tab + 列表区块 | 新建/导出放页头，搜索/筛选放列表工具栏 |
| 实体详情页 | 订单、商品、客户 | 返回上下文 + 实体摘要 + 页面级 Tab + 当前内容 | 编辑/导出/业务动作放页头右侧 |
| 记录页 | 发货记录、资金流水、工资结算 | 页头 + 记录区块 + 明细/快照 | 新增记录放所属区块右侧，记录操作在行内 |
| 设置页 | 工作室参数、计算公式、财务资料 | 页头 + 页面级设置 Tab + 设置卡片 | 编辑放页面头；字段只读展示默认优先 |
| 工作区 | 排班处理、期初在制品 | 页头 + 任务上下文 + 工作区内容 | 返回放标题左侧；处理动作放任务/区块内部 |

### 4.5 分步工作区与选择结果

期初在制品等工作区属于跨步骤的初始化流程，不能将“第一步”显示成裸文本、而“第二步”再套进卡片，造成视觉层级和操作节奏断裂。

- 返回排班队列属于导航，必须放在标题左侧或标题上方的上下文行，不能占用右侧动作位；
- 每个步骤使用同一种 `YumiWorkflowStep`（或基于 `YumiSection` 的统一变体）承载：步骤标题、步骤说明、输入/选择结果和帮助信息；
- 已搜索到的订单商品必须渲染为可辨识的候选结果行：订单号、客户、商品、确认数量、选择状态/动作均在同一行或同一张紧凑卡片内；
- 选择结果与候选列表均须有明确的容器、间距、悬浮/选中态，禁止以连续裸文本和孤立按钮表达列表；
- “订单商品仅用于归属和后续交期、发货闭环”等帮助说明放在该步骤底部，不能与候选条目混排；
- 第一步完成后，第二步的选中商品、数量、目标阶段、登记日期和备注遵循统一的两列表单网格；窄屏时再降为单列；
- 工作区不以大面积留白表达“步骤感”，步骤之间使用 `--yumi-space-6` 的固定节奏。

## 5. 全局视觉 Token 与间距规范

### 5.1 间距原则

以 8px 为基础单位，所有新样式必须使用 token，不直接写新的任意像素值：

| Token | 建议值 | 用途 |
| --- | ---: | --- |
| `--yumi-space-1` | 4px | 图标与文字、极小内联间距 |
| `--yumi-space-2` | 8px | 标签内间距、紧凑字段 |
| `--yumi-space-3` | 12px | 控件组内间距 |
| `--yumi-space-4` | 16px | 表单字段、表格单元格、区块内部 |
| `--yumi-space-5` | 20px | 小区块间距 |
| `--yumi-space-6` | 24px | 页头与 Tab、区块之间 |
| `--yumi-space-8` | 32px | 页面主区块、容器内边距 |
| `--yumi-space-10` | 40px | 页面级大分组 |
| `--yumi-space-12` | 48px | 仅用于明确的页面分隔，不作为默认留白 |

规则：

- 页面容器内边距默认 32px；窄屏降为 20px 或 16px；
- 页头标题、说明、动作组之间不使用空白撑高；
- Tab 与内容区默认间距 24px；
- 区块标题与区块内容默认 16px；
- 空状态只按内容需要占高，不设置用于模拟设计图的固定最小高度；
- 页面出现大面积无信息空白时，优先检查 `min-height`、`align-content` 和父级 grid/flex 约束。

### 5.2 尺寸与响应式

- 页面内容区域采用统一最大宽度 token；
- 1440px 桌面视口使用完整内容密度；
- 1024px 及以下逐步压缩页面内边距和列间距；
- 窄屏下表格允许横向滚动，不能让按钮或筛选控件被压扁；
- 页面级动作允许换行，但每个按钮保持完整文字和最小可用宽度；
- 详情页的摘要指标在窄屏下由 4 列降为 2 列或 1 列，不改变信息顺序。

## 6. 页头、返回和操作规范

### 6.1 页头动作位置

- 页面级动作统一放在主标题行右侧；
- 说明文字只负责补充范围、状态或下一步，不承载页面级主操作；
- 说明不是必填项；如果标题已经表达完整上下文，则不额外添加空泛说明；
- 区块级动作统一放在该区块标题行右侧；
- 不允许同一页面不同 Tab 分别把同类动作放在主标题和副标题两处；
- “新建、编辑、导出、刷新”等动作应根据作用域放在页面头或对应区块头，不放在内容底部。

### 6.2 返回按钮

- 返回是导航动作，不是业务动作；
- 独立详情页：放在页面标题上方的面包屑/上下文行，或标题左侧；
- 工作区：放在标题左侧，并使用统一的返回文案；
- 不得插入“编辑、导出、作废、发货”等业务按钮组中间；
- 业务动作组内按“低风险辅助动作 → 次要动作 → 主动作”排序，主动作固定在最右侧。

### 6.3 “更多”菜单

- 核心、频繁、可影响当前工作流的动作必须直接显示；
- 只有低频、次要、空间确实不足且不影响发现性的动作才进入菜单；
- 订单详情右上角应直接展示用户已确认的核心动作，不用“更多”隐藏导出、编辑等常用动作；
- 菜单不能作为解决布局不统一的默认手段。

## 7. 列表工具栏与表格规范

### 7.1 工具栏布局

工具栏采用稳定的三段式布局：

```text
[搜索输入框：自适应填充] [筛选控件：固定宽度] [统计文本：不压缩]
```

实现约束：

- 搜索容器 `flex: 1 1 auto; min-width: 180px`；
- 筛选控件 `flex: 0 0 auto`，设置明确最小宽度；
- 统计文本 `flex: 0 0 auto; white-space: nowrap`；
- 工具栏窄屏时允许换行，不允许按钮缩成不可读的窄条；
- 搜索、筛选和统计的垂直对齐统一；
- 按钮、选择框和输入框高度统一使用控件尺寸 token；
- 搜索区下方与表头之间使用 24px 或既定 token，不根据页面随意变化。

### 7.2 多筛选条件的桌面布局

两个及以上筛选条件不能作为一个无结构、可任意换行的节点交给工具栏。组件接口和布局都要能够表达每一个筛选项的独立宽度与顺序。

1440px 及常规桌面视口的目标结构：

```text
[搜索订单号、客户：自适应] [全部资金状态：固定宽度] [全部交付排班：固定宽度] [共 1 张订单：不压缩]
```

实现约束：

- `YumiListToolbar` 应接收结构化的筛选项列表/插槽，而非将多个 `ReactNode` 无差别包入同一个可换行容器；
- 桌面端采用稳定的列结构，例如 `minmax(240px, 1fr) auto auto auto`，搜索区占剩余空间，每个选择框各占一个固定宽度槽；
- 普通筛选选择框使用统一的理想宽度 token（建议 184px～200px），在桌面端不得因外层 `width: 100%` 或 `flex-wrap` 被拆为上下两行；
- 筛选项之间使用 `--yumi-space-3`，统计文本靠右且 `white-space: nowrap`；
- 只有当容器实际小于 1024px 或内容确实无法容纳时，工具栏才允许折行；640px 及以下搜索、筛选和统计依次全宽排列；
- 标签文案已包含“全部资金状态”“全部交付排班”时，视觉上不额外叠加第二行字段标签；但无障碍标签仍必须完整存在。

当前订单列表中“资金状态”和“交付排班”上下堆叠属于不合格状态，不能以增加空白或压窄搜索框规避。

### 7.3 表格

- 表头、行高、单元格内边距使用共享表格 token；
- 操作列靠右，保持固定最小宽度；
- 主字段允许两行信息，但不通过极窄列迫使每个字换行；
- 空状态、加载状态、错误状态和有数据状态必须共用相同的表格容器；
- 详情型实体优先使用独立详情页，不用抽屉承载超宽表格。

### 7.4 排班任务分配列

排班队列的“待派 / 已派任务”列应改名为“任务分配”，按**一个工序一行**表达分配事实，不再使用工序卡片套任务卡片的多层布局。

桌面端每个工序行的目标结构：

```text
制作 · 已指派 0 件 · 未指派 70 件                              [派工]
捏毛装袋 · 已指派 小A 30 件 · 未指派 0 件                     [查看任务]
```

规则：

- `已指派数量` 由该工序 `schedule.tasks` 的计划数量聚合；`未指派数量` 使用现有 `schedule.unassignedQuantity`；如存在 `overassignedQuantity`，以紧凑告警标签单独显示，不能混入正常数量；
- 工序名称、已指派、未指派和主操作默认水平对齐；桌面端正常内容不得因为样式把“制作 70”“未派 70”“派工”拆成两三行；
- 已有一个任务时，展示负责人和数量，例如“已指派 小A 30 件”；多个任务时收敛为“已指派 2 人 / 30 件”，通过“查看任务”进入处理上下文，不在单元格中为每个任务再堆一个大按钮；
- 未指派数量大于 0 时展示“派工”；全部已派时展示“查看任务”或同等上下文动作；操作按钮使用紧凑尺寸且不可收缩；
- 只有实际内容溢出、存在超派告警或窄屏宽度不足时才允许换行；换行优先保持工序与数量在一起，而不是把按钮或数字拆成孤立行；
- 该列本质是队列摘要，具体派工日期、任务状态和全部任务明细应在“进入处理”后的工作区呈现，不能抢占列表行高度。

## 8. Drawer、Dialog 与独立详情页

### 8.1 使用边界

| 展现方式 | 应用场景 | 禁止场景 |
| --- | --- | --- |
| 独立详情页 | 订单/客户/商品等需要多 Tab、长表格、深层上下文的实体详情 | 仅为少量字段查看而增加页面跳转 |
| Dialog | 短表单、确认、少量字段编辑、不可分割的快速操作 | 长表格、多 Tab、复杂业务流程 |
| Drawer | 与当前列表强关联的短编辑/快速录入，且内容高度可控 | 详情页、长表格、需要固定底部操作且会发生错位的复杂内容 |

### 8.2 迁移原则

- 当前已出现错位的详情抽屉优先迁移为独立详情页或居中 Dialog；
- 抽屉必须有稳定宽度、滚动区域、底部操作区和关闭后状态恢复；
- 不通过抽屉承载页面级 Tab；
- 打开客户、商品、订单详情时，默认先进入只读详情，不直接进入编辑态；
- 编辑必须是明确动作，保存/取消不影响详情页当前 Tab。

## 9. 订单详情页目标结构

订单详情是本次端到端验收样板，目标结构如下：

```text
返回订单列表
订单详情页头
├─ 罗小雨｜订单详情（标题承载客户和对象信息）
├─ 待发货 · 预计 2026-09-26 发货（只补充当前状态和交付上下文）
├─ 订单号 YUMI-20260909-40DA4997（辅助识别信息，小字号）
├─ 联系人 / 交付安排 / 地址等高价值摘要
└─ 导出订单表、编辑订单等页面级动作（直接显示）

页面级 Tab
概览 | 排班 | 发货 | 资金 | 盈利 | 售后

当前 Tab
```

### 9.1 概览

- 只显示订单摘要、客户/交付摘要和核心指标；
- 核心指标包括订单金额、累计收款、待收款、发货进度；
- 仅保留排班概览，不把排班队列、人员周历和任务操作重复放入概览；
- 商品信息以高密度表格或简洁列表呈现；
- 不用一张过高的空卡片承载低密度信息。

### 9.2 排班

- 订单详情内新增并固定“排班”页面级 Tab；
- 展示本订单的制作、捏毛装袋、打包等阶段和负责人/状态；
- 进入复杂处理时跳转或进入排班工作区，不在概览内展开完整工作区；
- 阶段数量、待派工、制作中、待质检、已完成等指标保持在当前 Tab 内。

### 9.3 发货

- 展示发货记录列表；
- 新增发货记录必须通过“新增发货”动作进入表单，初始页面不能直接出现可编辑空行；
- 每条发货记录包含发货数量、时间、物流/单号、运费、运费承担方和备注等已确认字段；
- 承担方仅允许两方：工作室、客户；
- 发货清单属于每次发货记录，不属于订单概览；
- 创建发货记录时生成清单快照，后续商品、订单或价格变化不能修改已生成清单；
- 支持查看、下载该次发货的清单快照。

### 9.4 资金

- 展示收款、待收款、优惠金额和资金流水；
- 新建订单时保留订单优惠金额字段；
- 资金 Tab 只展示资金事实，不把盈利成本混入订单商品计算。

### 9.5 盈利

- 独立展示收入、商品成本、人工成本、提成、运费/其他支出和预计/已实现盈利；
- 商品计算不包含运费；
- 人工成本、提成基于现有数据和设置中的公式计算；
- 兼职人工时薪使用设置中的全局值；
- 计算公式在设置的“计算公式” Tab 中集中列出，不在订单页面重复维护；
- 后端若需要新增汇总查询或快照字段，必须在实施计划中显式列出。

## 10. 设计 Token 与共享组件改造边界

## 11. 后端与运行时改动清单

本次以“前端按规范还原，后端只补支撑真实功能”为原则。需要后端/运行时确认或改动的项目如下：

### 11.1 必须修复

- 确认 `getOrderBusinessDetail` 在当前 Electron preload 构建产物中被暴露；
- 确认 `v2:reports:orders:business:detail` IPC handler 在主进程注册；
- 确认 service 返回契约与 renderer `V2OrderBusinessDetail` 一致；
- 增加运行时自检或集成测试，避免静态类型通过但真实 preload 缺失。

### 11.2 按现有数据模型评估

- 盈利 Tab 是否已有订单级汇总查询；若没有，新增只读查询接口，不把计算逻辑散落到前端；
- 发货记录是否已有运费、承担方和快照字段；缺失时新增迁移、写入和读取契约；
- 发货清单下载是否基于发货记录快照；若当前是动态读取商品，则改为创建记录时固化快照；
- 订单优惠金额是否已进入订单快照、资金和盈利口径；若没有，补充字段和计算链路；
- 计算公式设置是否已有持久化结构；若已有，前端只做统一展示和编辑入口；若没有，先在实施计划中明确后端存储与版本策略。

### 11.3 后端边界

- 公式的最终计算和金额精度必须由后端/领域服务作为事实来源；
- 前端只展示输入、公式说明、结果和加载/错误状态；
- 历史发货清单和历史订单金额不能因当前设置变化而被重新解释；
- 任何新增字段必须有默认值、迁移策略和历史数据兼容策略。

## 14. 风险、回滚与实施边界

### 14.1 风险

- 共享页头或 Tab 调整可能影响多个页面，需要先补组件测试再迁移页面；
- 详情从 Drawer 改为独立页面可能影响路由/hash 和返回逻辑；
- preload 构建缓存可能让源码修复未即时反映到运行实例；
- 发货快照、订单优惠和盈利汇总涉及历史数据兼容，不能只改前端；
- 窄屏换行策略若没有固定最小宽度，可能再次产生按钮压缩。

### 14.2 回滚

- 共享组件改动按组件和页面分组提交，出现回归时可以按页面回退；
- 后端字段或数据库迁移必须提供向后兼容读取和默认值；
- 详情页切换保留原入口映射，保证旧 hash/深链可以转换到新页面；
- 任何视觉迁移不删除真实数据读取逻辑，先保留旧分支直至新页面完成回归。

### 14.3 实施边界

本方案完成后只代表设计和实施边界已经确认。下一阶段必须单独创建 OpenSpec 实施任务，明确：

- 每个组件和页面的具体任务；
- 前后端契约与数据库影响；
- 测试先行和验收证据；
- 每个任务的完成边界；
- 是否允许提交、何时提交以及提交范围。
