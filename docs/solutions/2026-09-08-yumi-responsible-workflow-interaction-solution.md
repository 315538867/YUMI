# YUMI 负责人工作流交互重构方案

## 1. 目标与问题定义

YUMI 面向定制捏捏工作室负责人。负责人每天实际需要处理的不是页面模块，而是订单推进、生产安排、质量异常、分批发货、售后决策、工资确认和私人垫付报销。

当前界面的问题不是单纯视觉样式，而是信息架构把“页面名称、区块名称、说明、空状态、操作入口”同时摊在一个页面：同一件事被多次命名，同一个动作被多次放置，且经营概览、流水、报销、资料维护等互不相干的任务在同一屏竞争注意力。页面看似完整，负责人却不能快速判断下一步。

本方案目标是把系统改为负责人任务驱动的操作工具：

1. 打开系统后先看到真实业务产生的待处理事项；
2. 每个页面只服务一个主要任务；
3. 订单、生产批次、发货批次、售后、工资和财务保持可追溯但不互相挤占页面；
4. 系统提供事实、计算和提醒，负责人保留售后、收费、排班和最终实发工资的裁量；
5. 不改变已经确认的 V2 业务口径，也不新增库存、权限或自动决策体系。

## 2. 已验证现状与约束

### 2.1 现有入口

当前应用主导航位于 `src/renderer/pages/app.tsx`，已有订单、履约、工资、财务、报表、客户、商品、设置八个入口。订单页已有列表、创建、详情三种内部状态；工资页已有结算与人员时薪切换；财务页已有经营概览、流水、待报销能力。相关领域契约分别位于 `src/shared/contracts/orders.ts`、`fulfillment.ts`、`settlements.ts`、`finance.ts` 和 `after-sales.ts`。

### 2.2 不可改变的业务规则

- 一个订单可含多个商品；每个商品及其生产、发货均可分批。
- 制作、捏毛装袋、打包、发货是履约工序；制作与捏毛有提成，打包和发货仅参考时薪。
- 制作验收以合格数量为提成依据；不合格品扣提成、固定标准工时工资及胶水成本。
- 不合格品须由负责人重新排班，返工任务作为新正常任务计算，不免费回写原任务。
- 打卡机不接入系统；工资必须同时保留排班参考和考勤参考，两者不能合并为总工时。
- 最终实发金额、付款日期和备注由负责人确认；确认即代表实际发放。
- 私人垫付有待报销与已报销状态；报销不重复计入经营支出。
- 收支按实际付款日期统计；日常支出不关联订单；不做原料库存。
- 客户退回、补发、换包装、加封边、加配饰等售后由负责人决定责任、收费和处理方案，系统不得强制固定场景。

## 3. 推荐信息架构

```text
工作台

业务
- 订单
- 履约
- 工资

资金
- 财务
- 经营报表

资料与设置
- 客户
- 商品
- 设置
```

工作台是默认首页。订单、履约、工资和财务是高频任务入口；客户、商品和设置是低频资料维护入口；报表只负责分析和导出，不承载日常操作。

## 4. 工作台：唯一的负责人待处理事项队列

### 4.1 职责

工作台不是经营仪表盘，也不是多个模块列表的拼接。它只展示真实业务状态自动产生、需要负责人处理的事项。

工作台仅有一个列表，并通过两个互斥视图筛选：

- **需要我决定**：售后责任与方案、工资草稿确认、私人垫付报销、质量不合格处理、订单补款或退款等；
- **可以推进**：待安排制作、待安排捏毛、待打包、待登记发货、待建立工资结算等。

每条事项必须包含来源、关联对象、出现原因和唯一下一步动作。点击后直接进入对象详情中实际需要处理的区域，而非先跳到模块首页再让负责人查找。

### 4.2 排序与状态

事项先按“需要我决定”与“可以推进”排序；同类事项按业务阻塞程度和发生时间排序。系统不擅自标记紧急程度、不替负责人设定截止日期，也不在第一版提供手工待办，避免真实业务事项与个人提醒混淆。

### 4.3 首次使用

无基础资料时，工作台显示最小启动路径：建立客户 → 建立商品 → 创建第一张订单。一次只突出当前下一步；人员、财务类目和垫付人不是首次启动硬前置条件。

## 5. 订单、履约与售后

### 5.1 三个不可混淆的对象

| 对象 | 职责 |
| --- | --- |
| 订单 | 客户购买内容、价格、收款、总交付进度与售后归属 |
| 生产批次 | 单一商品的一部分数量在制作、捏毛、打包中的履约过程 |
| 发货批次 | 某次实际寄给客户的商品组合，可组合多个商品和生产批次 |

生产批次不等于发货批次。一次发货只能选择已完成打包且尚未发出的数量；一张订单可同时存在制作中、待发货和已发出批次。

### 5.2 订单列表与创建

订单列表默认显示“进行中”，并提供待确认、已完成、全部等互斥筛选。每行只展示客户、商品种数与总数量、履约摘要、收款摘要和最近需要推进的事项。列表只负责定位订单，不直接摊开展开排班、发货、售后或资金表单。

新建订单是独立聚焦流程：选择客户、添加商品与数量、填写价格/收款/备注、创建订单。创建订单不要求同时拆分生产批次。创建过程中可就地新建客户或商品，保存后自动回填到当前订单草稿。

### 5.3 订单工作区

订单详情以订单身份和当前状态为头部，上下文互斥切换为：概览、履约、资金、售后。

- **概览**：只展示订单整体交付、收款和需处理事项，并作为进入具体处理位置的入口；
- **履约**：切换生产批次与发货记录。生产批次按商品和批次展示当前工序，发货记录按实际寄件记录展示；
- **资金**：处理订单收款、退款、售后收费等订单资金事项；
- **售后**：记录退回事实，支持负责人选择责任说明、处理动作、客户收费与内部成本。

订单层不设置笼统的“推进下一步”操作，因为多批次订单没有唯一下一步。具体操作必须落在具体生产批次、发货批次或售后记录上。

### 5.4 履约主页面和任务详情

履约主页面是跨订单任务队列，采用待制作、待捏毛、待打包、待发货、异常等互斥工序筛选，一次只展示一个工序队列。每行显示商品、订单、批次、数量、当前状态和唯一下一步，例如安排捏毛或登记发货。

履约任务详情只处理某生产批次当前工序。制作验收录入合格数量、不合格数量、原因和胶水成本；合格数量进入下一工序，不合格数量生成可追溯扣款参考，并由负责人显式创建新的正常制作任务。捏毛、打包、发货记录任务数量、排班参考时长、考勤参考时长与完成确认；不虚构打卡明细或精确每件耗时。

### 5.5 中途接入与售后

对于系统启用前已制作完成、尚未捏毛或打包的存量，订单履约提供“接入已有在制批次”。负责人填写商品、数量、当前工序和说明；系统从该工序继续记录，不补造历史排班、工资、提成或质检记录。

售后必须关联原订单及原发货批次。先记录退回/客户反馈等事实，再由负责人决定责任说明、处理动作、客户收费、内部成本和是否生成重新包装、加工、补发或新制作任务。售后不覆盖原发货历史；其产生的任务回到履约，其资金结果回到订单资金与财务。

订单状态为进行中、待收尾、已完成。全部应交付数量已发出但仍存在待收款、未关闭售后或负责人未确认时为待收尾；最终关闭由负责人确认。

## 6. 工资与结算

### 6.1 页面结构

工资页提供本期待结算、结算记录、人员与时薪三个互斥工作区。默认本期待结算先选择负责人填写的结算周期，再列出该周期内有工作、扣款或待处理结算的人员。

### 6.2 两套参考口径

结算详情必须分别展示：

```text
排班参考时长 / 考勤参考时长
排班参考工资 / 考勤参考工资
```

排班参考工资 = 排班参考时薪 + 制作合格提成 + 捏毛完成提成 − 不合格扣款。

考勤参考工资 = 考勤参考时薪 + 制作合格提成 + 捏毛完成提成 − 不合格扣款。

考勤参考时长由负责人按打卡机汇总录入，可附来源备注；系统不要求逐次打卡明细。打包、发货不计提成，仅参与对应时薪参考。制作与捏毛提成均使用任务与商品规则快照。

### 6.3 扣款、确认与历史

不合格扣款需逐条显示来源订单、商品、生产批次、数量、提成扣除、固定标准工时扣除、胶水成本和处理状态。

- 原工资尚未结清：扣款作为待扣项纳入后续结算；
- 原工资已结清：不可回写已确认结算，改为生成待退款记录；
- 退款完成后保留待退款、已退款历史。

负责人确认结算时填写最终实发金额、付款日期和备注。若最终金额与两套参考均不同，系统要求说明但不阻止确认。确认后锁定参考快照及已纳入扣款，标记实际发放，并自动生成来源为工资结算的实际支出，避免在财务重复登记。

人员与时薪维护当前时薪和生效历史；未来调整只影响后续任务和结算，不回写历史快照。

## 7. 财务与报销

### 7.1 页面结构

财务页以统计期间为上下文，提供月度结果、收支流水、待报销三个互斥视图，并保持“登记收支”为唯一页面级主操作。

- **月度结果**：实际收入、经营支出、经营结果、待报销；
- **收支流水**：按实际付款日期、收入/支出、类目、金额、垫付及报销状态查询；
- **待报销**：只展示私人垫付且尚未报销的记录，支持选择多笔完整报销。

### 7.2 收支登记与统计口径

登记收支先选择收入或支出，再渐进展示相关字段。收入填写类目、金额、实际收款日期、备注，不区分账户。支出填写类目、金额、实际付款日期、付款来源和备注；仅在选择私人垫付后要求选择垫付人。

所有收入和支出按实际付款日期归属月份。私人垫付在原发生日计入经营支出；登记报销只形成现金流，不再次计入经营支出。每笔私人垫付只能完整报销一次，可多笔合并报销。日常支出不关联订单，不做原料库存管理。

### 7.3 财务基础资料

设置中的财务基础使用“收支类目 / 垫付人”互斥视图。类目与垫付人可新增、改名和停用；已被历史流水引用的资料不可删除，停用后不再参与新建选择，但历史展示保持不变。

## 8. 客户、商品与设置

客户和商品使用统一资料库模型：单一页面标题、唯一新增操作、搜索/筛选、单一业务列表和右侧详情/编辑抽屉。客户详情可查看联系人、收件信息、订单概况和最近订单；商品详情可在基本资料、成本与提成、使用情况之间互斥切换。

客户采用轻量新建与编辑抽屉。商品价格、材料成本、制作提成等修改只影响后续新建订单或后续排班；订单、排班、结算和历史报表保留各自快照。商品或基础资料停用后不能再选用，但历史对象不受影响。

设置只承担低频配置，不能在同一屏同时铺开收入类目、支出类目与垫付人多个空白区域。

## 9. 全局交互规范

### 9.1 页面模型

所有页面必须从以下模型中选择，不自由拼接：

| 模型 | 用途 | 页面 |
| --- | --- | --- |
| 工作台 | 聚合需要负责人处理的真实事项 | 工作台 |
| 任务列表 | 查找与推进业务对象 | 订单、履约、工资、财务流水 |
| 对象工作区 | 在单一复杂对象内切换处理上下文 | 订单、履约任务、工资结算、售后详情 |
| 资料库/设置 | 维护低频基础数据 | 客户、商品、类目、垫付人、人员时薪 |

### 9.2 标题、操作和列表

- 每页只能有一个页面标题；不再重复“客户 / 客户资料”或“商品 / 商品资料”；
- 每页最多一层内容切换；
- 每个视图只有一个页面级主操作；其他操作置于对象详情、更多菜单或上下文区域；
- 一屏只展示一张主业务列表；若存在详情，则是列表与详情的主从关系，不可并列多个互不相关列表；
- 列表行默认点击进入详情，次要操作收纳，避免形成按钮墙。

### 9.3 空状态

必须区分三类状态：

| 状态 | 文案与动作 |
| --- | --- |
| 首次无数据 | 页面右上仅保留唯一新增操作；内容区简短说明，不重复同一按钮 |
| 前置条件不足 | 页面主操作切换为当前唯一前置步骤，按顺序引导，不显示注定失败的业务动作 |
| 筛选无结果 | 明确说明没有匹配结果，提供清除筛选，不误称为没有数据 |

工作台无待办时只表示当前无事项，不使用大面积空壳模块。

### 9.4 上下文、取消与返回

从订单、收支登记、排班等流程中创建客户、商品、类目、垫付人或人员后，保存结果必须自动回填当前表单并留在原流程。关闭抽屉或详情后，保留搜索、筛选、月份/日期范围、列表滚动位置与当前对象上下文。复杂表单存在未保存输入时，关闭或返回必须提示继续编辑或放弃内容。

## 10. 非目标与兼容性

本方案不引入原料库存、云同步、多人权限、手工待办、打卡机明细采集、自动工资决策、自动售后责任判定或日常支出订单归集。它不修改已确认的领域计算口径；后续实施应优先复用既有 V2 领域契约和数据，只有无法承载“工作台聚合”或明确交互状态时才提出最小的新读模型或字段变更。

## 11. 验收标准

### 11.1 负责人操作效率

1. 打开应用后可在工作台三秒内识别需要决定或推进的事项；
2. 从工作台到某项实际处理位置不超过一次点击；
3. 从订单中创建客户或商品后不丢失订单草稿且自动回填；
4. 多商品、多生产批次、多发货批次订单可明确查看和推进；
5. 售后可追溯到原订单和原发货批次，并能创建新的履约任务；
6. 工资同时展示两套参考，最终金额始终由负责人确认；
7. 私人垫付可完整报销一次且不会重复计入经营支出。

### 11.2 页面结构

1. 页面仅保留一个标题、一个页面级主操作和最多一层内容切换；
2. 同一屏不再堆叠多个无关联标题、列表或空状态；
3. 首次无数据、缺少前置条件和筛选无结果均使用正确且不同的交互；
4. 资料库、设置和复杂业务对象分别使用合适的抽屉、列表或工作区模型；
5. 负责人保留所有需要业务裁量的最终决定权。

## 12. 后续实施边界

本方案获负责人书面复核后，进入新的 OpenSpec 提案与任务规划。提案应按页面模型和真实任务路径拆分，不可仅按“调整样式”或“替换组件”拆分。实施前需先核对现有 V2 契约能否直接提供工作台聚合、订单批次/发货批次定位、售后处理跳转、结算扣款状态与报销筛选；任何新增数据变更必须在提案中单独说明迁移、兼容和回滚策略。

## 13. 实施回写（2026-09-08）

### 13.1 已落地结果

- 应用默认入口已改为工作台；“需要我决定 / 可以推进”为互斥视图，事项跳转进入订单、履约、工资或财务的真实处理位置。
- 订单保持列表、创建、详情三种互斥工作区；详情使用概览、履约、资金、售后子视图。履约改为跨订单单一队列，并支持阶段筛选、在制品接入和分批发货定位。
- 工资页面将结算、待退款、人员与时薪分为互斥视图；新建结算移入抽屉，排班和考勤工资只作两套参考，负责人填写最终实发后才确认并写入工资支出。
- 财务页面将月度结果、现金流水、待报销分为互斥视图；私人垫付支持全量预校验后的原子批量报销，报销现金流不会重复计入经营支出。
- 客户、商品、订单和工资等页面移除了重复区块标题、同屏重复空状态和重复新增按钮；客户/商品建档与工资新建均按需打开抽屉。
- 已新增统一空状态语义：`first-use`、`prerequisite`、`filter`，分别用于首次资料缺失、业务动作缺少前置资料和筛选结果为空；筛选状态提供回到全部待办，前置资料状态提供前往客户/商品建档的真实入口。

### 13.2 实际边界与方案一致性

- **无范围外的业务规则扩张。** 原料库存、打卡机明细接入、自动工资决策、自动售后定责、自动生成售后返工/收费仍不在范围内。
- 售后采用比“确认即自动派生”更严格的负责人裁量边界：确认售后只保存责任、收费、成本和备注等事实；返工、补发、重新包装、实际收费与财务登记必须由负责人继续显式发起，不由系统根据原因或责任自动生成。
- 系统中途接入的在制品只从负责人填写的当前工序继续，不回填接入前的排班、工资、提成或质检历史。
- 除上述为落实“负责人决定”而明确的边界外，实施结果与本方案的页面模型、财务口径、工资口径及导航原则一致。
