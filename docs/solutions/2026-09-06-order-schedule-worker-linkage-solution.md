# YUMI 订单、排班与兼职人员数据联动方案

## 1. 目标与背景

当前订单、排班、兼职人员分别有独立页面和状态展示。底层数据实际上已经存在关联：排班任务通过 `orderItemId` 关联订单商品，班次通过 `workerId` 关联兼职人员；但订单页面没有聚合展示相关排班和合格完成进度，兼职人员页面也不能反查其订单任务，因此使用者会感觉三块数据彼此独立。

本变更将订单商品作为生产需求的事实来源，将排班任务和实际制作结果作为生产事实来源，在已有订单、排班、兼职人员页面补齐同一套实时汇总数据，形成：

- 订单 → 商品 → 相关排班 → 兼职人员的正向追踪；
- 兼职人员 → 订单商品 → 班次的反向追踪；
- 订单数量、有效排班、合格完成、不合格数量和待补排缺口的一致口径；
- 排班超出订单合格品需求时的明确提示和确认保护。

## 2. 已确认的业务规则

### 2.1 订单数量口径

订单商品的 `quantity` 表示需要交付的**合格产品数量**。不合格品、返工品和报废品均保留在质量记录中，但不能抵扣订单需求。

### 2.2 生产进度口径

以订单商品为最小汇总单元，再汇总到订单层级：

- **订单数量**：订单商品数量之和，表示合格品需求；
- **合格完成**：相关排班任务登记的 `qualifiedQuantity` 之和；
- **有效已排**：状态为 `scheduled` 的班次任务 `plannedQuantity` 之和；已完成班次不再以计划量占用未完成排产额度；
- **未排 / 待补排**：`max(0, 订单数量 - 合格完成 - 有效已排)`；
- **不合格累计**：相关任务的 `unqualifiedQuantity` 之和，仅用于质量统计；
- **超排量**：排班预览时，本次安排后预计覆盖量超过订单需求的部分。

请假、缺勤、取消的班次不计入有效已排，其原计划数量立即释放回缺口。已完成班次以实际合格完成数为准；计划数量与合格完成数的差额会形成待补排。

### 2.3 自动排产状态

新增只读的“排产状态”展示，不立即删除或替换现有 `productionStatus` 字段，以兼容当前报表、发货流程和历史数据。排产状态按订单商品计算后汇总至订单：

| 排产状态 | 判断规则                                                                                  |
| -------- | ----------------------------------------------------------------------------------------- |
| 待排产   | 合格完成为 0、有效已排为 0，且没有需要补排的历史生产记录                                  |
| 部分已排 | 合格完成 + 有效已排小于订单数量，且当前存在有效已排                                       |
| 已排满   | 合格完成 + 有效已排达到或超过订单数量，但合格完成小于订单数量                             |
| 待补排   | 合格完成 + 有效已排小于订单数量，且存在不合格、报废、已完成但合格不足、或被释放的历史安排 |
| 制作完成 | 合格完成大于或等于订单数量                                                                |

当多个商品状态不一致时，订单层级优先展示更严重或更需要行动的状态：制作完成仅在全部商品完成时成立；存在待补排时优先展示待补排；否则按已排满、部分已排、待排产的顺序判断。订单详情仍展示每个商品的独立状态和数量。

> “未排 / 待补排”是数量口径，“排产状态”是用户界面状态。两者同时展示，避免只看一个状态无法判断实际缺口。

### 2.4 超排保护

新增或编辑排班保存前，按订单商品计算：

`历史合格完成 + 其他有效已排（编辑时排除当前班次） + 本次计划数量 > 订单数量`

满足条件时，排班预览返回订单超排风险，必须向用户显示明确的黄色提示，至少包含：订单编号、商品名称、订单需求、当前合格完成、当前有效已排、本次安排数量和超出数量。未确认风险时禁止保存；用户确认后允许保存，并沿用现有风险确认/审计机制。

此规则是**强提示而非绝对禁止**，以兼容备货、赠品或工作室主动多做的场景；界面不得静默截断数量，也不得把超出部分伪装成正常未排进度。

订单商品数量被下调时，如果低于已有合格完成或当前有效排班覆盖，也使用同一类超量影响提示，不删除历史实际制作记录。

## 3. 页面设计

### 3.1 订单列表

在现有订单列表中新增紧凑的生产进度信息：

- 合格完成 / 订单需求；
- 当前有效已排数量；
- 未排 / 待补排数量；
- 排产状态徽标；
- 待补排和超排使用醒目的语义色提示。

列表层面按订单汇总，不展开所有班次；点击订单进入详情查看商品和排班明细。

### 3.2 订单详情

新增“商品生产进度”和“相关排班”区域。

商品生产进度按商品展示：

- 商品名称；
- 订单数量；
- 合格完成；
- 不合格累计；
- 有效已排；
- 未排 / 待补排；
- 排产状态。

相关排班按商品或日期展示：

- 班次日期和时间；
- 兼职人员；
- 计划数量；
- 班次状态；
- 合格数量、不合格数量；
- 未完成数量；
- 进入对应班次详情的操作。

订单详情从相关排班可以定位到班次详情和兼职人员，不复制生产数据，只传递实体 ID 或查询条件。

### 3.3 排班创建与编辑

选择订单商品时，在候选项旁显示当前生产进度，例如：

`草莓熊 · 合格 7/20 · 当前有效已排 8 · 可继续安排 5`

优先展示仍有缺口的商品，但不隐藏已覆盖商品。预览区展示本次安排后的预计覆盖量；超排时显示风险明细，只有确认后才能保存。班次状态或生产结果发生变化后，订单列表、详情和兼职人员详情重新读取即可得到最新汇总。

### 3.4 兼职人员详情

新增“订单任务”汇总，按订单 → 商品分组展示：

- 计划数量；
- 合格完成；
- 不合格数量；
- 尚未完成数量；
- 相关班次日期；
- 各班次状态。

支持从人员订单任务打开订单详情，也支持继续进入对应班次详情，形成双向追踪。

## 4. 数据模型与接口边界

采用**实时汇总读模型**，不新增排产进度表，也不在订单表或订单商品表持久化“已排、未排、待补排”等易产生不同步的冗余字段。所有页面复用服务端同一套聚合规则。

共享契约增加以下只读模型：

- `ProductionProgressSummary`：订单商品的需求、合格完成、不合格、有效已排、未排/待补排、状态和超排信息；
- `OrderScheduleSummary`：订单相关班次及其商品、兼职人员、计划量、班次状态和完成结果；
- `WorkerOrderTaskSummary`：兼职人员按订单商品汇总的计划量、合格量、不合格量、未完成量和班次日期。

扩展现有返回值：

- `OrderSummary` 增加订单级排产进度和排产状态；
- `OrderItemDetail` 增加商品级排产进度；
- `OrderDetail` 增加相关排班列表；
- `WorkerDetail` 增加订单任务汇总；
- `ShiftPreviewResult.risks` 增加订单商品超排风险。

写入入口保持不变：订单创建/编辑、排班创建/编辑、班次状态变更、实际制作结果登记。写入完成后不需要额外同步任务，下一次读取通过聚合查询得到最新结果。

## 5. 测试与验收标准

### 5.1 服务和领域测试

必须覆盖：

1. 无排班时的待排产和全量未排数量；
2. 部分排班时的有效已排、未排和部分已排状态；
3. 有效已排覆盖需求但合格完成不足时的已排满状态；
4. 合格完成达到需求时的制作完成状态；
5. 不合格、报废或实际合格数不足时自动形成待补排；
6. 请假、缺勤、取消立即释放计划量；
7. 已完成班次不以计划量抵扣，按实际合格数量结算；
8. 新增和编辑排班超排时返回风险，未确认不能保存，确认后可以保存；
9. 编辑排班预览排除当前班次，避免把原任务重复计算；
10. 订单详情相关班次和兼职人员订单任务汇总与底层记录一致；
11. 多商品订单按商品状态正确汇总为订单级状态；
12. 订单数量下调时不静默截断历史记录并给出影响提示。

### 5.2 渲染层验收

- 订单列表能同时看到合格完成、有效已排、未排/待补排和排产状态；
- 订单详情能按商品看到生产进度及相关班次；
- 排班表单能看到候选订单商品当前缺口和超排警告；
- 兼职人员详情能看到订单任务汇总并完成双向跳转；
- 待补排、超排、不合格相关信息具有清晰的视觉警示；
- 页面刷新或完成保存后，三个页面不会保留过期的进度数字。

## 6. 范围、依赖与非目标

### 本期范围

- 订单、排班、兼职人员三处的实时联动展示；
- 合格品口径的生产进度汇总；
- 超排提示与确认保护；
- 请假、缺勤、取消、不合格造成缺口的自动反映；
- 相关服务契约、聚合查询、渲染展示和自动化测试。

### 依赖

- 继续使用现有 SQLite 表：`orders`、`order_items`、`shifts`、`shift_tasks`、`workers`；
- 继续使用现有 `orderItemId` 和 `workerId` 关联；
- 复用现有排班风险确认和审计机制；
- 当前数据库无需迁移，旧订单和历史排班按现有记录参与汇总。

### 非目标

- 不自动替用户安排日期或自动分配兼职人员；
- 不新建独立排产工作台；
- 不改变收款、发货和人员结算的既有计算口径；
- 不立即删除或重定义现有 `productionStatus`；
- 不阻止用户在确认风险后进行超排；
- 不引入多人协作、云同步或库存扣减。

## 7. 实施顺序建议

1. 抽取并测试统一的订单商品生产进度聚合规则；
2. 扩展共享契约和主进程服务/仓储查询；
3. 接入订单列表与订单详情；
4. 接入排班预览、超排确认和候选商品进度；
5. 接入兼职人员详情的订单任务汇总与跳转；
6. 完成渲染层回归测试和端到端验收。
