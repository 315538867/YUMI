# YUMI V2 核心业务重构方案

## 1. 方案目标

YUMI 用于定制捏捏工作室的订单履约、兼职协作和经营管理。工作室的真实流程不是单一制作任务，而是：

```text
客户确认订单
  → 制作
  → 捏毛装袋
  → 打包
  → 分批发货
  → 可能发生售后、退回、补发或改包装
```

兼职人员可承担制作、捏毛装袋、打包、发货等不同工序；其中制作与捏毛装袋有提成，打包和发货只有时薪。兼职的工作时间较自由，系统不连接打卡机，因此工资要同时提供排班口径和考勤口径作为参考，最终实发金额由负责人确认。

本方案不以最小改动为原则。当前系统中的订单、排班、制作记录和成本报表均为测试数据，不需要保留或兼容。本方案以真实业务的可追溯性、职责清晰和后续可扩展性为优先，建立 V2 数据模型与模块边界。

## 2. 已验证的当前实现

### 2.1 当前可复用基础

以下能力已有实现，可保留业务概念或在 V2 中重新接入：

- `customers`、`products`、`orders`、`order_items` 已支持客户、商品及一单多商品。
- `payments` 已支持一笔订单下多次收款和退款。
- `shipments`、`shipment_items` 已支持按订单商品分批发货。
- `products` 已保存标准制作分钟、制作单件提成、胶水/包装/配饰/替换袋/捏毛装袋/缝边等成本字段。
- `workers` 和 `worker_wage_history` 已提供兼职人员与时薪历史基础。
- 本地 SQLite、附件管理、备份与恢复、审计日志均已具备基础设施。

### 2.2 当前结构不能继续作为 V2 核心的原因

| 当前结构 | 当前职责 | 与真实业务的冲突 |
| --- | --- | --- |
| `shifts` | 排班，同时依赖开始/结束时间 | 兼职时间自由，固定上下班时间不是可靠工资依据 |
| `shift_tasks` | 排班、制作数量、完成情况、人工成本、提成混在一条记录 | 无工序概念，无法支持制作、捏毛、打包、发货，也无法隔离质检与结算 |
| `production_records` | 记录实际分钟、合格/返工/报废及成本 | 不能表达次日质检、在制品流转、售后补发与不合格扣款依据 |
| `WorkerSettlementReport` | 按日期汇总统计 | 只是报表，不是可确认、可实发、可顺延的工资结算单 |
| `payments` | 订单收退款 | 无日常收入、日常支出、私人垫付和报销能力 |
| `products` + 订单成本 | 产品核算成本与实际现金支出相邻且容易混淆 | 无法形成按实际付款日期统计的月度经营结果 |
| `src/renderer/pages/app.tsx` | 导航、页面、表单、请求和状态大量集中 | 再叠加财务、结算、售后会持续失去可维护性 |
| `src/shared/contracts.ts` | 全部共享类型集中 | V2 多领域契约继续堆叠会导致修改范围失控 |

## 3. 目标行为

V2 应成为一套围绕订单履约事实运转的单机工作室系统：订单商品在固定四道工序之间按可追溯数量流转；工作任务、完成申报与次日质检彼此独立；工资结算同时呈现排班和考勤两套参考结果，但由负责人确认最终实发；订单资金与日常财务按实际收付款日期统计；售后、金额调整和例外处理保留负责人决定权及完整记录。

系统以独立的 V2 数据文件承载全新测试数据，不迁移 V1 业务记录；所有已确认的质检、工资与财务事实均可追溯，不能被静默覆盖。

## 4. 范围与非目标

### 3.1 本方案范围

1. 订单金额调整、多笔收退款、订单变更、分批发货和售后记录。
2. 制作、捏毛装袋、打包、发货四道固定工序的工作安排、任务、完成、质检和数量流转。
3. 期初在制品录入，用于系统中途上线。
4. 制作与捏毛装袋的不合格扣款、返工、售后补发和扣款顺延。
5. 兼职工资结算的排班口径、考勤口径、最终实发金额与财务自动记账。
6. 日常收支、动态类目、私人垫付、完整报销和月度财务首页。
7. 订单核算成本与真实财务流水的口径分离。
8. 页面、共享契约、主进程服务和仓储结构按领域拆分。
9. V2 使用全新数据存储，不迁移 V1 测试业务数据。

### 3.2 明确不做

- 原料、包装物、配饰等库存数量管理。
- 原料采购成本按订单、数量、工时或金额的自动分摊。
- 银行、微信、支付宝或打卡机自动同步。
- 公账收入账户管理、公账余额、完整银行对账和会计凭证。
- 预计收款计划、到期提醒和自动催款。
- 物流轨迹、扫码出入库、快递接口。
- 可自定义工序、可任意调整工序顺序的工作流引擎。
- 复杂售后审批、系统自动定责、自动退款、自动补发或自动扣薪。
- 兼职部分报销、一次垫付拆成多次报销。

## 5. 总体原则与口径

### 4.1 三套口径必须分开

| 口径 | 用途 | 事实来源 | 不与其混用的内容 |
| --- | --- | --- | --- |
| 产品/订单核算成本 | 判断订单做下来是否划算 | 产品成本快照、已确认的工序任务及售后核算成本 | 日常采购流水、房租水电、实际工资付款 |
| 兼职工资参考 | 帮负责人判断应发工资 | 排班分钟或人工录入的考勤总分钟、合格提成、扣款依据 | 负责人最终实发金额 |
| 财务经营收支 | 查看某月实际收了多少、花了多少 | 按实际收款/付款日期的财务流水 | 产品预计成本、订单公共成本分摊 |

### 4.2 系统计算与负责人决定的边界

系统负责：

- 保存业务事实；
- 计算数量、应收、工资参考、扣款和汇总；
- 给出必要的数量不足、超量、重复结算、重复报销等明确提示；
- 保存每个数字的来源。

负责人负责：

- 创建和调整订单；
- 安排任务及额外预留时间；
- 确认质检结果；
- 决定返工、补发、售后处理和客户收费；
- 输入考勤总时长；
- 输入工资最终实发金额、付款时间和备注；
- 决定是否进行负责人调整，并留下原因。

系统不得自动替负责人决定退款、补发、售后责任、最终工资或是否允许业务上的例外处理。

### 4.3 不可变事实与可调整事实

- 已确认的质检结果、已确认的工资结算、已发生的财务流水不直接覆盖修改。
- 发现错误时，通过冲正、工资调整、数量调整或新的订单金额调整留下新事实。
- 草稿状态的工作安排、任务、售后单和工资结算可以编辑或取消。
- 每个调整动作必须保存日期、原因和备注；自动动作还须保存来源记录 ID。

## 6. V2 数据初始化与 V1 处理

### 5.1 V2 不迁移 V1 测试数据

已确认当前订单、收款、排班、发货和相关历史均为测试数据，V2 不承担将旧 `payments`、`shifts`、`shift_tasks`、`production_records` 等数据转换成新模型的责任。

V2 采用新的数据文件与附件目录，例如：

```text
V1：yumi-studio.sqlite / attachments
V2：yumi-studio-v2.sqlite / attachments-v2
```

这样做的结果：

- V2 第一次启动就是空的正式业务库；
- V1 测试库不被自动删除，仍可作为回退参考；
- V2 的备份、恢复和附件只处理 V2 数据；
- 不需要在启动迁移中执行危险的 `DROP TABLE`；
- 正式录入前可由负责人从空库开始录入真实基础资料。

备份元数据中的数据库文件名和附件目录必须从当前 V2 存储配置读取，不再使用写死的 V1 文件名。

### 5.2 初始基础资料与期初在制品

上线顺序：

1. 新建真实的产品、客户、兼职人员、财务类目和垫付人。
2. 新建仍未结束的订单，并录入当前订单产品确认数量和初始确认金额。
3. 将系统启用当天已存在、但尚未走完流程的产品录入为期初在制品。
4. 期初在制品仅进入后续工序流转，不反推历史排班、历史工资、历史提成、历史不合格扣款或历史实际成本。

期初在制品字段：

- 订单；
- 订单产品；
- 数量；
- 当前阶段：待捏毛装袋、待打包、待发货；
- 录入日期；
- 备注。

## 7. 订单、金额与售后设计

### 6.1 订单与订单产品

订单保留客户、订单号、创建时间、备注、当前状态和产品明细。订单产品保留在订单创建或订单变更时的产品快照，至少包括：

- 名称、编码和规格；
- 客户单价；
- 原材料及包装等核算成本；
- 制作标准分钟；
- 制作单件提成；
- 制作不合格所需的单位胶水扣款成本。

产品后续被修改，不影响既有订单与既有任务的历史快照。

### 6.2 订单金额与内容变更

订单不再以可随意覆盖的 `receivable_cents` 作为金额事实来源。

#### 数据对象

- `order_amount_adjustments`：金额增减、日期、原因、备注。
- `order_change_records`：变更前/后的订单产品快照、说明、日期、可选关联的金额调整。

#### 派生规则

```text
当前订单金额 = 初始确认金额 + 全部金额调整之和
当前待收金额 = 当前订单金额 - 累计收款 + 累计退款
实际净收款 = 累计收款 - 累计退款
```

#### 操作规则

- 增加产品、改数量、加配饰、换包装、改版等内容变化，通过订单变更记录保存前后快照。
- 负责人手工填写确认后的金额增减；系统不根据产品变化自动推断金额。
- 订单金额减少而仍有待收时，系统仅减少后续待收，不生成退款。
- 订单已经结清后再减少金额，由负责人手工登记退款；系统显示待收为负的风险提示，但不自动退款。
- 金额调整、收款和退款均不可通过修改订单总额静默覆盖。

### 6.3 统一订单收退款与财务流水

订单收款、退款和售后收费均从订单页面手工录入，但保存到统一的 `financial_entries` 中，不再维护独立的 `payments` 事实表。

订单资金记录字段：

- 方向：收入或支出；
- 业务类型：订单收款、订单退款、售后收费；
- 收款分类：定金、阶段款、尾款、售后收费、其他；
- 金额；
- 实际发生日期；
- 收款方式；
- 备注；
- 可选凭证附件；
- 订单 ID。

约束：

- 每笔订单资金记录只能关联一个订单；
- 一个订单可有多笔收款与退款；
- 金额必须大于 0；
- 退款不删除或修改原收款；
- 已保存记录的金额或日期需要纠正时，使用冲正和新记录，保持财务可追溯。

### 6.4 分批发货

保留现有“订单下多次发货、一次发货包含多个订单产品”的业务概念，V2 重新关联新的订单产品和履约数量事件。

发货记录包含：

- 订单；
- 发货日期；
- 本次商品与数量；
- 可选快递/单号；
- 可选备注；
- 由负责人手工创建。

订单产品展示：确认数量、已发货数量、待发货数量。发货不要求对应收款，也不阻止未结清订单发货。

### 6.5 售后处理单

售后采用轻量记录，不做规则穷举或自动审批。

`after_sales_cases` 包含：

- 订单；
- 可选关联发货批次；
- 发生日期；
- 原因说明；
- 客户提出的处理要求；
- 责任归属：工作室、客户、协商处理；
- 处理内容；
- 状态：处理中、已完成、已取消；
- 客户收费说明；
- 售后核算成本；
- 备注。

规则：

- 客户收费为 0 时仍允许录入售后核算成本。
- 客户实际付款仍由负责人在订单中登记售后收费财务流水；售后单本身不等同已收款。
- 售后核算成本用于订单直接成本参考，不生成日常财务支出，也不与材料采购流水重复计入月度经营支出。
- 质量问题补发、换袋子、加封边、加配饰等操作，由负责人从售后单创建后续任务或发货；系统不自动定责、自动收费或自动创建任务。
- 产品退回后，负责人可选择将数量以“负责人调整”进入待打包或待发货阶段，或直接新建售后补发任务；系统要求填写处理说明，但不限制具体业务路径。

## 8. 多工序履约与数量流转

### 7.1 固定工序

V2 固定四道工序：

```text
制作 → 捏毛装袋 → 打包 → 发货
```

不提供自定义工序和工序排序。工资、质检、数量流转和提成规则依赖这些明确含义，固定工序能避免后续规则失真。

### 7.2 工作安排与工序任务

#### `work_assignments`

表示负责人对兼职人员的某日工作安排：

- 兼职人员；
- 日期；
- 工序；
- 状态：草稿、已安排、已取消、已完成；
- 备注。

不保存必填的开始时间和结束时间。

#### `process_tasks`

表示工作安排中实际做的业务任务：

- 工作安排 ID；
- 工序；
- 订单产品；发货辅助任务可不关联具体订单产品；
- 任务来源：正常生产、不合格返工、售后补发、其他负责人安排；
- 计划数量；制作、捏毛装袋、打包为必填，发货辅助任务可为空；
- 计划分钟；
- 制作额外预留分钟；
- 状态：待完成、待质检、已确认、已取消；
- 当时适用的时薪、制作提成/捏毛提成和必要成本快照。

一个工作安排可以包含多个同工序任务；工作安排的排班总分钟由其中任务计划分钟与额外预留分钟之和派生，不单独填写第二个相互矛盾的总时长。

#### 计划时长规则

| 工序 | 计划数量 | 计划分钟 | 计件规则 |
| --- | --- | --- | --- |
| 制作 | 必填 | `产品标准分钟 × 计划数量 + 负责人额外预留分钟`，负责人可调整预留 | 产品快照中的制作单件提成 |
| 捏毛装袋 | 必填 | 负责人手工填写 | 当前统一捏毛单件提成快照 |
| 打包 | 必填 | 负责人手工填写 | 无提成 |
| 发货 | 可选 | 负责人手工填写 | 无提成 |

系统显示兼职人员某日和某周期的已排计划分钟，用于工作量与饱和度判断；不以此阻止负责人安排业务例外。

### 7.3 完成、质检与工序推进

制作和捏毛装袋需要“完成”与“质检”两个独立事实：

```text
待完成
  → 兼职提交完成数量
  → 待质检
  → 负责人确认合格/不合格
  → 合格数量进入下一阶段
```

#### `process_results`

记录兼职完成事实：

- 工序任务；
- 完成数量；
- 制作实际分钟，可选，仅用于生产分析；
- 提交日期；
- 备注。

实际制作分钟不能替代排班分钟或考勤分钟。

#### `quality_inspections`

记录负责人通常于次日完成的质检：

- 工序任务；
- 合格数量；
- 不合格数量；
- 检查日期；
- 原因备注；
- 是否需要重新安排；
- 备注。

校验：合格数量加不合格数量必须等于该次提交完成数量；每个完成记录只可确认一次质检。

工序推进：

- 制作合格 → 待捏毛装袋；
- 捏毛装袋合格 → 待打包；
- 打包完成 → 待发货；
- 发货记录确认 → 已发货。

打包不进入按件质检规则；负责人确认打包完成后直接推进。发货以负责人创建的分批发货记录为准，发货辅助任务仅服务排班与工资参考，不替代发货事实。

### 7.4 履约数量事件

`fulfillment_events` 是订单产品各阶段数量的唯一流转来源。事件至少包括：

- 期初在制品；
- 制作质检合格；
- 捏毛装袋质检合格；
- 打包完成；
- 发货；
- 负责人数量调整；
- 售后退回处理；
- 售后补发完成。

每条事件保存：订单产品、数量、来源阶段、目标阶段、业务来源类型、来源记录 ID、发生日期、备注。

各阶段可用量由事件聚合派生，不在订单或订单产品上维护可被覆盖的累计数量字段。

#### 数量保护与负责人例外

- 完成或质检确认时，不允许让来源阶段可用量变为负数。
- 创建任务时，系统提示计划数量超过当前可用量或订单需求的风险，但不替负责人决定是否排班。
- 如果负责人确定存在系统外数量、退回货或其他例外，先创建带原因的负责人数量调整事件，再完成后续任务。
- 已确认的数量事件不直接删除；发生录错时，用反向调整事件修正。

这既保证数量账不出现静默负数，也保留负责人处理真实例外的自由。

### 7.5 不合格、返工与售后补发

#### 制作不合格

质检确认制作不合格后：

1. 不合格数量不产生下一工序可用量；
2. 自动创建扣款依据；
3. 不合格品如需继续处理，由负责人新建来源为“不合格返工”的制作任务；
4. 返工任务合格后，按一条新的正常完成事实计入时薪参考和制作提成。

#### 捏毛装袋不合格

与制作相同：不进入打包，自动形成扣款依据，负责人新建返工任务；返工合格后按新任务正常计薪与计件。

#### 售后补发

售后处理单明确需要补发时，负责人建立来源为“售后补发”的制作任务。补发任务合格后正常进入工序流转，且按正常规则形成工资参考与订单核算成本。是否向客户收费由负责人另行登记订单售后收费。

## 9. 兼职工资结算

### 8.1 结算单而非统计报表

现有 `WorkerSettlementReport` 只保留为旧实现参考，V2 建立独立的 `worker_settlements`：

- 兼职人员；
- 结算开始/结束日期；
- 排班总分钟；
- 考勤总分钟；
- 排班口径工资；
- 考勤口径工资；
- 合格提成；
- 本期新扣款；
- 历史顺延扣款；
- 本期实际扣除；
- 本期继续顺延；
- 其他调整；
- 最终实发金额；
- 实际付款日期；
- 负责人备注；
- 状态：草稿、已确认、已调整。

结算周期不固定。负责人可以创建任意起止日期的结算单。

### 8.2 两套工资参考口径

系统同时计算并展示：

```text
排班口径工资 = 排班总分钟 × 时薪 ÷ 60 + 合格提成 - 可扣款 + 其他调整
考勤口径工资 = 考勤总分钟 × 时薪 ÷ 60 + 合格提成 - 可扣款 + 其他调整
```

两种口径中：

- 合格提成、扣款、其他调整相同；
- 只有时薪对应的工作总分钟不同；
- 考勤分钟由负责人结算时根据打卡机手工填写总分钟，可选填写说明；
- 排班分钟来自已确认任务的计划分钟及制作额外预留分钟；
- 系统不要求录入系统内的开始和结束打卡时间。

负责人最终填写实际发放金额、实际付款日期和备注。系统不自动选择排班口径或考勤口径，也不覆盖负责人填写的金额。

### 8.3 时薪与提成快照

任务创建时保存适用快照：

- 兼职人员当日生效时薪；
- 制作任务的产品制作单件提成；
- 捏毛装袋任务的统一单件提成；
- 制作任务的不合格单位胶水扣款成本；
- 任务计划数量、计划分钟和制作额外预留分钟。

当前所有兼职人员时薪相同，但数据模型始终按人员和任务快照计算，以支持未来不同人员时薪而不重写历史。

### 8.4 提成规则

| 工序 | 合格结果 | 不合格结果 | 返工/补发合格结果 |
| --- | --- | --- | --- |
| 制作 | 合格数量 × 产品制作提成 | 不计提成，并产生对应扣款依据 | 按新任务正常计提成 |
| 捏毛装袋 | 合格数量 × 统一捏毛提成 | 不计提成，并产生对应扣款依据 | 按新任务正常计提成 |
| 打包 | 无提成 | 不纳入本期不合格扣款模型 | 无提成 |
| 发货 | 无提成 | 不纳入本期不合格扣款模型 | 无提成 |

### 8.5 不合格扣款依据

`worker_deduction_records` 每条必须关联原始任务和质量结果，保存：

- 兼职人员；
- 原工作安排和工序任务；
- 订单、订单产品；
- 不合格数量；
- 扣除提成；
- 扣除时薪；
- 扣除胶水成本；
- 总扣款；
- 已扣金额；
- 剩余顺延金额；
- 状态。

#### 制作不合格公式

```text
扣除制作提成 = 不合格数量 × 任务快照中的制作单件提成
扣除时薪 = 不合格数量 × 产品标准分钟 × 任务快照时薪 ÷ 60
扣除胶水 = 不合格数量 × 任务快照中的单位胶水扣款成本
```

#### 捏毛装袋不合格公式

```text
不合格应扣分钟 = 任务计划分钟 ÷ 任务计划数量 × 不合格数量
扣除捏毛提成 = 不合格数量 × 任务快照中的捏毛单件提成
扣除时薪 = 不合格应扣分钟 × 任务快照时薪 ÷ 60
```

所有金额以分保存；涉及除法时按分四舍五入，并在扣款明细中保存最终计算值，避免后续规则修改导致历史金额变化。

### 8.6 扣款顺延

扣款不会把工资参考结果计算为负数。

- 结算单先汇总历史未扣金额和本期新扣款。
- 系统以排班口径的扣前应发作为默认可抵扣上限；这是排班包含负责人额外预留、且可追溯到任务的主要参考口径。
- 若负责人需要以不同金额实际抵扣，可在结算草稿中填写“实际扣除金额”并说明原因；该值不得超过当前未扣总额，也不得超过负责人决定用于本期抵扣的金额。
- 未抵扣部分按扣款明细的发生顺序保留为顺延扣款，自动带入下一次结算。
- 最终实发金额是实际付款事实，不自动反向改写扣款余额；负责人如需改变扣款处理，必须修改草稿中的实际扣除金额并留下备注。

这一设计同时满足“负责人决定实际发多少”和“扣款不能无缘无故消失”的要求。

### 8.7 结算确认与财务联动

结算确认前必须填写：

- 最终实发金额；
- 实际付款日期；
- 备注，可为空。

确认操作使用单个数据库事务：

1. 锁定本结算单涉及的任务、扣款与快照；
2. 写入最终实发金额和扣款分配；
3. 将结算状态改为已确认；
4. 创建一笔来源为 `wage_payment` 的财务支出；
5. 写入审计日志。

重复确认必须被拒绝，不得产生两笔工资支出。

结算确认后发现错误时，原结算单不直接覆盖。负责人创建工资调整，类型为补发、追回、扣款修正或其他调整；每条已确认调整同样创建一笔关联的财务流水。

## 10. 财务管理

### 9.1 财务流水

`financial_entries` 是所有真实发生收付款的唯一事实来源。

字段包括：

- ID；
- 方向：收入、支出；
- 来源：手工录入、订单资金、工资结算、工资调整、报销付款；
- 财务类目；
- 金额；
- 实际发生日期；
- 订单 ID，可为空；
- 工资结算/调整 ID，可为空；
- 是否计入经营结果；
- 支出付款来源：公账支出、私人垫付；收入无需选择账户来源；
- 垫付人 ID，仅私人垫付时必填；
- 备注；
- 可选附件；
- 创建/更新时间。

约束：

- 金额必须大于 0；
- 订单资金记录必须关联一个订单；
- 工资付款必须关联一个已确认结算或调整；
- 私人垫付必须关联启用的垫付人；
- 报销付款必须关联一笔待报销私人垫付；
- 自动生成来源的流水不能在财务页面直接修改或删除；通过原业务单据的调整流程修正。

### 9.2 动态财务类目

`financial_categories`：

- 名称；
- 方向：收入、支出；
- 是否系统内置；
- 是否启用；
- 创建和修改时间。

初始系统类目：

| 收入 | 支出 |
| --- | --- |
| 订单收款 | 材料采购 |
| 售后收费 | 包装采购 |
| 其他收入 | 兼职工资 |
|  | 快递物流 |
|  | 房租 |
|  | 水费 |
|  | 电费 |
|  | 物业 |
|  | 设备 |
|  | 日常杂费 |
|  | 订单退款 |
|  | 其他支出 |

负责人可以新增、改名、停用手工类目。已使用类目不能删除。系统自动使用的类目，例如兼职工资和订单退款，不允许停用或删除。

### 9.3 手工收入与支出

除工资确认自动产生的工资支出外，其余收支由负责人手工新增：

- 日常收入：实际收款日期、金额、收入类目、备注；如属于订单，使用订单内的收款入口；
- 公账支出：实际付款日期、金额、支出类目、备注；
- 私人垫付：实际付款日期、金额、支出类目、垫付人、备注。

日常支出不关联订单。材料采购、包装采购、房租、水电、物业、设备等只进入月度经营统计，不进入订单成本，避免与产品成本快照重复计算。

### 9.4 垫付人与报销

`advance_payers` 维护可选择的垫付人：姓名、启用状态、备注。

`expense_reimbursements` 记录私人垫付的完整报销：

- 原私人垫付财务流水；
- 垫付人；
- 报销日期；
- 报销金额，必须等于原垫付金额；
- 备注；
- 自动生成的报销付款财务流水。

状态仅有：待报销、已报销。

规则：

- 新建私人垫付时，只能选择已建立且启用的垫付人；不得临时输入姓名。
- 每笔垫付只能完整报销一次；不支持部分报销。
- 私人垫付在垫付日期已经计入经营支出。
- 报销付款记录为真实公账付款，但 `counts_as_operating_result = false`，不得再次减少经营结果。
- 垫付人停用后仍可查询历史待报销、已报销数据，不能用于新垫付。

### 9.5 月度财务首页

默认按月份，以每笔流水的实际发生日期统计，首期固定展示：

```text
收入
- 经营支出
= 经营结果

待报销金额
```

定义：

- 收入：当月所有 `direction = income` 且计入经营结果的流水；
- 经营支出：当月所有 `direction = expense` 且计入经营结果的流水；
- 经营结果：收入减经营支出；
- 待报销金额：截止查询日，全部待报销私人垫付金额总和，不受月份筛选限制时须明确显示“截至当前”。

页面还提供：

- 当月收支流水列表；
- 按类目汇总；
- 私人垫付待报销清单；
- 已报销记录。

不显示公账余额，原因是收入不区分进入公账还是私人账户，计算公账余额会产生虚假精确性。

### 9.6 订单视图与财务视图的关系

订单页展示：

- 初始金额、金额调整、当前订单金额；
- 累计收款、累计退款、实际净收款、当前待收；
- 产品与已确认工序形成的核算成本；
- 售后核算成本；
- 订单直接利润参考。

月度财务页展示的是实际收付款，包含订单收款、工资、采购和共同经营费用。

两者无需相等：

```text
订单直接利润参考 = 订单净收款 - 订单核算成本
月度经营结果 = 月度实际收入 - 月度实际经营支出
```

不分摊房租、水电、物业和公共材料到订单；订单页不因日常材料采购重复增加成本。

### 11.3 关键调用链

#### 创建订单资金记录

```text
订单详情录入收款/退款
→ orders composable
→ window.yumi.orders.recordFundEntry(input)
→ order IPC
→ OrderService.recordFundEntry
→ FinanceRepository 在事务内写 financial_entries + audit_logs
→ 返回最新订单资金汇总和财务摘要
```

失败分支：订单不存在、金额非正、分类非法、日期无效、重复提交时返回明确领域错误；前端保留表单内容并显示错误，不重复插入。

#### 确认质检

```text
生产履约页确认合格/不合格
→ fulfillment composable
→ window.yumi.fulfillment.confirmInspection(input)
→ FulfillmentService.confirmInspection
→ 事务内写 quality_inspections、fulfillment_events、必要的 worker_deduction_records、audit_logs
→ 返回任务与订单产品最新阶段数量
```

失败分支：任务不存在、任务非待质检、数量不等于已提交数量、来源阶段不足、重复质检，均拒绝操作且不写入部分数据。

#### 确认工资结算

```text
工资结算页确认实发
→ settlements composable
→ window.yumi.settlements.confirm(input)
→ SettlementService.confirm
→ 事务内冻结结算明细、分配扣款、确认结算、写工资 financial_entry、写审计
→ 返回已确认结算单和财务流水摘要
```

失败分支：结算已确认、任务已被其他结算占用、最终金额非法、付款日期无效、扣款分配超额，全部回滚；不能生成孤立工资支出。

#### 标记私人垫付已报销

```text
财务页点击已报销
→ finance composable
→ window.yumi.finance.confirmReimbursement(input)
→ FinanceService.confirmReimbursement
→ 事务内写 expense_reimbursements、报销付款 financial_entry、审计日志
→ 返回更新后的待报销汇总
```

失败分支：垫付不存在、不是私人垫付、已报销、金额不等于原垫付金额或日期无效，全部拒绝。

## 13. 并发、重复请求与数据一致性

应用为单电脑本地桌面软件，但仍需要防止双击和连续操作造成重复事实。

- 所有创建财务流水、确认质检、确认结算、确认报销、创建发货均使用 SQLite 事务。
- 质检记录对同一完成记录建立唯一约束。
- 工资结算明细对同一任务/扣款分配建立唯一归属约束；已纳入确认结算的任务不可再次纳入另一张结算。
- 私人垫付与报销建立一对一唯一约束。
- 工资结算与自动工资支出建立一对一唯一约束。
- 订单发货项以发货记录为事实来源；同一记录重复提交由前端禁用提交按钮和服务端幂等键共同避免。
- 所有负责人调整、冲正和取消操作保留审计日志，包含前后值、实体、来源和时间。

## 14. 订单核算成本规则

V2 将产品成本拆为“产品直接材料/包装等成本快照”和“工序人工核算成本”。

- 产品直接材料、包装、配饰、替换袋、缝边等仍取订单创建或变更时的产品快照。
- 制作与捏毛的人工核算成本取已确认工序任务的时薪和提成快照，不取负责人最后手填的工资实发金额。
- 工资最终实发金额用于财务真实支出；它可能包含负责人管理调整，无法可靠拆回单个订单，因此不强行分摊到订单。
- 售后单的售后核算成本作为订单直接成本调整项。
- 房租、水电、物业、公共材料采购等不进入订单成本。

因此：

```text
订单核算成本 = 产品直接成本 + 已确认工序人工核算成本 + 售后核算成本
订单直接利润参考 = 订单净收款 - 订单核算成本
```

该规则消除了当前产品成本、排班实际成本和真实工资付款互相覆盖的风险。

| 日常材料采购 | 进入月度经营支出，不自动挂订单，也不重复增加订单产品成本 |

## 18. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 大范围重构导致 V1、V2 逻辑交叉 | V2 使用独立数据库、独立 IPC 命名和按阶段替换的页面入口 |
| 真实业务规则被写死 | 固定必要工序，售后、最终实发、金额调整和负责人数量调整保留人工决定与备注 |
| 产品成本和现金支出重复计算 | 明确订单核算成本与财务经营收支两套口径；日常支出不关联订单 |
| 工资确认重复记账 | 结算和工资流水使用一对一约束与单事务确认 |
| 垫付报销重复计入经营成本 | 原垫付计入经营支出；报销付款保留现金事实但不计入经营结果 |
| 不合格扣款无法解释 | 每条扣款关联任务、质检、订单产品和具体三项金额 |
| 数量流转失真 | 以履约事件为唯一来源，禁止静默负库存，例外使用带原因的负责人调整 |
| 当前主页面继续膨胀 | 先拆分页面、composable、组件，再引入新领域页面 |
| V1 测试数据误删 | V2 使用新数据文件与附件目录，不做自动删除 |

## 19. 开放问题与变更规则

当前没有阻塞实施的未决业务规则。实施中不得自行扩大为原料库存、订单支出分摊、打卡机同步、可配置工序、收入账户区分或报销拆分等已排除能力。

如需改变以下已确认边界，必须先更新本方案并由负责人重新确认：固定四道工序；制作与捏毛装袋的不合格扣款公式；报销仅支持整笔报销；财务日常支出不关联订单；工资最终实发由负责人填写。

## 20. 方案确认结论

已确认采用 **方案 C：重构核心履约模型**，并明确：

- 以最优业务模型为原则，不以最小改动为原则；
- 当前数据均为测试数据，V2 不做旧业务数据迁移；
- V2 开发分支为 `codex/v2`；
- 订单、生产履约、工资结算、财务流水必须分为独立领域；
- 系统计算参考，负责人对售后、例外和最终工资实发拥有最终决定权；
- 实施前先在本 OpenSpec 提案内确认阶段任务计划，未经实施授权不得修改业务代码。
