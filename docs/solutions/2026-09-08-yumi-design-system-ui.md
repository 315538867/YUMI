# YUMI 前端设计系统与界面重构方案

## 1. 目标与范围

本方案为 YUMI 捏捏工作室管理桌面应用重做前端视觉和交互组件系统。目标不是给现有页面换一层淡粉颜色，而是建立可持续使用的桌面经营工作台：品牌气质有手作工作室的温度，信息组织和操作效率则保持接近 Codex 桌面端的克制、清晰与高密度。

### 本次范围

- 仅支持浅色主题；不建设深色模式。
- 建立一套 YUMI 专属的颜色、排版、间距、圆角、阴影、状态色和图标规范。
- 统一所有按钮、输入框、数字输入、文本域、下拉选择、日期、日期范围、日期时间范围、弹窗、抽屉、标签、表格和空状态。
- 迁移订单、履约、工资、财务、报表、客户、商品、设置、排班、售后等全部现有业务页面。
- 保留已实施的 `improve-operational-ui-flow` 信息架构：列表、创建、详情和基础资料维护职责保持分离。
- 保留现有 V2 领域规则、IPC 接口、数据模型、数据库事实与负责人裁量，不借 UI 重构改变业务决策。

### 不在本次范围

- 深色模式、移动端专属界面和响应式移动工作流。
- 库存、云同步、账号权限、自动工资决策或新业务模块。
- 修改 V2 数据库 schema、领域口径或主进程 IPC 契约。

## 2. 已确认的设计方向

### 2.1 品牌与工作台气质

采用“手作工作室”方向：保留经营工作台的稳定结构，同时通过柔和的轮廓、留白、淡粉识别色和品牌细节表达 YUMI 的手作气质。

设计原则：

1. 粉色是品牌识别、选中态和主操作色，不是大面积页面底色。
2. 内容读取优先于装饰；订单、履约、工资与财务数据必须可快速扫描。
3. 页面避免无意义卡片化；只有独立的事实组、概览、表格和浮层使用面板。
4. 一页最多突出一个实体级主操作；危险操作不得使用主色伪装成常规确认。
5. 所有可操作控件必须是统一的 YUMI 组件，业务页面不直接决定其视觉样式。

### 2.2 视觉令牌

| 类别 | 令牌 | 值 | 用途 |
| --- | --- | --- | --- |
| 画布 | `--yumi-canvas` | `#F9F6F7` | 应用内容画布与浅背景 |
| 表面 | `--yumi-surface` | `#FFFDFD` | 面板、表格、浮层 |
| 主文字 | `--yumi-ink` | `#30272B` | 标题与主要业务文字 |
| 次文字 | `--yumi-muted` | `#7F7177` | 说明、辅助信息 |
| 分割线 | `--yumi-border` | `#EADFE3` | 常规边界与表格行分隔 |
| 主色 | `--yumi-brand` | `#C4567C` | 主按钮、已选端点、关键选中态 |
| 主色浅层 | `--yumi-brand-soft` | `#FAE6ED` | 选中行、轻提示、状态标签 |
| 主色极浅层 | `--yumi-brand-subtle` | `#FFF4F7` | 悬停、弱背景与提示区 |
| 成功 | `--yumi-success` | `#2D8562` | 已完成、已结清等正向状态 |
| 警告 | `--yumi-warning` | `#AF712D` | 待处理、临近或需关注状态 |
| 危险 | `--yumi-danger` | `#BC4D58` | 删除、作废、异常状态 |
| 信息 | `--yumi-info` | `#7266AA` | 进行中和中性流程状态 |

排版固定为：页面标题 `28/36, 750`；区块标题 `18/26, 700`；卡片与表格标题 `15/22, 700`；业务正文 `14/21, 450`；辅助文字 `12/18, 450`。字体优先使用 `Inter`、`PingFang SC`、`Microsoft YaHei`，不使用会降低数据可读性的装饰字体。

间距采用 4px 基准：页面边距 32px、区块间距 20px、面板内部 20px、组件内间距 12px。内容面板圆角 16px，输入和按钮圆角 8px，标签与筛选项采用胶囊形；阴影只用于浮层和关键面板。

## 3. 组件规范

### 3.1 按钮与状态

| 组件 | 样式 | 适用范围 |
| --- | --- | --- |
| 主按钮 | 主色实心、白字、8px 圆角 | 新建订单、保存、确认、应用筛选等当前页面唯一主操作 |
| 次按钮 | 白底、细描边 | 导出、次级确认、辅助操作 |
| 文字按钮 | 透明背景、深粉文字 | 取消、返回、查看全部等低风险操作 |
| 危险按钮 | 浅红底、危险色文字 | 删除、作废、不可逆操作；需配合二次确认 |
| 状态标签 | 浅色底 + 状态色文字 | 待确认、进行中、待处理、已完成、需处理 |

加载、禁用、悬停、键盘焦点和错误态均需要在组件层定义，页面不得自行拼接不一致的状态色。

### 3.2 下拉选择器

不再使用原生 `<select>`。

- 少量固定选项使用常规选择器：触发框高度 40px；下拉浮层紧贴触发框，间距 6px；选项高度 36px。
- 客户、商品、订单等会增长的数据使用可搜索选择器：顶部显示搜索框，可按名称或编号筛选。
- 当前选中项使用淡粉底、品牌色文字和对勾；悬停项使用极浅粉底。
- 列表最大高度 288px，超出后在浮层内部滚动；空间不足时自动向上展开。
- 在上下文合理时，底部显示“＋ 新建客户”“＋ 新建商品”等入口，不要求用户退出当前录入任务。
- 支持焦点、上下箭头、回车确认、Esc 关闭、点击外部关闭。

### 3.3 日期、时间与范围选择器

不再使用浏览器原生 `date`、`month`、`time` 或 `datetime-local` 控件。

| 场景 | 组件 | 规则 |
| --- | --- | --- |
| 交期、付款日、发货日、发生日期 | `YumiDatePicker` | 月历单选；今天为粉色描边，已选日期为主色实心；显示格式统一为“2026 年 9 月 12 日” |
| 报表、流水、订单筛选 | `YumiDateRangePicker` | 开始/结束端点为主色，区间为连续淡粉；提供本周、本月、上月快捷范围；跨月时桌面端可显示双月 |
| 排班开始与结束时段 | `YumiDateTimeRangePicker` | 明确开始/结束日期时间，显示预计时长；结束早于开始时禁止确认并提示 |
| 仅需精确时刻 | `YumiDateTimePicker` | 月历与时间面板并置；常用时间快捷选择，另可输入精确时间 |

日期范围用于查找与统计；日期时间范围仅用于真正存在时段意义的实体（例如排班），不得为了视觉统一而增加业务录入负担。

### 3.4 浮层、弹窗与抽屉

- 下拉、日期和轻量确认使用 `Popover` 浮层，白色表面、1px 描边、11px 圆角、低对比阴影。
- 简单资料的新建或编辑（客户、商品、人员、分类）使用右侧抽屉或居中弹窗。
- 订单、结算等长表单进入专用工作区，不以抽屉替代完整业务编辑界面。
- 所有浮层支持 Esc 关闭、点击外部关闭、焦点回归触发控件；有未保存内容的长表单在关闭前提示。

### 3.5 经营列表、表格、空状态与图标

- 订单、履约待办、工资结算和财务流水默认使用 `YumiBusinessList` 经营列表，而不是传统数据表格或卡片墙。每一行是连续记录：左侧为状态细色条或状态点，中间按“订单/记录主标题 → 客户、产品、数量等辅助事实”组织，右侧固定承载状态/进度、金额或关键数值、最近更新时间与进入详情入口。
- 经营列表使用行分隔与留白保持连续感；悬停或键盘选中时使用淡粉背景和左侧品牌色标记，不依赖深色填充或一行一个厚重卡片。点击整行进入详情，行内仅保留不影响主路径的轻量快捷操作。
- `YumiDataTable` 只用于横向精确对比有价值的场景，例如月度财务汇总、统计报表、需要同时比较多个指标的清单；它不作为订单等日常经营记录的默认呈现方式。
- 行操作默认使用图标加文字或“更多”菜单；危险操作不直接放在每行主视觉位置。
- 空状态提供当前页面的说明和下一步操作，例如“暂无待处理履约产品”与“创建订单”。
- 图标统一采用 Lucide 线性图标，默认 16px，永远辅助文字而不取代有歧义的文字操作。

## 4. 页面模式与信息架构

已实施的操作流继续有效，但统一使用以下页面模式。

### 4.1 列表工作台

适用于订单、履约待办、工资结算、财务流水、客户、商品和人员资料。

页面顺序固定为：面包屑 → 页面标题与说明 → 唯一主操作 → 筛选/搜索 → 数据列表或概览。默认职责是“找和看”，不长期并置复杂新建表单。

订单、履约待办、工资结算和财务流水采用连续的经营列表：状态线索在左，记录主次信息居中，状态/进度、金额与更新时间在右；点击整行进入详情。筛选项以状态胶囊、时间范围与搜索为主。客户、商品、人员等基础资料可按信息密度选择经营列表或数据表格；报表仅在需横向比较指标时使用数据表格。

### 4.2 详情与操作工作台

适用于订单详情、履约处理、结算单详情与售后处理。

页面优先显示关键事实、进度和记录；新增发货、补充收款、售后处理、确认工资等变更动作放在对应事实区块或弹窗。详情页可明确返回列表，但不做强制向导。

### 4.3 创建与编辑工作区

- 客户、商品、人员、分类等简单主数据：通过抽屉或弹窗录入，成功后回到资料列表。
- 订单、结算等复杂表单：进入独立创建工作区，避免与列表同屏堆叠。
- 负责人可随时取消创建或返回列表；界面不强制把负责人锁进线性流程。

## 5. 技术架构与迁移方式

### 5.1 组件边界

在 `/Volumes/code/YUMI/src/renderer/` 内建立专属 UI 层，建议目录为：

```text
components/ui/
  button/
  field/
  select/
  date-picker/
  dialog/
  sheet/
  status-tag/
  business-list/
  data-table/
  empty-state/
  page-header/
styles/
  tokens.css
  base.css
  components.css
  pages.css
```

每个 UI 组件负责视觉令牌、交互状态、键盘支持与无障碍语义；业务页面只传递值、选项、加载状态、错误和业务回调。

### 5.2 UI 库策略

实际实现移除了 `@radix-ui/themes` 及其默认样式，不再将主题库作为交互能力的间接来源。YUMI 组件层直接依赖 `@radix-ui/react-alert-dialog`、`@radix-ui/react-dialog`、`@radix-ui/react-popover` 与 `@radix-ui/react-select`，统一接管 Dialog、Popover、Select、焦点管理和键盘交互；业务页面不直接暴露 Radix 默认视觉。

日历与范围能力通过直接依赖 `@daypicker/react` 实现，职责限于日期网格、月份切换和键盘日期导航；视觉、中文格式化和业务限制由 YUMI 组件层管理。

### 5.3 迁移顺序

这是一个提案内部的分阶段实施，不拆分为多个互相脱节的 UI 方案：

1. **设计系统基础**：定义令牌；建立按钮、字段、下拉、日期与范围、浮层、抽屉、标签、经营列表、数据表格和空状态组件；替换应用壳和全局样式。
2. **核心经营页面**：迁移订单、履约、工资、财务和报表，订单、履约、工资和流水优先落地经营列表；报表保留按需使用的数据表格，落实列表/详情/创建三种工作模式。
3. **基础资料与辅助模块**：迁移客户、商品、人员、排班、售后、设置与数字输入等组件。
4. **清理与验证**：移除业务页面中的原生选择与日期输入，清理无效样式覆盖，完成交互测试、类型检查、Lint、构建及桌面端人工检查。

实施前基线：7 个渲染层文件仍含原生选择器；8 个文件含日期或时间输入，共 15 个控件；15 个文件直接使用 `@radix-ui/themes`。实施后业务页面已改用 YUMI 选择和日期组件，`main.tsx` 不再加载 `@radix-ui/themes`。

## 6. 保持不变的业务边界

- 订单、履约、工资、售后、财务和报表的现有数据结构及接口不变。
- 售后责任、是否收费、排班、实际工资发放仍由负责人决定；组件只能呈现候选事实、计算结果和提示。
- 工资结算确认仍代表实际发放；负责人仍可在确认时输入实际工资金额和备注。
- 财务发生、垫付和报销口径保持既有 V2 规则；UI 仅改善录入、筛选和阅读。
- 上一轮已确认的“列表负责找和看、创建负责录入、详情负责后续处理、基础资料维护规则”继续作为页面设计前提。

## 7. 验收标准与测试矩阵

| 类别 | 验收 |
| --- | --- |
| 视觉一致性 | 所有业务页使用同一色板、字号、间距、按钮和状态标签；无系统原生下拉、日期或时间控件残留 |
| 关键交互 | 下拉支持搜索、键盘和点击外部关闭；日期、日期范围、日期时间范围的边界与格式符合规范 |
| 页面结构 | 订单、履约、工资结算和财务流水使用经营列表；报表仅在需要横向比较时使用数据表格；各页面符合对应列表/详情/创建模式，不重新出现列表与复杂表单长期同屏 |
| 业务回归 | 原有 V2 IPC、数据校验、负责人裁量、工资与财务口径保持有效 |
| 自动验证 | 新增 UI 组件测试和关键页面渲染/交互测试；通过类型检查、Lint、构建和 OpenSpec 严格校验 |
| 人工验证 | 在 Electron 桌面端检查导航、空状态、表单、浮层、弹窗、长列表滚动、键盘焦点和主要业务路径 |

## 8. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 视觉重构破坏成熟业务交互 | 组件层只接管呈现与控件交互；领域计算、IPC 和数据服务保持不动，并对关键页面做回归测试 |
| Radix 默认视觉残留 | 页面不得直接使用默认组件；通过 YUMI 包装层和审查规则逐页消除直接依赖 |
| 日期/范围交互复杂 | 按单日期、日期范围、日期时间、日期时间范围四个明确场景实现，避免一个万能控件承担全部场景 |
| 重构范围过大 | 在同一 OpenSpec 提案内按基础组件、核心经营页、辅助模块、验证四阶段执行；每阶段完成后做可运行验证 |
| 打包环境的原生依赖波动 | UI 验证优先使用前端定向测试、类型检查、Lint 和构建；现有 `better-sqlite3` 本机绑定问题单独记录，不通过修改业务代码掩盖 |

## 9. 与现有 OpenSpec 的关系

`improve-operational-ui-flow` 已于提交 `a14709a` 实施，其职责是修正运营界面的信息架构。本方案不会撤回那些操作流规则，而是在其基础上建立统一视觉和组件层。

已于 2026-09-08 创建 OpenSpec 变更 `yumi-design-system-ui`。该变更引用本方案版本 `1.1`，已将本方案第 5.3 节的四个阶段拆成文件与符号级任务；实施完成后才回写本方案的实施状态、验证结果与实际偏差。

## 10. 实施结果（2026-09-08）

### 10.1 已落地内容

- 已建立 `tokens.css`、`base.css`、`components.css`、`pages.css` 四层样式体系，移除旧 `app.css` 和 `@radix-ui/themes` 默认主题入口；应用固定为浅色淡粉品牌工作台。
- 已实现并统一导出按钮、字段、状态标签、页面标题、常规/搜索选择器、单日期/月份/日期范围/日期时间/日期时间范围、弹窗、确认弹窗、抽屉、经营列表、数据表格和空状态组件。
- 已迁移订单、履约、工资、财务、报表、客户、商品、设置、人员、排班、售后和数字输入等现有渲染页面；日常运营记录使用经营列表，横向指标比较保留数据表格。
- 实际直接依赖为 `@daypicker/react`、`@radix-ui/react-alert-dialog`、`@radix-ui/react-dialog`、`@radix-ui/react-popover` 和 `@radix-ui/react-select`；不再依赖 `@radix-ui/themes`。

### 10.2 验证记录

- 渲染层回归：`npm --ignore-scripts test -- src/renderer` 通过 **14 个文件、46 项测试**，包含按钮、选择器键盘与焦点、日期触发器、浮层层级、弹窗、经营列表、页面结构、数字字段和售后面板。
- 工程校验：`npm run typecheck`、`npm run lint`、`npm run build`、`git diff --check` 和 `npx openspec validate yumi-design-system-ui --strict` 均通过。
