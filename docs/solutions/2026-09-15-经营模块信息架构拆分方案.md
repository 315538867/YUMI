# YUMI 经营模块信息架构拆分方案

> 方案日期：2026-09-15
> 方案状态：待确认
> 本文档只定义产品与界面方案，不包含代码实施。

## 1. 背景

当前经营报表页面同时承载了月度经营、商品产能风险、交期风险、订单核算、排班进度和工资结算等内容。虽然这些数据本身都有业务价值，但它们对应的是不同的用户任务，被连续堆叠在同一个页面后，产生了几个明显问题：

- 用户无法判断当前页面最重要的信息是什么。
- 核心经营结果和操作型明细表格争夺同一层级的注意力。
- 用户需要在收入、支出、订单、排班、产能、交期和工资之间频繁切换思维。
- 页面看起来像数据仓库，而不是帮助负责人做经营判断的工作台。
- 即使继续美化表格或增加统计卡片，也只能改善局部视觉，无法解决页面职责混杂的问题。

因此，本次方案不再以“优化一张报表”为目标，而是重新拆分经营模块的信息架构。

## 2. 核心结论

> 经营总览负责判断，业务页面负责调查和处理，完整表格只出现在对应的明细页面。

经营模块拆分为四个页面：

```text
经营
├── 经营总览
├── 资金与成本
├── 订单与交付
└── 工资结算
```

其中：

- **经营总览**：默认进入，只展示核心结论、比例和少量待处理事项。
- **资金与成本**：解释收入、支出和经营结果，提供资金明细追溯。
- **订单与交付**：统一承接订单、产能、交期和排班相关问题。
- **工资结算**：承接工资状态、结算和付款处理。

这四个页面按照“用户要做什么”拆分，而不是按照数据库表或接口拆分。

## 3. 设计目标

### 3.1 用户目标

用户打开经营模块后，应当能够：

1. 在 10 秒内知道本月收入、支出和经营结果。
2. 看懂经营支出主要花在哪里。
3. 判断当前是否存在需要马上处理的经营风险。
4. 从异常事项直接进入对应的处理页面。
5. 需要追溯时，再进入完整明细和表格。

### 3.2 体验目标

- 首屏先给结论，再给解释，最后给入口。
- 同一页面只服务一个主要问题。
- 表格是追溯工具，不是首页主叙事。
- 统计比例必须带明确分母，避免用户误读。
- 不为了“看起来像仪表盘”添加没有业务意义的趋势、雷达图或复杂图表。
- 不制造不存在的数据趋势，不把不同统计口径强行合并成一个利润数字。

## 4. 非目标

本次方案不包含以下内容：

- 不重新定义后端财务、订单或工资数据模型。
- 不改变现有实际收付款统计口径。
- 不将订单商品成本、售后成本直接并入现金经营结果。
- 不删除现有明细数据和导出能力。
- 不在没有真实历史数据的情况下增加趋势分析。
- 不通过增加更多卡片、图表或装饰来解决信息架构问题。
- 不在方案确认前继续修改业务代码。

## 5. 方案比较

### 5.1 方案 A：拆成四个业务页面（推荐）

```text
经营总览 / 资金与成本 / 订单与交付 / 工资结算
```

优点：

- 页面职责清晰。
- 每个页面都可以围绕一个业务问题设计。
- 表格可以自然下沉到明细页面。
- 后续增加功能时，不需要继续膨胀总览页。

代价：

- 导航入口增加。
- 用户需要在页面之间切换。

### 5.2 方案 B：一个页面内使用标签页

```text
经营报表
[总览] [资金与成本] [订单与交付] [工资结算]
```

优点：

- 导航入口较少。
- 改造集中在一个模块内。

问题：

- 标签页只能隐藏内容，不能真正解决页面职责问题。
- 用户仍然需要理解多个业务域。
- “总览”容易继续变成所有内容的容器。

### 5.3 方案 C：总览页配合抽屉查看明细

```text
经营总览
  └── 点击查看明细 → 右侧抽屉
```

优点：

- 首屏最干净。
- 适合快速查看少量记录。

问题：

- 订单核算、排班、工资结算等复杂任务不适合长期放在抽屉里。
- 表格空间有限，容易形成多层弹窗。
- 抽屉适合补充查看，不适合作为完整页面架构。

### 5.4 方案决策

采用方案 A，并吸收方案 C 的局部思路：

- 页面之间真正拆开。
- 总览页通过少量异常事项和入口跳转到明细页。
- 对于特别简单的补充信息，可使用局部展开或抽屉，但不承载完整业务表格。

## 6. 信息架构

### 6.1 导航名称

建议将原“经营报表”模块升级为“经营”，默认入口命名为“经营总览”。

```text
经营
├── 经营总览
├── 资金与成本
├── 订单与交付
└── 工资结算
```

“报表”不再作为总入口名称，而作为页面中的能力名称出现，例如：

- 导出资金明细
- 导出订单核算
- 导出发货汇总
- 导出工资结算

### 6.2 页面职责矩阵

| 页面 | 用户要解决的问题 | 首屏展示 | 明细内容 |
| --- | --- | --- | --- |
| 经营总览 | 现在经营得怎么样 | 收入、支出、结果、比例、异常 | 不展示完整表格 |
| 资金与成本 | 钱从哪里来、花到哪里 | 收入结构、支出构成、现金结果 | 收付款和成本明细 |
| 订单与交付 | 订单能否按时、按成本交付 | 交付状态、风险订单、处理入口 | 交期、产能、排班、订单核算 |
| 工资结算 | 工资是否核对、确认、付款 | 结算状态、工资总额、待处理项 | 工资结算明细 |

## 7. 页面一：经营总览

### 7.1 页面定位

经营总览是老板或负责人每天打开的页面，不是数据查询页。

它只负责回答：

- 收入是多少？
- 支出是多少？
- 最后留下多少？
- 支出去了哪里？
- 有没有必须处理的事情？

### 7.2 推荐布局

```text
经营总览
2026-09 · 实际收付款口径

┌────────────────────────────────────────────┐
│ 实际收入 ¥100,000                          │
│ − 经营支出 ¥40,000                         │
│ = 经营结果 ¥60,000                         │
│                                            │
│ 经营结果占收入 60%                         │
└────────────────────────────────────────────┘

钱去了哪里
工资              ¥10,000       25% 的经营支出
其他经营支出      ¥30,000       75% 的经营支出

经营判断
本月每收到 ¥100，约 ¥40 用于经营支出，
最终形成 ¥60 的现金经营结果。

需要处理
交期风险    YUMI-001       已逾期        进入处理
产能风险    羊毛杯垫         缺口 30 件    查看详情
工资结算    3 笔待确认                    查看结算
```

### 7.3 首屏模块

#### A. 统计口径区

展示：

- 当前统计月份。
- “实际收付款口径”说明。
- 月份切换入口。
- 刷新数据入口。

不展示：

- 过多筛选条件。
- 订单筛选、风险筛选、工资筛选等明细条件。

#### B. 核心经营结果

使用一条清晰的经营公式：

```text
实际收入 − 经营支出 = 现金经营结果
```

其中：

- 实际收入：本月实际收到的金额。
- 经营支出：本月实际支付且归入经营支出的金额。
- 现金经营结果：按照当前数据口径计算出的收入减支出结果。

展示比例：

- 收入：固定作为 100% 基准。
- 经营支出：占收入比例。
- 经营结果：占收入比例。

#### C. 支出构成

第一阶段展示：

- 已确认工资。
- 其他经营支出。

每一项同时展示两个比例：

1. 占经营支出比例。
2. 占收入比例。

页面必须明确分母，例如：

```text
25% 的经营支出 / 10% 的收入
```

不能只显示一个没有解释的“25%”。

“其他经营支出”在第一阶段定义为：

```text
经营支出 − 已确认并实际发放工资
```

并明确说明它是剩余经营付款，不代表完整的订单成本分摊。

#### D. 经营判断

使用自然语言把数字翻译成判断：

```text
本月每收到 ¥100，约 ¥40 用于经营支出，最终形成 ¥60 的现金经营结果。
```

不增加没有真实数据支持的环比、同比或未来预测。

#### E. 需要处理

只展示高优先级、可行动的少量事项，建议最多 3～5 条。

每条事项包含：

- 事项类型。
- 对象名称。
- 当前状态或风险原因。
- 下一步动作。

例如：

```text
交期风险 / YUMI-001 / 已逾期 / 进入处理
产能风险 / 羊毛杯垫 / 缺口 30 件 / 查看详情
工资结算 / 3 笔待确认 / 待确认 / 查看结算
```

超过展示数量的内容通过“查看全部”进入对应页面，不在总览页继续展开。

### 7.4 经营总览明确不放

- 完整订单表格。
- 完整交期风险表格。
- 完整产能风险表格。
- 完整排班进度表格。
- 完整工资结算表格。
- 每笔付款记录。
- 每个订单的成本明细。

## 8. 页面二：资金与成本

### 8.1 页面定位

资金与成本页面解决：

> 钱从哪里来，花到哪里，成本结构是否合理。

### 8.2 首屏结构

```text
资金与成本
2026-09

收入概况
实际收入       ¥100,000
待收款          ¥20,000
退款 / 售后      ¥3,000

支出构成
工资           ¥10,000    25%
材料            ¥8,000    20%
包装            ¥4,000    10%
物流            ¥8,000    20%
其他经营支出   ¥10,000    25%

现金经营结果
收入 ¥100,000 − 支出 ¥40,000 = 结果 ¥60,000
```

### 8.3 明细层

明细可以使用表格，但应该位于总结内容之后，并支持按类型切换：

- 收款明细。
- 付款明细。
- 工资付款明细。
- 材料、包装、物流等支出明细。
- 退款或售后资金影响明细。

### 8.4 口径边界

资金与成本关注真实资金流动：

- 实际收款。
- 实际付款。
- 工资发放。
- 其他经营支出。

订单与交付页面的订单核算关注订单层面的业务核算：

- 订单金额。
- 已收款。
- 待收款。
- 商品成本。
- 售后成本。
- 已知利润或已知毛利。

这两个页面不直接合并成一个“利润”数字。

## 9. 页面三：订单与交付

### 9.1 页面定位

订单与交付页面解决：

> 订单能不能按时、按成本完成？哪里卡住了？下一步应该处理什么？

以下内容统一归入此页面：

- 订单核算。
- 商品产能风险。
- 交期风险。
- 排班进度。

### 9.2 首屏先展示状态，不先展示表格

```text
订单与交付

待交付订单       12
存在交期风险      2
存在产能缺口      1
排班未开始        3
已完成交付        8
```

然后展示重点订单处理列表：

```text
重点关注订单

YUMI-001
羊毛杯垫 · 100 件
交付日期：2026-09-15
已排：20 件
风险：可用产能不足 30 件
[进入处理]
```

### 9.3 详细视图

建议拆成三个视图或标签：

```text
[交付风险] [生产进度] [订单核算]
```

#### 交付风险

- 已逾期订单。
- 即将到期订单。
- 产能不足订单。
- 未排班订单。
- 风险来源和处理入口。

#### 生产进度

- 已确认数量。
- 制作中。
- 待捏毛 / 装袋。
- 待打包。
- 待发货。
- 已发货。

#### 订单核算

- 订单金额。
- 已收款。
- 待收款。
- 商品成本。
- 售后成本。
- 已知利润或已知核算结果。

完整表格保留在这些详细视图中，不放回经营总览。

## 10. 页面四：工资结算

### 10.1 页面定位

工资结算不是普通统计表，而是一个需要持续处理的业务流程。

它要回答：

- 本月已经发了多少工资？
- 工资占经营支出多少？
- 哪些结算待核对？
- 哪些结算待确认？
- 哪些结算待付款？

### 10.2 首屏结构

```text
工资结算

本月已发工资       ¥10,000
占经营支出          25%

待核对              2 笔
待确认              1 笔
待付款              1 笔
已完成              8 笔
```

下面展示待处理结算：

```text
张三
结算周期：09-01 至 09-07
应发金额：¥1,200
当前状态：待确认
[查看结算]
```

完整工资表放在“全部记录”或状态明细中，不默认全部铺开。

## 11. 页面跳转关系

经营总览是所有页面的入口，入口必须指向可继续处理的上下文。

```text
经营总览
│
├── 点击经营支出       → 资金与成本
├── 点击工资占比       → 工资结算
├── 点击交期风险       → 订单与交付 / 交付风险
├── 点击产能缺口       → 订单与交付 / 交付风险
└── 点击订单成本       → 订单与交付 / 订单核算
```

从总览跳转到明细页面时，应保留：

- 当前统计月份。
- 当前业务视图。
- 当前风险筛选。
- 当前对象或订单。

例如：

```text
经营总览 → 交期风险 2 条

进入订单与交付后默认：
统计月份：2026-09
当前视图：交付风险
筛选：仅显示高风险
```

用户不需要重新设置同一组条件。

## 12. 视觉与交互原则

### 12.1 首屏保持单一主叙事

首屏主叙事固定为：

```text
收入 − 支出 = 经营结果
```

其他内容围绕这个结论解释，不与它竞争。

### 12.2 使用账本式结构，而不是指标卡矩阵

推荐：

- 一条经营公式。
- 一块支出构成。
- 一段经营判断。
- 一组待处理事项。

不推荐：

- 四列或六列指标卡。
- 每个指标一个独立大卡片。
- 把所有模块都包装成相同的卡片。

### 12.3 使用比例带和处理列表

比例适合回答“钱去了哪里”，处理列表适合回答“下一步做什么”。

不需要增加复杂图表。除非后续拥有真实的历史数据和明确的分析需求，否则不增加：

- 趋势折线。
- 环形图。
- 雷达图。
- 预测图。
- 没有业务含义的装饰性图表。

### 12.4 表格只承担追溯职责

表格不是被禁止，而是重新定位：

- 总览页：不展示完整表格。
- 业务页：先展示结论和状态，再展示表格。
- 表格页：提供筛选、排序、导出和逐条处理。

## 13. 数据与统计口径

### 13.1 月度经营结果

```text
现金经营结果 = 实际收入 − 经营支出
```

统计依据：

- 实际收款日期。
- 实际经营付款日期。
- 已确认并实际发放的工资。

### 13.2 比例分母

页面所有比例必须明确分母：

| 指标 | 分子 | 分母 |
| --- | --- | --- |
| 收入基准 | 实际收入 | 实际收入 |
| 支出占收入 | 经营支出 | 实际收入 |
| 结果占收入 | 经营结果 | 实际收入 |
| 工资占支出 | 已确认工资 | 经营支出 |
| 工资占收入 | 已确认工资 | 实际收入 |
| 其他支出占支出 | 其他经营支出 | 经营支出 |
| 其他支出占收入 | 其他经营支出 | 实际收入 |

### 13.3 零值和异常

- 实际收入为 0 时，收入占比、支出占收入、结果占收入显示 `—`。
- 经营支出为 0 时，工资占支出、其他支出占支出显示 `—`。
- 已确认工资高于经营支出时，不显示负的“其他经营支出”，而是显示数据口径异常提示。
- 不为了补齐图形而虚构比例或趋势。

### 13.4 订单成本边界

订单商品成本、售后成本可以用于订单核算，但在当前阶段不直接混入月度现金经营结果。

页面必须明确提示：

```text
订单商品成本、售后成本属于订单核算口径，不与本月现金经营结果混算。
```

## 14. 分阶段实施建议

本方案确认后，建议按以下顺序实施。

### 阶段一：确认信息架构

产出：

- 四个页面的导航关系。
- 每个页面的职责边界。
- 总览页与明细页的内容清单。

本阶段不改代码。

### 阶段二：建立页面骨架

产出：

- 经营总览页面。
- 资金与成本页面。
- 订单与交付页面。
- 工资结算页面。
- 页面之间的跳转关系。

先完成信息层级，不追求视觉细节。

### 阶段三：迁移现有内容

迁移原则：

- 现有数据来源尽量复用。
- 现有导出能力保留。
- 现有风险处理入口保留。
- 将完整表格移动到正确页面。
- 重新组织筛选器，使其只出现在相关页面。

### 阶段四：统一视觉和交互

统一处理：

- 金额层级。
- 比例展示。
- 风险状态。
- 空状态。
- 加载状态。
- 页面间返回逻辑。
- 小窗口和窄屏适配。

### 阶段五：验证

验证重点：

- 总览页是否不再出现完整表格。
- 用户是否能从异常事项进入处理页面。
- 月份筛选是否能跨页面保持。
- 统计口径是否清晰。
- 订单成本是否没有被误算进现金经营结果。
- 原有导出和跳转能力是否保持。

## 15. 验收标准

### 15.1 经营总览

- 首屏不出现完整数据表格。
- 首屏可以直接看到收入、支出和经营结果。
- 收入、支出、结果都能看到明确比例。
- 可以看懂工资和其他经营支出的构成。
- 最多展示少量需要处理的事项。
- 每个事项都有明确的下一步入口。

### 15.2 资金与成本

- 可以查看收入、支出和成本构成。
- 可以追溯到具体收付款记录。
- 可以区分实际资金流和订单核算成本。
- 支出分类和比例的分母明确。

### 15.3 订单与交付

- 可以先看订单交付状态，再进入明细表格。
- 交期、产能、排班和订单核算有统一入口。
- 风险订单能够直接进入处理动作。
- 不需要用户在多个页面重复查找同一个订单。

### 15.4 工资结算

- 可以先看工资结算状态，再进入工资明细。
- 可以看到工资总额和工资占经营支出的比例。
- 待核对、待确认、待付款和已完成状态清晰。
- 用户能够直接进入具体结算处理。
